Lecture 36

Linux Capability

영상 16분

"root냐 아니냐"의 이분법은 너무 거칩니다. 시각을 맞추려는 프로그램에게 Disk를 포맷할 권한까지 줄 이유가 없습니다. Capability는 root의 권한을 약 40개로 쪼갠 것입니다.

학습 목표

  • 전통적인 root/setuid 모델의 문제와 Capability의 발상을 설명할 수 있다.
  • Process의 다섯 Capability 집합을 읽고, 권한 검사가 Effective 집합으로 이루어짐을 설명할 수 있다.
  • File Capability(setcap)로 setuid root 없이 필요한 권한만 부여할 수 있다.
  • root로 시작한 프로그램이 초기화 후 필요한 Capability만 남기고 권한을 내려놓는 코드를 작성할 수 있다.

36-2. 전부 아니면 전무: root와 setuid의 문제

전통적인 Unix의 권한 검사는 한 줄입니다.

if (euid == 0)  /* 모든 검사를 통과 */

일반 사용자가 특권이 필요한 일(비밀번호 변경은 /etc/shadow 쓰기가 필요)을 하려면 setuid root 프로그램을 거칩니다.

ls -l /usr/bin/passwd

-rwsr-xr-x 1 root root 64152 ... /usr/bin/passwd

s bit가 있으면 누가 실행하든 euid = 0으로 실행됩니다. 문제는 그 순간 그 Process가 root의 모든 권한을 갖는다는 것입니다. passwd에 필요한 것은 File 하나를 고칠 권한뿐인데, Bug(Buffer Overflow 등)가 하나라도 있으면 공격자는 System 전체를 얻습니다. setuid root 프로그램의 취약점이 곧 "권한 상승 취약점"인 이유입니다.

집합 의미

36-6. File Capability: setuid root 없이

실행 File에 Capability를 붙일 수 있습니다(File System의 확장 속성 security.capability에 저장).

sudo setcap cap_sys_nice+ep ./capdemo
getcap ./capdemo
./capdemo

./capdemo cap_sys_nice=ep
uid=1000 euid=1000
/etc/shadow 읽기                       CAP_DAC_READ_SEARCH    Permission denied
우선순위 올리기 nice(-5)               CAP_SYS_NICE           성공
File 소유자를 uid 1 로 변경            CAP_CHOWN              Operation not permitted
256MB 를 mlock (RLIMIT_MEMLOCK 초과)   CAP_IPC_LOCK           Cannot allocate memory

일반 사용자(uid 1000)로 실행했는데 nice(-5)만 성공합니다. 이 프로그램에 Bug가 있어 공격자에게 장악되더라도 얻는 것은 "우선순위를 올릴 권한"뿐입니다. setuid root였다면 System 전체였습니다.

cap_sys_nice+ep의 의미
p (Permitted) exec 후 Process의 Permitted에 넣는다
e (Effective) 곧바로 Effective에도 켠다. Capability를 모르는 기존 프로그램을 위한 것
i (Inheritable) Process의 Inheritable과 교집합

exec 때의 계산은 (단순화하면) 다음과 같습니다.

P'(permitted) = ( P(inheritable) & F(inheritable) ) | ( F(permitted) & P(bounding) ) | P'(ambient)
P'(effective) = F(effective) ? P'(permitted) : P'(ambient)

System에서 실제로 쓰이는 예를 찾아봅니다.

getcap -r /usr/bin /usr/sbin 2>/dev/null

/usr/bin/ping cap_net_raw=ep
/usr/bin/mtr-packet cap_net_raw=ep

ping은 과거에 setuid root였지만 지금은 cap_net_raw 하나만 가집니다(배포판에 따라 다름).

⚠ WARNING
File Capability는 복사하면 사라지고(cp는 확장 속성을 기본으로 복사하지 않음), File을 수정하면 Kernel이 지웁니다. 다시 Build한 뒤에는 setcap을 다시 해야 합니다. nosuid로 Mount된 File System과 Script(#!)에는 적용되지 않습니다.

sudo setcap -r ./capdemo        # 제거

36-7. 권한 내려놓기

Server 프로그램의 전형적인 구조는 "root로 시작 → 특권이 필요한 초기화 → 권한을 버리고 일반 사용자로 → 본 작업" 입니다. dropcaps.c는 CAP_SYS_NICE 하나만 남깁니다.

prctl(PR_SET_KEEPCAPS, 1);                              /* uid 를 바꿔도 Permitted 를 유지하라 */
setgroups(0, NULL); setresgid(RUN_AS, …); setresuid(RUN_AS, RUN_AS, RUN_AS);    /* 순서: Group → gid → uid */

caps = cap_init();                                      /* 빈 집합에서 시작해 */
cap_set_flag(caps, CAP_PERMITTED, 1, keep, CAP_SET);    /* 필요한 것만 넣는다 */
cap_set_flag(caps, CAP_EFFECTIVE, 1, keep, CAP_SET);
cap_set_proc(caps);

prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);                 /* 이후 어떤 exec 로도 권한을 얻지 못한다 */

sudo ./dropcaps

1. root (초기화 단계)          uid=0     /etc/shadow: 읽힘                nice(-5): 성공
2. nobody + CAP_SYS_NICE       uid=65534 /etc/shadow: Permission denied   nice(-5): 성공
현재 Capability: cap_sys_nice=ep
3. root 로 돌아가기: Operation not permitted  ← 되돌릴 수 없다
주의점
PR_SET_KEEPCAPS 없으면 uid 0을 떠나는 순간 Permitted가 전부 지워진다. 있어도 Effective는 지워지므로 다시 켜야 한다
순서 uid를 먼저 바꾸면 gid를 바꿀 권한(CAP_SETGID)이 이미 없다. 보조 Group → gid → uid
setresuid real, effective, saved 세 개를 모두 바꾼다. saved uid가 0으로 남으면 되돌아갈 수 있다
return 값 확인 setuid 계열의 실패를 무시해 root로 계속 실행된 사고가 실제로 여러 번 있었다
Thread Capability는 Thread별이다. Thread를 만들기 전에 버리거나 libcap의 psx를 사용

이 코드가 Final Project의 harden.h에 그대로 들어갑니다.

36-8. Bounding Set, NoNewPrivs, 그리고 Container

장치 효과
Bounding Set 여기서 뺀 Capability는 이 Process와 모든 자손이 setuid root나 File Capability로도 얻을 수 없다. Container Runtime이 Container를 시작할 때 줄여 둔다
PR_SET_NO_NEW_PRIVS 이후의 execve가 권한을 늘리는 모든 경로(setuid bit, File Capability)를 무시한다. 한 번 켜면 끌 수 없고 자손에게 상속된다. L37의 seccomp에 필수 
docker run --rm ubuntu sh -c 'grep Cap /proc/self/status'

CapPrm:	00000000a80425fb
CapEff:	00000000a80425fb
CapBnd:	00000000a80425fb

Docker Container 안의 root는 uid 0이지만 Capability는 14개뿐입니다. CAP_SYS_ADMIN, CAP_SYS_PTRACE, CAP_SYS_MODULE, CAP_SYS_TIME, CAP_BPF, CAP_PERFMON이 없습니다. Chapter 7의 도구들이 Container에서 동작하지 않았던 이유 중 하나입니다. --cap-add, --cap-drop, --privileged(전부 허용)가 이 집합을 조절합니다.

make clean

정리

  • 전통적인 모델은 euid 0이면 전부 허용. setuid root 프로그램의 Bug 하나가 System 전체를 내줍니다.
  • Capability는 root의 권한을 약 40개로 나눈 것입니다. Kernel의 검사는 capable(CAP_XXX)이고 Effective 집합을 봅니다. CAP_SYS_ADMIN은 지나치게 비대합니다.
  • 다섯 집합: Effective(지금 쓰이는 것), Permitted(상한), Inheritable, Bounding(천장), Ambient. /proc/PID/status, capsh --decode, getpcaps.
  • File Capability(setcap cap_xxx+ep): setuid root 없이 필요한 권한만. 수정·복사하면 사라집니다.
  • 권한 내려놓기: PR_SET_KEEPCAPS → Group/gid/uid 순으로 전환 → 필요한 것만 담아 cap_set_proc → PR_SET_NO_NEW_PRIVS. 되돌릴 수 없어야 합니다.
  • Container의 root는 Capability가 줄어든 root입니다.

    /* 4. CAP_SYS_NICE 하나만 남기고 전부 버린다 */
    caps = cap_init();                                  /* 빈 집합에서 시작 */
    cap_set_flag(caps, CAP_PERMITTED, 1, keep, CAP_SET);
    cap_set_flag(caps, CAP_EFFECTIVE, 1, keep, CAP_SET);
    if (cap_set_proc(caps) < 0) {
        perror("cap_set_proc");
        return EXIT_FAILURE;
    }
    cap_free(caps);

    /* 5. 이후 어떤 방법으로도(setuid 실행 File, File Capability) 권한을 다시 얻지 못하게 한다 */
    prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);

PR_SET_KEEPCAPS 가 없으면 uid 0 을 떠나는 순간 Permitted 집합이 전부 지워집니다. 전환 순서는 보조 Group → gid → uid 입니다. cap_init() 로 빈 집합에서 시작해 필요한 것만 넣고 cap_set_proc 로 적용합니다. 마지막 PR_SET_NO_NEW_PRIVS 는 이후 setuid 실행 File 이나 File Capability 로 권한을 다시 얻는 길을 막습니다.

37-1. 무엇을 막으려는가

Linux의 System Call은 약 400개입니다. 하나하나가 User Space에서 Kernel 코드로 들어가는 문이고, Kernel의 취약점은 대부분 이 문들 뒤에 있습니다. 그런데 보통의 프로그램이 실제로 쓰는 것은 그중 수십 개입니다(L40의 monitor는 30개).

공격자가 Process를 장악했을 때 Capability로 seccomp로
execve("/bin/sh")로 Shell 실행 막을 수 없다 (특권이 필요 없다) 막을 수 있다
socket/connect로 외부에 Data 유출 막을 수 없다 막을 수 있다
잘 쓰이지 않는 System Call의 Kernel 취약점 공격 막을 수 없다 그 System Call 자체를 호출할 수 없다

"이 프로그램은 이 System Call들만 쓴다"를 선언해 두면, 장악당하더라도 그 밖의 일은 할 수 없습니다.

37-2. Strict Mode: 네 개만 허용

2005년의 첫 seccomp는 단순했습니다. read, write, _exit, sigreturn 넷만 허용하고 그 외에는 즉시 SIGKILL입니다. strict.c

prctl(PR_SET_SECCOMP, SECCOMP_MODE_STRICT);

./strict; echo "exit=$?"

0. 진입 전: 무엇이든 할 수 있다 (pid 827)
1. Strict Mode 진입 후: write 는 허용된다
2. 이제 open 을 시도한다...
Killed
exit=137

open을 호출하는 순간 죽었습니다(137 = 128 + SIGKILL 9). "신뢰할 수 없는 계산 코드에게 미리 열어 둔 fd로 입출력만 허용"하는 용도였지만 너무 제한적이어서 거의 쓰이지 않았습니다.

37-3. Filter Mode: Filter는 BPF Program이다

2012년에 추가된 Filter Mode(seccomp-bpf)는 어떤 System Call을 어떤 인자로 허용할지를 BPF Program으로 기술합니다. L35의 eBPF의 조상인 classic BPF입니다. Filter에 주어지는 입력은 이 구조체 하나입니다.

struct seccomp_data {
    int   nr;                       /* System Call 번호 */
    __u32 arch;                     /* AUDIT_ARCH_X86_64 등 */
    __u64 instruction_pointer;
    __u64 args[6];                  /* 인자 6 개 (Register 값 그대로) */
};

rawbpf.c는 Library 없이 Filter를 직접 작성합니다. 규칙은 "mkdir/mkdirat은 EACCES로 실패시키고 나머지는 허용"입니다.

struct sock_filter filter[] = {
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, arch)),       /* A = arch */
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, AUDIT_ARCH_X86_64, 1, 0),                  /* x86-64 가 아니면 */
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),                           /*   죽인다 */
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, nr)),         /* A = System Call 번호 */
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, SYS_mkdir, 2, 0),
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, SYS_mkdirat, 1, 0),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),                                  /* 허용 */
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | (EACCES & SECCOMP_RET_DATA)),    /* 실행하지 않고 EACCES */
};
prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);
prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog);

./rawbpf

Filter 설치 완료 (BPF 명령어 8 개)
mkdir  → 실패: Permission denied   ← Kernel 은 mkdir 을 실행조차 하지 않았다
getpid → 828 (허용)
   NoNewPrivs:	1
   Seccomp:	2
   Seccomp_filters:	1

/proc/PID/status의 Seccomp: 2가 Filter Mode입니다(0 없음, 1 Strict).

Filter의 성질
되돌릴 수 없다 설치한 Filter는 제거할 수 없다. 더 추가할 수만 있고, 여러 Filter가 있으면 가장 엄격한 결과가 적용된다
상속된다 fork, clone, execve 후에도 유지
NO_NEW_PRIVS가 필수 (root가 아니면) Filter를 건 채 setuid 프로그램을 실행해, 그 프로그램의 System Call을 실패시켜 오동작을 유도하는 공격을 막는다 (L36)
arch를 먼저 검사 x86-64에서 32bit System Call(int 0x80)은 번호 체계가 다르다. 검사하지 않으면 우회된다
실행 비용 System Call마다 Filter 실행. 수십 ns. Kernel은 "항상 허용"인 번호를 Bitmap으로 Cache한다

37-5. libseccomp로 Allowlist 만들기

BPF를 손으로 쓰는 것은 번거롭고 실수하기 쉽습니다(arch 검사 누락, 번호 오타). libseccomp가 규칙을 BPF로 Compile해 줍니다. sandbox.c

scmp_filter_ctx ctx = seccomp_init(SCMP_ACT_ERRNO(EPERM));          /* 기본: 목록에 없으면 EPERM */
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(read), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit_group), 0);
...
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 1,
                 SCMP_A0(SCMP_CMP_LE, 2));                          /* write 는 fd ≤ 2 일 때만 */
seccomp_load(ctx);                                                  /* Compile → 설치 (NO_NEW_PRIVS 자동) */

./sandbox

Mode: ERRNO(EPERM)
1. write(stdout)            → 허용
2. write(fd 3, 이미 열린 File) → Operation not permitted   ← 인자(fd) 검사에 걸림
3. open("/etc/passwd")       → Operation not permitted
4. fork()                   → Operation not permitted
5. 끝까지 실행됨

Denylist가 아니라 Allowlist입니다. "위험한 것을 막는다"가 아니라 "필요한 것만 허용한다"여야 합니다. Kernel에는 새 System Call이 계속 추가되므로(openat2, clone3, io_uring_*) Denylist는 시간이 지나면 뚫립니다.

2번을 보세요. Filter 설치 전에 이미 열어 둔 fd 3에 대한 write도 인자 조건(fd ≤ 2)에 걸려 거부됩니다. 반대로 조건이 없었다면 허용됩니다. seccomp는 "이 fd가 무엇을 가리키는가"는 모릅니다. 숫자만 봅니다.

37-6. 위반하면 어떻게 할 것인가

./sandbox kill; echo "exit=$?"

Mode: KILL_PROCESS
1. write(stdout)            → 허용
Bad system call
exit=159

159 = 128 + 31(SIGSYS). Kernel Log에 기록이 남습니다.

sudo dmesg | tail -n 1          # 또는 journalctl -k | grep type=1326

audit: type=1326 … pid=830 comm="sandbox" exe="…/sandbox" sig=31 arch=c000003e syscall=1 compat=0 ip=0x7feb46f1c844 code=0x80000000

syscall=1은 write입니다(fd 3에 대한 것). 어떤 System Call 때문에 죽었는지를 여기서 알 수 있습니다.

Action 동작 용도
SCMP_ACT_ALLOW 실행
SCMP_ACT_ERRNO(e) 실행하지 않고 -1, errno = e 프로그램이 오류를 처리하며 계속 실행. 호환성이 필요할 때 (Docker의 기본)
SCMP_ACT_KILL_PROCESS SIGSYS로 Process 전체 종료 가장 안전. 위반 = 침입으로 간주
SCMP_ACT_KILL_THREAD 그 Thread만 종료 나머지 Thread가 이상한 상태로 남는다. 피한다
SCMP_ACT_LOG 허용하되 Log에 기록 Allowlist를 만드는 과정에서
SCMP_ACT_TRAP SIGSYS Handler로 (어떤 호출이었는지 siginfo에) Debug, Emulation
SCMP_ACT_NOTIFY 다른 Process(Supervisor)에게 결정을 위임 Container Runtime이 mount 등을 대신 수행

⚠ WARNING
ERRNO는 조용한 오동작을 만들 수 있습니다. glibc나 Library가 내부적으로 쓰는 System Call이 거부되면 프로그램은 전혀 관계없어 보이는 곳에서 실패합니다(예: printf가 Terminal 여부를 확인하는 ioctl, malloc이 쓰는 mmap/brk, Thread 생성의 clone3). 거부된 호출을 찾을 때는 strace -Z(실패한 것만)가 유용합니다.

37-7. Allowlist는 어떻게 만드는가

L32의 strace -c -f가 출발점입니다.

strace -c -f -o calls.txt ./대상프로그램; awk 'NR>2 && $NF!="total" {print $NF}' calls.txt | sort
절차
1. 수집 모든 기능을 실행해 보며 strace -f -c. 오류 처리 경로와 종료 경로도 포함. L35의 bpftrace syscount.bt로 운영 중에 수집할 수도 있다
2. 초기화와 본 작업을 나눈다 execve, openat(설정 File), socket, bind는 초기화에만 필요한 경우가 많다. Filter는 초기화가 끝난 뒤에 설치하면 목록이 훨씬 짧아진다
3. SCMP_ACT_LOG로 시험 운영 빠뜨린 것이 Log에 남는다
4. ERRNO 또는 KILL로 전환
5. 유지 보수 glibc나 Compiler를 올리면 내부에서 쓰는 System Call이 바뀐다(open → openat, clone → clone3, rseq 추가 …). Library Upgrade 후에 Filter 때문에 죽는 것이 seccomp 운영의 가장 흔한 문제

Final Project의 harden.h가 이 절차로 만든 30개짜리 Allowlist입니다.

한계 내용
포인터 인자를 역참조할 수 없다 Filter는 args[]의 숫자만 본다. openat(…, "/etc/shadow", …)의 경로 문자열은 검사할 수 없다(검사 후에 다른 Thread가 바꿀 수 있으므로 의미도 없다). 경로 기반 제한은 Landlock, AppArmor, SELinux의 영역
io_uring L27에서 봤듯이 io_uring은 SQE로 openat, read, connect를 수행한다. 이들은 System Call이 아니므로 seccomp Filter를 지나지 않는다. Filter에서 openat을 막아도 io_uring_enter가 허용되어 있으면 우회된다. Docker, Android, ChromeOS가 io_uring System Call 자체를 차단하는 이유

정리

  • seccomp는 System Call을 걸러 Kernel의 공격 표면을 줄입니다. 특권이 필요 없는 execve, socket도 막을 수 있어 Capability와 상호 보완입니다.
  • Strict Mode: read/write/_exit/sigreturn만. Filter Mode: struct seccomp_data(번호, arch, 인자 6개)를 입력으로 받는 BPF Program.
  • Filter는 되돌릴 수 없고, 상속되며, NO_NEW_PRIVS가 필요합니다. arch를 먼저 검사합니다.
  • libseccomp로 Allowlist를 만듭니다. 인자(숫자)에 조건을 걸 수 있습니다.
  • Action: ERRNO(호환성), KILL_PROCESS(안전), LOG(목록 작성 중). 위반은 Kernel Log의 type=1326에서 확인합니다.
  • 목록은 strace -c -f로 수집하고 초기화 후에 설치해 짧게 유지합니다. Library Upgrade에 주의합니다.
  • 포인터 인자(경로)는 볼 수 없고, io_uring은 Filter를 우회합니다.

static int install(int kill_mode)
{
    /* 기본 동작: Allowlist 에 없는 모든 System Call */
    scmp_filter_ctx ctx = (kill_mode ? SCMP_ACT_KILL_PROCESS : SCMP_ACT_ERRNO(EPERM));
    int             rc = 0;

    if (ctx == NULL)
        return -1;
    rc |= seccomp_rule_add(ctx, , SCMP_SYS(read), 0);
    rc |= seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit_group), 0);
    rc |= seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(rt_sigreturn), 0);
    rc |= seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(fstat), 0);
    rc |= seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(newfstatat), 0);
    /* 인자까지 검사: write 는 fd 1(stdout), 2(stderr) 에만 허용 */
    rc |= seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 1, (SCMP_CMP_LE, 2));
    if (rc == 0)
        rc = (ctx);                         /* BPF 로 Compile 해서 Kernel 에 설치 (NO_NEW_PRIVS 자동 설정) */
    seccomp_release(ctx);
    return rc;

    rc |= seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(rt_sigreturn), 0);

38-1. Namespace의 종류

Kernel의 전역 자원 가운데 일부를 Process Group마다 따로 보이게 하는 것이 Namespace입니다.

Namespace clone Flag 격리하는 것 도입
Mount (mnt) CLONE_NEWNS Mount Tree. 어떤 File System이 어디에 붙어 있는가 2002
UTS CLONE_NEWUTS hostname, domainname 2006
IPC CLONE_NEWIPC System V IPC, POSIX Message Queue (기존 과정 5장) 2006
PID CLONE_NEWPID Process 번호. 새 Namespace의 첫 Process가 PID 1 2008
Network (net) CLONE_NEWNET Network Interface, Routing, Port, iptables 2009
User CLONE_NEWUSER uid/gid와 Capability. 일반 사용자도 만들 수 있다 2013
Cgroup CLONE_NEWCGROUP Cgroup Tree의 Root가 어디로 보이는가 (L39) 2016
Time CLONE_NEWTIME CLOCK_MONOTONIC, CLOCK_BOOTTIME의 Offset 2020

핵심은 Kernel은 하나라는 것입니다. 가상 머신은 Hardware를 흉내 내어 Kernel을 여러 개 실행하지만, Namespace는 한 Kernel이 Process마다 다른 답을 돌려주는 것입니다. 그래서 가볍고(Process 하나 만드는 비용), 그래서 격리가 VM보다 약합니다.

38-7. User Namespace: root 없이 root 되기

지금까지의 실습은 전부 sudo가 필요했습니다(CAP_SYS_ADMIN). User Namespace만은 일반 사용자가 만들 수 있고, 그 안에서는 uid 0과 모든 Capability를 갖습니다. userns.c

unshare(CLONE_NEWUSER | CLONE_NEWUTS);
write("/proc/self/uid_map", "0 1000 1");        /* 안의 uid 0 ↔ 밖의 uid 1000, 1 개 */

./userns                                        # sudo 없이

밖: uid=1000
안: uid=0  ← Namespace 안에서는 root
    sethostname: 성공  ← 이 User Namespace 가 소유한 UTS Namespace 에 대해서는 CAP_SYS_ADMIN 이 있다
    /etc/shadow 읽기: Permission denied  ← Host 의 자원에 대해서는 여전히 원래 사용자
규칙
Capability는 그 User Namespace가 소유한 자원에만 유효하다 함께 만든 UTS Namespace의 hostname은 바꿀 수 있다. Host의 hostname, Host의 File은 안 된다
File 접근은 밖의 uid로 검사된다 /etc/shadow(root 소유)는 밖의 uid 1000으로는 읽을 수 없다
Mapping되지 않은 uid는 nobody(65534)로 보인다

Rootless Container(Podman, Rootless Docker), Browser Sandbox, Flatpak, bwrap이 이것으로 동작합니다. root 권한 없이 Container를 만들 수 있고, Container 안의 root가 탈출하더라도 Host에서는 일반 사용자입니다.

⚠ WARNING
User Namespace는 일반 사용자에게 "Namespace 안의 CAP_SYS_ADMIN"을 주므로, 평소에는 root만 도달할 수 있던 Kernel 코드(mount, netfilter 등)가 공격 표면에 들어옵니다. 실제로 많은 Kernel 취약점이 이 경로로 악용되었습니다. 그래서 Ubuntu 24.04부터는 AppArmor로 일반 프로그램의 User Namespace 생성을 기본 제한합니다(kernel.apparmor_restrict_unprivileged_userns). ./userns가 Permission denied로 실패하면 이 설정 때문입니다(오류 해결 참고).

38-8. Namespace가 격리하지 않는 것

격리되지 않는 것
Kernel 자체 모든 Container가 같은 Kernel을 쓴다. Kernel 취약점 하나가 전체의 탈출구가 된다. 그래서 seccomp(L37)로 System Call을 줄이고 Capability(L36)를 줄인다. 더 강한 격리가 필요하면 gVisor(User Space Kernel), Kata Containers / Firecracker(경량 VM)

시각(wall clock), Kernel Log, 일부 /proc·/sys 항목 /proc/meminfo, /proc/cpuinfo는 Host의 값이 보인다. Container 안의 프로그램이 Host의 CPU 수를 보고 Thread를 만드는 문제의 원인

정리

  • Namespace는 Kernel의 전역 자원을 Process Group마다 따로 보이게 합니다. 8종: mnt, uts, ipc, pid, net, user, cgroup, time. Kernel은 하나입니다.
  • /proc/PID/ns/*의 번호가 같으면 같은 Namespace. lsns.
  • 만들기: clone(CLONE_NEW*)(Child부터), unshare()(자신), 들어가기: setns(). 명령으로는 unshare, nsenter.
  • PID Namespace: 같은 Process가 밖에서는 860, 안에서는 1. /proc을 다시 Mount해야 ps가 안쪽만 봅니다(MS_PRIVATE 먼저). PID 1은 고아를 입양하고, 기본 Signal 동작이 무시되며, 죽으면 Namespace 전체가 죽습니다.
  • Host에서는 Container 안이 그대로 보입니다. nsenter = docker exec.
  • User Namespace는 일반 사용자도 만들 수 있고 안에서는 root지만, Capability는 그 Namespace가 소유한 자원에만 유효합니다. 공격 표면을 넓히므로 배포판이 제한하기도 합니다.
  • Namespace는 Kernel과 자원 사용량을 격리하지 않습니다.

Cgroup

영상 17분

Namespace가 "무엇이 보이는가"라면 Cgroup(Control Group)은 "얼마나 쓸 수 있는가" 입니다. Process들을 Group으로 묶고, Group마다 CPU, Memory, Process 수의 한도를 걸고, 사용량을 집계합니다. Interface는 이번에도 File입니다.

상황 Namespace, Capability, seccomp로
Container 하나가 무한 Loop로 CPU를 100% 쓴다 막을 수 없다
Memory Leak이 있는 Service가 Host의 Memory를 다 써서 다른 Service가 OOM Kill된다 막을 수 없다

ulimit(setrlimit)은 Process 하나에 대한 한도입니다. Process 100개를 만들면 100배를 씁니다. Cgroup은 Process들의 묶음에 한도를 걸고, 그 묶음의 자손이 아무리 늘어나도 합계로 계산합니다.

정리

  • Cgroup은 Process의 묶음에 자원 한도를 걸고 사용량을 집계합니다. ulimit은 Process 하나, Cgroup은 자손 전체의 합계.
  • v2는 /sys/fs/cgroup의 단일 Directory Tree. mkdir = Group 생성, cgroup.procs에 PID 쓰기 = 이동, cgroup.subtree_control로 Child에게 Controller를 켭니다. Process는 Leaf에만.
  • cpu.max = "quota period": 주기마다 quota만큼만 실행. 나머지는 Throttled. 평균 사용률이 낮아도 Latency가 튈 수 있고, 진단은 cpu.stat의 nr_throttled. cpu.weight는 경쟁 시의 비율.
  • memory.max: 닿으면 Group 안에서 Reclaim → 안 되면 OOM Kill(SIGKILL, Exit 137). malloc은 실패하지 않습니다. Page Cache도 계산됩니다. memory.high는 죽이지 않고 늦춥니다. memory.events의 oom_kill 을 감시합니다.
  • pids.max: fork/pthread_create가 EAGAIN.
  • systemd는 Service마다 Cgroup을 만들고(systemd-run, systemd-cgtop), Docker/Kubernetes의 자원 한도는 이 File들에 값을 쓰는 것입니다.

40-5. Worker Thread와 두 개의 eventfd

대상 몇 개의 /proc/PID/stat을 읽는 것은 수십 µs입니다. 그러나 모든 Process를 1초 간격으로 두 번 읽어 CPU 상위를 구하는 일은 1초 이상 걸립니다. 이것을 Timer Handler에서 하면 L26의 loop_stall이 됩니다.

{

        na = scan_all(a, 4096);  nanosleep(&gap, NULL);  nb = scan_all(b, 4096);        /* 오래 걸리는 일 */
        … 상위 N 개 계산 …
        pthread_mutex_lock(&top_lock);                              /* 결과를 넘길 때만 짧게 잠근다 */

방향 Mode 이유
req_efd main → Worker Blocking Worker는 할 일이 없으면 자야 한다. read에서 잠든다
done_efd Worker → main Non-blocking + epoll main은 다른 Event와 함께 기다린다
  • Worker가 아직 Scan 중인데 main이 또 요청하면? eventfd의 Counter에 합산됩니다(L25). 요청이 쌓여 밀리지 않습니다.
  • 공유하는 것은 top[] 하나이고 복사하는 동안만 잠급니다. Lock을 쥔 채 /proc을 읽지 않습니다(L20: Critical Section은 짧게).
  • 종료할 때는 stopping을 세우고 req_efd에 write해 Worker를 깨워서 빠져나오게 한 뒤 pthread_join합니다.

순서가 설계입니다. ① 특권이 필요한 자원을 모두 연다 → ② Thread를 만든다 → ③ uid와 Capability를 버린다 → ④ seccomp를 설치한다. seccomp를 먼저 설치하면 setresuid가 막히고, Thread를 나중에 만들면 clone3을 허용해야 합니다. 그리고 Capability는 Thread별이므로 Worker를 만든 뒤에 cap_set_proc을 하면 Worker에는 적용되지 않습니다. 이 예제는 설명의 편의상 Worker를 먼저 만들었으므로 Worker Thread는 축소 전의 Capability를 갖습니다. 제품 코드에서는 권한을 버린 뒤에 Thread를 만들고 clone3을 허용하거나 libcap의 psx로 모든 Thread에 적용합니다(확장 과제).

static inline int mlog_open(struct mlog *m, const char *path)
{
    m->bytes = sizeof(struct mlog_hdr) + sizeof(struct mrec) * MLOG_CAP;
    m->fd = open(path, O_RDWR | O_CREAT, 0644);

        return -1;
    m->hdr = mmap(NULL, m->bytes, PROT_READ | PROT_WRITE, MAP_SHARED, m->fd, 0);
    if (m->hdr == MAP_FAILED)
        return -1;
    m->rec = (struct mrec *)(m->hdr + 1);

        m->hdr->magic = MLOG_MAGIC;
        m->hdr->cap   = MLOG_CAP;
        m->hdr->total = 0;

    return 0;
}
