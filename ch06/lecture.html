Lecture 26

Linux Async I/O는 왜 필요해졌는가

영상 16분

epoll은 "읽을 수 있게 되면 알려 주는" 장치입니다. 그런데 Disk의 File은 언제나 "읽을 수 있다"고 답하고는, 막상 읽으면 잠듭니다. 이 Chapter는 그 빈틈을 메우는 이야기입니다.

학습 목표

  • Readiness 모델(epoll)과 Completion 모델의 차이를 설명할 수 있다.
  • 일반 File이 Readiness 모델에 맞지 않는 이유를 설명하고, Event Loop가 File I/O로 멈추는 현상을 재현할 수 있다.
  • 기존 해법(Thread Pool, POSIX AIO, Linux Native AIO)의 동작 방식과 한계를 설명할 수 있다.
  • io_uring이 해결하려는 두 가지 문제(진짜 비동기 File I/O, System Call 비용)를 말할 수 있다.

26-1. 복습: Chapter 5가 남긴 문제

Chapter 5에서 두 번 말했습니다. "일반 File은 epoll에 넣을 수 없다." 그리고 Single Thread Event Loop의 규칙은 "Handler는 Block하지 않는다" 였습니다. 그런데 프로그램은 File을 읽고 써야 합니다. Log, 설정, Database, Static File. 이 둘이 충돌합니다.

26-2. 일반 File은 언제나 "준비됨"이다

epoll_file.c

./epoll_file

epoll_ctl(ADD, 일반 File) = -1, errno = 1 (Operation not permitted)
poll(일반 File)           = 1, revents = 0x5  (POLLIN | POLLOUT) → 언제나 "준비됨"
→ Readiness 모델은 Disk File 에 대해 아무 정보도 주지 못한다.
  O_NONBLOCK 으로 열었어도 Page Cache Miss 면 read() 는 Disk 를 기다리며 잠든다.

epoll은 등록 자체를 거부하고(EPERM), poll은 "읽을 수도 쓸 수도 있다"고 항상 답합니다. L12의 file_operations에서 ext4는 .poll을 구현하지 않기 때문입니다.

왜 구현하지 않았을까요. Pipe의 "준비됨"은 "Buffer에 Data가 있다"로 명확합니다. File의 "준비됨"은 "읽으려는 그 Offset의 Page가 Page Cache에 있다"여야 하는데, 어느 Offset을 읽을지는 read()를 호출해 봐야 압니다. Readiness라는 질문 자체가 File에는 성립하지 않습니다.

26-3. Event Loop가 멈춘다

loop_stall.c는 10ms 주기의 timerfd로 "심장 박동"을 찍는 Event Loop입니다. 세 번째 Tick의 Handler에서 Cache를 비운 256MB File을 read합니다. L25에서 배운 대로 timerfd의 만료 횟수가 놓친 Tick의 수를 알려 줍니다.

./loop_stall

big.dat (256MB) 생성 중...
[   10.0 ms] tick 1  (만료 횟수 1)
[   20.0 ms] tick 2  (만료 횟수 1)
[   30.1 ms] tick 3  (만료 횟수 1)
             Handler: 256MB read 에 1207.4 ms
[ 1237.6 ms] tick 4  (만료 횟수 121)   ← 그동안 Loop 가 멈춰 있었다
[ 1240.0 ms] tick 5  (만료 횟수 1)
[ 1250.0 ms] tick 6  (만료 횟수 1)

(read에 걸리는 시간은 Disk에 따라 다릅니다. 놓친 Tick 수 ≈ read 시간 / 10ms)

1.2초 동안 Event Loop가 완전히 멈췄습니다. 이 Loop에 signalfd와 eventfd가 있었다면 Ctrl+C도, Worker의 통지도 1.2초 동안 처리되지 못했을 것입니다. O_NONBLOCK으로 열었지만 아무 효과가 없습니다(L21).

26-4. Readiness와 Completion

Readiness 모델 Completion 모델
질문 "지금 하면 Block되지 않는가?" "부탁한 일이 끝났는가?"
순서 ① 준비되면 알려 줘 → ② 통지 → ③ 내가 read() ① 이 Buffer에 읽어 줘 → ② Kernel이 읽음 → ③ 완료 통지
I/O를 수행하는 주체 Application (System Call 안에서) Kernel (Background에서)
대표 select, poll, epoll, kqueue io_uring, Windows IOCP, POSIX AIO
Pipe, Socket, Timer 잘 맞는다 가능
Disk File 맞지 않는다 (항상 "준비됨") 잘 맞는다
Buffer를 넘기는 시점 읽기 직전 요청할 때. 완료될 때까지 Buffer를 유지해야 한다

Readiness 모델에서는 통지를 받은 뒤에도 read()라는 System Call을 내가 또 해야 합니다. Completion 모델에서는 통지를 받았을 때 Data가 이미 내 Buffer에 들어 있습니다.

26-5. Animation: 두 모델 비교

  1. Readiness (epoll + pipe): 준비 통지 → read() → 복사.
  2. Readiness에 File을 넣으면: "준비됨"이라고 답하고는 read()에서 잠듭니다.
  3. Completion: 요청을 맡기고 Loop로 돌아갑니다. Kernel이 읽고 완료를 알립니다.

26-6. 기존 해법 1: Thread Pool과 POSIX AIO

가장 흔한 해법은 L25에서 본 것입니다. File I/O를 Worker Thread로 보내고 완료를 eventfd로 받습니다. Node.js(libuv), nginx의 aio threads, Python asyncio의 File I/O가 모두 이 방식입니다.

POSIX 표준의 aio_read()도 있습니다. 이름은 비동기 I/O이지만 glibc의 구현을 들여다보면 같은 방식입니다. posix_aio.c

./posix_aio

aio_read 호출 전 Thread 수: 1
aio_read 4 개 요청 직후 Thread 수: 2   ← glibc 가 Worker Thread 를 만들었다
요청 0 완료: 1111 Byte
요청 1 완료: 1111 Byte
요청 2 완료: 1111 Byte
요청 3 완료: 1111 Byte

aio_read를 호출하자 Thread가 생겼습니다. glibc가 몰래 만든 Thread가 평범한 Blocking pread를 대신 호출하는 것입니다. Kernel은 이것이 비동기 I/O인지 모릅니다.

strace -f -e trace=clone3,pread64 ./posix_aio 2>&1 | grep -E "clone3|pread64" | head -n 4

clone3({flags=CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|..., ...}) = 2715
[pid  2715] pread64(3, "root:x:0:0:root:/root:/bin/bash\n"..., 4096, 0) = 1111
[pid  2715] pread64(3, "root:x:0:0:root:/root:/bin/bash\n"..., 4096, 0) = 1111
Thread Pool 방식의 비용
요청마다 Thread 간 전달 Queue + Lock + futex + Context Switch 2회 (L19, L20)
동시 I/O 수 = Thread 수 NVMe는 수만 개의 요청을 동시에 받을 수 있는데 Thread를 수만 개 만들 수는 없다
완료 통지 POSIX AIO는 Signal 또는 Thread Callback. Event Loop와 맞지 않는다

느린 Disk(HDD, 10ms)에서는 이 비용이 묻힙니다. 그러나 NVMe SSD는 요청 하나를 수십 µs에 처리합니다. Software의 전달 비용이 장치의 처리 시간과 비슷해지면서 문제가 드러났습니다.

26-7. 기존 해법 2: Linux Native AIO

Linux에는 2.6 시절부터 Kernel이 직접 지원하는 비동기 I/O가 있었습니다(io_setup, io_submit, io_getevents. Library는 libaio). Thread를 쓰지 않는 진짜 비동기입니다. 그러나 널리 쓰이지 못했습니다.

한계 내용
O_DIRECT 전용 Buffered I/O에서는 io_submit이 조용히 Block된다. Page Cache를 쓰는 일반 프로그램에는 쓸모가 없다
그마저도 Block될 수 있다 Metadata 읽기, Block 할당, Queue가 가득 찼을 때
File 읽기/쓰기만 open, fsync(한동안), stat, Socket은 지원하지 않거나 뒤늦게 추가
요청마다 System Call io_submit 1회 + io_getevents 1회. 요청마다 64 + 32Byte 복사
불편한 API

자체 Cache를 갖고 O_DIRECT를 쓰는 Database(Oracle, MySQL InnoDB, ScyllaDB)만의 도구였습니다(L14).

26-8. 또 하나의 압력: System Call 비용

L02에서 System Call 한 번이 수백 ns라는 것을, L11에서 작은 I/O는 그 고정 비용이 지배한다는 것을 봤습니다. 2018년의 Spectre/Meltdown 대응(KPTI 등)으로 User ↔ Kernel 전환 비용은 더 커졌습니다.

I/O 1회의 장치 시간 System Call 비용(약 0.2~1µs)의 비중
HDD 약 10,000µs 무시 가능
SATA SSD 약 100µs 1%
NVMe SSD 약 10~20µs 5~10%
Optane, Page Cache Hit, Network의 작은 Packet 약 1~10µs 수십 %

장치가 빨라질수록 "I/O 한 번에 System Call 한 번(epoll은 두 번)"이라는 구조 자체가 병목이 됩니다.

26-9. io_uring의 설계 목표

2019년 Linux 5.1에 Jens Axboe(Block Layer Maintainer)가 추가한 io_uring은 위의 문제들을 한꺼번에 겨냥했습니다.

목표 방법 (이후 Lecture)
Buffered I/O를 포함한 진짜 비동기 File I/O 가능하면 즉시 처리, Block될 상황이면 Kernel 내부에서 비동기로 (L27, L30)
System Call 횟수 줄이기 요청과 완료를 공유 Memory의 Ring Buffer로 주고받는다. 여러 요청을 System Call 한 번에(Batch), 설정에 따라 0번 (L27~L30)
요청마다의 복사 없애기 Ring을 mmap으로 공유 (L10)
File만이 아닌 범용 비동기 Interface read/write뿐 아니라 open, close, fsync, statx, rename, timeout, poll, Socket 연산 … 60여 종
확장 가능한 설계 opcode를 추가하는 방식

📌 NOTE
io_uring이 epoll을 대체하는 것은 아닙니다. Readiness로 충분한 곳(Socket, Timer, Signal)에는 epoll이 여전히 단순하고 검증된 선택입니다. 두 모델은 목적이 다르며 함께 쓸 수도 있습니다(L30).

make clean

정리

  • Readiness 모델(epoll)은 "지금 하면 Block되지 않는가"를 알려 주고 I/O는 Application이 합니다. Completion 모델은 I/O를 맡기고 "끝났다"를 통지받습니다.
  • Disk File은 Readiness라는 질문이 성립하지 않습니다. epoll은 거부하고, poll은 항상 "준비됨"이라 답하며, O_NONBLOCK은 효과가 없습니다. Event Loop 안의 File read는 Loop 전체를 멈춥니다.
  • 기존 해법: Thread Pool(POSIX AIO도 실제로는 이것)은 요청마다 Thread 전달 비용이 들고 동시 I/O 수가 Thread 수로 제한됩니다. Linux Native AIO는 O_DIRECT 전용이었습니다.
  • 장치가 빨라지면서 System Call 비용 자체가 병목이 되었습니다.
  • io_uring의 목표: Buffered I/O까지 포함한 진짜 비동기 + 공유 Ring Buffer로 System Call과 복사 줄이기 + 범용 Interface.

Lecture 27

io_uring Architecture

영상 17분

io_uring은 Application과 Kernel이 Memory를 공유하는 두 개의 Ring Buffer입니다. 요청은 Submission Queue에 적고, 결과는 Completion Queue에서 읽습니다. 적고 읽는 데는 System Call이 필요 없습니다.

학습 목표

  • io_uring의 구성 요소(SQ, CQ, SQE 배열, Ring fd)와 세 개의 System Call을 설명할 수 있다.
  • liburing으로 File을 읽는 최소 프로그램을 작성할 수 있다.
  • liburing 없이 System Call만으로 같은 일을 하는 코드를 읽고, 공유 Memory의 Mapping을 /proc에서 확인할 수 있다.
  • 실행 환경이 io_uring을 지원하는지, 어떤 연산을 지원하는지 확인할 수 있다.

구성 요소 역할
SQ (Submission Queue) Application → Kernel. "이 일을 해 달라"
CQ (Completion Queue) Kernel → Application. "끝났다. 결과는 이것"
SQE (Submission Queue Entry) 요청 하나. opcode, fd, Buffer 주소, 길이, Offset, user_data
CQE (Completion Queue Entry) 결과 하나. user_data(요청의 꼬리표), res(return 값), flags
Ring fd 이 io_uring Instance를 가리키는 fd. anon_inode:[io_uring]
System Call 역할 빈도
io_uring_setup(entries, &params) Ring을 만들고 fd를 return 한 번
io_uring_enter(fd, to_submit, min_complete, flags, …) SQ의 요청을 Kernel에 알리고, 원하면 완료를 기다린다 여러 요청에 한 번
io_uring_register(fd, opcode, …) Buffer, File, eventfd 등을 미리 등록 (L30) 가끔

L23의 epoll과 발상이 닮았습니다. epoll은 "관심 목록을 Kernel에 두어" 매번 넘기는 비용을 없앴고, io_uring은 "요청과 결과가 오가는 통로 자체를 공유 Memory에 두어" 매번 복사하고 System Call하는 비용을 없앴습니다.

27-3. 가장 작은 io_uring 프로그램

uring_hello.c

io_uring_queue_init(8, &ring, 0);                       /* 1. Ring 생성: SQ 8 칸 (CQ 는 16 칸) */

sqe = io_uring_get_sqe(&ring);                          /* 2. 빈 SQE 하나를 얻는다 (System Call 아님) */
io_uring_prep_read(sqe, fd, buf, sizeof(buf) - 1, 0);   /* 3. "fd 의 offset 0 에서 buf 로 읽어라" 를 적는다 */
io_uring_sqe_set_data64(sqe, 42);                       /*    완료 때 그대로 돌려받을 꼬리표 */

io_uring_submit(&ring);                                 /* 4. 제출: io_uring_enter() */

io_uring_wait_cqe(&ring, &cqe);                         /* 5. 완료를 기다린다 */
printf("user_data = %llu, res = %d\n", cqe->user_data, cqe->res);
io_uring_cqe_seen(&ring, cqe);                          /* 6. CQE 를 소비했다고 표시 */

io_uring_queue_exit(&ring);

./uring_hello

io_uring_submit = 1  (제출된 SQE 수)
CQE: user_data = 42, res = 9
내용: lsp2-vm

res는 그 연산을 System Call로 했을 때의 return 값입니다. 여기서는 read()가 return했을 9(읽은 Byte 수)입니다.

❗ IMPORTANT
오류 처리 방식이 다릅니다. liburing의 함수들은 실패 시 -1을 return하고 errno를 설정하는 것이 아니라 -errno를 직접 return합니다. CQE의 res도 같습니다. res = -2면 ENOENT입니다. perror()가 아니라 strerror(-ret)를 씁니다. 여러 요청이 동시에 진행되므로 Thread당 하나뿐인 errno로는 어느 요청의 오류인지 알 수 없기 때문입니다.

27-7. 요청은 Kernel 안에서 어떻게 처리되는가

io_uring_enter로 들어간 Kernel은 SQE를 꺼내 다음 순서로 처리를 시도합니다.

1. Inline 시도: Block 되지 않는 Mode 로 바로 실행해 본다 (IOCB_NOWAIT)
      예: Page Cache Hit 인 read → 그 자리에서 복사하고 CQE 작성.  io_uring_enter 가 return 하기 전에 이미 완료

2. Block 될 상황이면 (-EAGAIN)
      a. Poll 가능한 대상 (Pipe, Socket): 내부적으로 Wait Queue 에 Callback 을 걸어 두고(L23 과 같은 방식),
         준비되면 그때 실행                                                   ← "FAST_POLL"
      b. Buffered File 읽기: Page 가 Disk 에서 올라오면 깨어나 이어서 실행
      c. O_DIRECT: Block Layer 에 비동기 요청으로 직접 제출. 완료 Interrupt 에서 CQE 작성
      d. 그 밖에 어쩔 수 없이 Block 되는 연산 (fsync, openat 등):
         Kernel 의 Worker Thread Pool (io-wq) 로 보낸다

d번이 L26의 Thread Pool과 다른 점은 Kernel 안의 Thread라는 것입니다. User ↔ Kernel 전환, User Space의 Queue와 Lock, futex가 없습니다. 그리고 1번에서 끝나는 요청은 Thread를 거치지 않습니다.

ps -eLo pid,tid,comm | grep -E "iou-wrk|iou-sqp" | head -n 3

   2811    2815 iou-wrk-2811

io-wq Worker는 요청한 Process의 Thread처럼 보입니다(iou-wrk-<pid>). 일이 없으면 사라지므로 위 명령은 io_uring 프로그램이 Block되는 I/O를 하는 동안에만 결과가 나옵니다.

정리

  • io_uring = Application과 Kernel이 mmap으로 공유하는 두 개의 Ring Buffer. SQ에 요청(SQE, 64Byte)을 적고 CQ에서 결과(CQE, 16Byte)를 읽습니다.
  • System Call은 셋: io_uring_setup(생성), io_uring_enter(제출과 대기), io_uring_register(사전 등록). SQE를 쓰고 CQE를 읽는 것은 Memory 접근입니다.
  • SQE는 "System Call의 인자를 Register 대신 공유 Memory에 적은 것". File을 읽어도 read System Call은 호출되지 않습니다.
  • 실전에서는 liburing을 씁니다. 오류는 errno가 아니라 -errno return 값과 CQE의 res 로 옵니다.
  • Kernel은 요청을 먼저 Inline으로 시도하고, Block될 상황이면 내부 Poll, 비동기 Block I/O, io-wq Worker 중 맞는 방법으로 처리합니다.
  • 환경에 따라 꺼져 있을 수 있습니다(io_uring_disabled, seccomp).

    ret = io_uring_submit(&ring);                       /* 4. 제출: io_uring_enter() System Call */
    printf("io_uring_submit = %d  (제출된 SQE 수)\n", ret);

    ret = io_uring_wait_cqe(&ring, &cqe);               /* 5. 완료를 기다린다 */
    if (ret < 0) {
        fprintf(stderr, "io_uring_wait_cqe: %s\n", strerror(-ret));
        return EXIT_FAILURE;
    }
    printf("CQE: user_data = %llu, res = %d\n", (unsigned long long)cqe->user_data, cqe->res);
    if (cqe->res < 0)                                   /*    res 는 read() 의 return 값. 실패면 -errno */
        fprintf(stderr, "read 실패: %s\n", strerror(-cqe->res));
    else
        printf("내용: %s", buf);
    io_uring_cqe_seen(&ring, cqe);                      /* 6. CQE 를 소비했다고 표시 (CQ head 전진) */

    io_uring_queue_exit(&ring);

① io_uring_queue_init 로 Ring 생성 ② io_uring_get_sqe 로 빈 SQE 를 얻고(System Call 아님) ③ io_uring_prep_read 로 요청 내용을 적은 뒤 ④ io_uring_submit(io_uring_enter System Call)으로 제출 ⑤ io_uring_wait_cqe 로 완료를 기다리고 ⑥ io_uring_cqe_seen 으로 CQE 를 소비했다고 표시합니다. 결과는 cqe->res(read 의 return 값, 실패면 -errno)입니다.

28-3. 왜 Lock이 필요 없는가

L16에서 Race Condition의 조건은 "여러 실행 흐름이 같은 변수를 쓴다"였습니다. 이 Ring에서는 각 변수를 쓰는 쪽이 하나뿐입니다.

SQ:   Application ── 쓴다 ──→ tail, SQE 내용          Kernel ── 쓴다 ──→ head
      Application ── 읽는다 ─→ head                   Kernel ── 읽는다 ─→ tail, SQE 내용

SPSC(Single Producer, Single Consumer) Queue입니다. L20의 Lock-Free Stack처럼 CAS 재시도도, ABA 문제도 없습니다. 필요한 것은 순서 하나뿐입니다.

sqes[idx] = ...;                                /* 1. 내용을 먼저 쓰고 */
atomic_store(sq_tail, tail + 1);                /* 2. 그 다음에 tail 을 공개한다 */

이 순서가 뒤집혀 보이면 Kernel은 아직 쓰이지 않은 쓰레기 SQE를 실행합니다. L18에서 배운 대로 Compiler와 CPU는 Memory 쓰기의 순서를 바꿀 수 있으므로, tail의 공개에는 Memory Barrier가 들어갑니다. liburing의 Source가 정확히 그렇게 되어 있습니다.

/* liburing: src/include/liburing.h, src/queue.c (발췌) */
#define io_uring_smp_store_release(p, v)  atomic_store_explicit((_Atomic typeof(*(p)) *)(p), (v), memory_order_release)
#define io_uring_smp_load_acquire(p)      atomic_load_explicit((_Atomic typeof(*(p)) *)(p), memory_order_acquire)

io_uring_smp_store_release(sq->ktail, tail);    /* tail 공개 */

📌 NOTE
하나의 Ring을 여러 Thread가 동시에 쓰면 Producer가 둘이 되어 이 전제가 깨집니다. liburing은 Thread-safe하지 않습니다. 일반적인 설계는 Thread마다 Ring을 하나씩 두는 것입니다.

Ring을 직접 다루는 코드가 "번거롭고 실수하기 쉽다"고 한 이유가 이것입니다. 순서와 Barrier를 하나라도 틀리면 드물게만 나타나는 Bug가 됩니다.

정리

  • Ring은 entries가 2의 거듭제곱인 배열 + 계속 증가하는 head와 tail. 위치는 index & mask, 개수는 tail - head.
  • SQ는 Application이 tail을, Kernel이 head를 전진시킵니다. CQ는 그 반대. 각 변수를 쓰는 쪽이 하나뿐인 SPSC Queue여서 Lock도 CAS도 필요 없고, "내용을 쓴 뒤 tail을 공개" 하는 순서와 Memory Barrier만 있으면 됩니다.
  • get_sqe는 local tail만 올리고, submit이 tail을 한 번에 공개합니다. 그래서 Batch가 됩니다.
  • SQE(64Byte)는 System Call의 인자를 적은 것. Offset은 항상 명시하고, 가리키는 Memory는 완료까지 유지합니다.
  • CQE(16Byte)는 user_data + res + flags. 요청과 완료를 잇는 것은 user_data뿐입니다.
  • 완료 순서는 제출 순서와 다릅니다. 오류는 CQE의 res로 옵니다. get_sqe의 NULL과 CQ Overflow에 대비합니다.

29-1. 기본 Loop의 모양

io_uring 프로그램은 거의 모두 다음 세 단계의 반복입니다.

while (할 일이 남았다) {
    ① 채우기   : SQ 에 자리가 있고 보낼 것이 있는 동안  get_sqe → prep → set_data
    ② 제출+대기 : io_uring_submit_and_wait(&ring, 1)          ← System Call 은 여기 한 번
    ③ 거두기   : 도착해 있는 CQE 를 전부  peek_cqe → res 확인 → cqe_seen
}
liburing 함수 System Call 용도
io_uring_submit io_uring_enter(to_submit=n, min_complete=0) 제출만 하고 바로 돌아온다
io_uring_submit_and_wait(ring, k) io_uring_enter(n, k, GETEVENTS) 제출 + k개 완료까지 대기. 한 번의 System Call
io_uring_wait_cqe CQ가 비어 있을 때만 io_uring_enter 하나를 기다린다
io_uring_peek_cqe 없음 CQ에 있으면 꺼내고 없으면 -EAGAIN
io_uring_cqe_seen 없음 CQ head 전진

29-2. uring_cat: File 전체 읽기

uring_cat.c는 File을 4KB Block으로 나눠 읽습니다. 요청마다 구조체를 하나 두고 그 포인터를 user_data에 넣습니다.

#define BLOCK 4096
#define QD    64                        /* Queue Depth: 동시에 걸어 둘 수 있는 요청 수 */

struct req { off_t off; size_t len; };

while (completed < nblocks) {
    /* ① SQ 에 자리가 있고 보낼 것이 남아 있는 동안 SQE 를 채운다 */
    while (submitted < nblocks && inflight < QD) {
        sqe = io_uring_get_sqe(&ring);
        if (sqe == NULL) break;
        ...
        io_uring_prep_read(sqe, fd, data + reqs[i].off, reqs[i].len, reqs[i].off);   /* 목적지 = 최종 위치 */
        io_uring_sqe_set_data(sqe, &reqs[i]);
        submitted++; inflight++;
    }
    /* ② 한 번의 System Call 로 전부 제출하고, 적어도 1 개가 끝날 때까지 기다린다 */
    io_uring_submit_and_wait(&ring, 1);

    /* ③ 도착해 있는 CQE 를 전부 거둔다 (System Call 없음) */
    while (io_uring_peek_cqe(&ring, &cqe) == 0) {
        struct req *r = io_uring_cqe_get_data(cqe);
        if (cqe->res < 0) { ... 오류 ... }
        if ((size_t)cqe->res != r->len) { ... Short Read ... }
        io_uring_cqe_seen(&ring, cqe);
        completed++; inflight--;
    }
}

설계 Point 세 가지입니다.

  • 완료 순서에 의존하지 않습니다. 각 요청이 data + off, 즉 최종 위치에 직접 읽으므로 어떤 순서로 끝나든 결과가 같습니다(L28).
  • inflight < QD: 진행 중인 요청 수를 제한합니다. SQ 크기뿐 아니라 CQ가 넘치지 않게 하는 장치입니다.
  • submit_and_wait(…, 1): 전부 끝날 때까지 기다리지 않고 하나라도 끝나면 돌아와 빈자리를 다시 채웁니다. Pipeline이 계속 차 있습니다.

System Call은 256분의 1로 줄었는데 시간은 23%만 줄었습니다. 이유를 나눠 봅니다.

64MB Memory 복사 같다 같다 ← 시간의 대부분

  • Batch 1은 pread보다 느립니다. System Call 횟수는 같은데 SQE/CQE를 다루는 비용이 더해졌습니다. "io_uring으로 바꾸면 빨라진다"가 아닙니다.
  • Batch 8 → 64 → 256에서 더 나아지지 않습니다. System Call 비용이 충분히 희석되고 나면 남는 것은 복사입니다.
  • 4KB 복사가 약 400ns, System Call 전환이 약 150ns인 상황입니다. 요청 하나의 실제 작업이 작을수록 Batch의 이득이 커지고(작은 Record, NOP에 가까운 연산), 클수록 작아집니다.

❗ IMPORTANT
io_uring의 이득은 두 종류이고 서로 다릅니다.

  1. System Call 절감 (Batch): 이번 실습에서 측정한 것. 작은 I/O를 아주 많이 할 때 의미가 있고, 그 크기는 "전환 비용 / 요청당 실제 작업"의 비율이 정합니다.
  2. 기다리지 않음 (Asynchrony): I/O가 실제로 Disk를 기다리는 동안 Thread가 다른 일을 하고, 수십~수백 개의 I/O가 동시에 진행된다. Cold Read, O_DIRECT, fsync가 많은 작업에서는 이쪽이 훨씬 큽니다(L30).

Page Cache Hit만 있는 순차 읽기는 두 이득이 모두 가장 작은 경우입니다. 이런 작업이라면 큰 Buffer의 read()(L11)나 mmap(L14)이 더 단순하고 빠릅니다.

29-7. Linked SQE: read → write → fsync

File 복사에서는 read가 끝난 뒤에 그 Buffer를 write해야 합니다. 그런데 io_uring은 제출된 요청들을 병렬로 실행합니다. 순서가 필요하면 IOSQE_IO_LINK로 연결합니다. uring_cp.c

sqe = io_uring_get_sqe(&ring);                      /* read: 끝나야 다음 SQE 가 시작된다 */
io_uring_prep_read(sqe, in, bufs[n], len, off);
sqe->flags |= IOSQE_IO_LINK;

sqe = io_uring_get_sqe(&ring);                      /* write: 위 read 가 성공한 뒤에 실행된다 */
io_uring_prep_write(sqe, out, bufs[n], len, off);
Link의 규칙
Flag가 붙은 SQE 다음 SQE가 연결된다 여러 개를 Chain으로 이을 수 있다
앞의 요청이 실패하면 뒤는 실행되지 않고 res = -ECANCELED Short Read도 실패로 취급. 계속 진행시키려면 IOSQE_IO_HARDLINK
서로 다른 Chain끼리는 병렬 이 예제에서는 (read→write) 8쌍이 동시에 진행
Chain은 한 번의 submit 안에서 끝나야 한다

마지막의 fsync도 SQE 하나입니다(L15).

io_uring_prep_fsync(sqe, out, 0);                   /* flags 에 IORING_FSYNC_DATASYNC 를 주면 fdatasync */

fsync는 수 ms~수십 ms 동안 Block되는 대표적인 System Call입니다. io_uring으로 제출하면 그동안 Thread가 다른 일을 할 수 있습니다. Database가 io_uring에 관심을 갖는 큰 이유입니다. write와 fsync를 Link하면 "쓰고 나서 sync"도 한 번의 제출로 끝납니다.

정리

  • 기본 Loop: 채우기 → submit_and_wait → 거두기. System Call은 가운데 한 번입니다.

  • io_uring의 이득은 System Call 절감과 기다리지 않음 두 가지이고, 큰 쪽은 대개 후자입니다.
  • IOSQE_IO_LINK 로 연산 순서를 보장합니다. 앞이 실패하면 뒤는 -ECANCELED.
  • fsync도 비동기 요청 하나입니다.

        /* 3. 도착해 있는 CQE 를 전부 거둔다 (System Call 없음) */
        while ((&ring, &cqe) == 0) {
            struct req *r = (cqe);

            if (cqe->res < 0) {
                fprintf(stderr, "read @%ld: %s\n", (long)r->off, strerror(-cqe->res));
                return EXIT_FAILURE;
            }
            if ((size_t)cqe->res != r->len)             /* Short Read: 실전에서는 남은 부분을 다시 제출한다 */

            io_uring_cqe_seen(&ring, cqe);
            completed++;
            inflight--;
        }

이번에는 Buffered(기본) Mode입니다.

Mode: Buffered

(이 출력은 CPU 1개, 매우 빠른 Disk 환경의 것입니다. 환경에 따라 놓친 Tick은 0~수 개로 달라집니다.)

loop_stall보다는 훨씬 낫지만 Tick을 몇 개 놓쳤습니다. 비동기인데 왜일까요. L14의 그림을 떠올리면 됩니다.

Buffered : Disk ──DMA──→ Page Cache ──CPU 복사──→ User Buffer
                          ↑ 이 대기는 비동기로 숨겨진다      ↑ 이 복사는 누군가의 CPU 시간이다
O_DIRECT : Disk ──DMA──→ User Buffer                        (CPU 가 할 일이 없다)
io_uring이 숨겨 주는 것 남는 것
Buffered Disk를 기다리는 시간 Page Cache → User Buffer 복사 256MB. Kernel은 이것을 요청한 Thread의 Context(System Call에 들어갈 때 처리되는 task_work)나 io-wq Worker에서 수행한다. CPU가 적으면 Event Loop와 경쟁한다
O_DIRECT Disk를 기다리는 시간 없음. Disk Controller가 User Buffer에 직접 쓴다

비동기 I/O가 없애 주는 것은 기다림이지 일이 아닙니다. 복사라는 CPU 작업은 어디선가 실행되어야 합니다.

📌 NOTE
L14에서 "O_DIRECT는 비동기 I/O와 함께 쓰는 것이 일반적"이라고 한 이유가 이것입니다. O_DIRECT + io_uring은 CPU 복사도, 대기도, Thread도 없는 조합이고, 자체 Cache를 가진 Database와 Storage Engine이 io_uring을 쓰는 방식입니다. 반대로 Page Cache의 혜택이 필요한 일반 프로그램은 Buffered + io_uring으로도 "Disk 대기를 숨기는" 이득은 얻습니다.

30-4. SQPOLL: System Call 0번

L29에서 Batch로 System Call을 줄였습니다. SQPOLL은 남은 io_uring_enter마저 없앱니다.

p.flags          = IORING_SETUP_SQPOLL;
p.sq_thread_idle = 2000;                    /* 2 초 동안 일이 없으면 Kernel Thread 가 잠든다 */
io_uring_queue_init_params(8, &ring, &p);

이 Flag로 Ring을 만들면 Kernel이 전용 Thread(iou-sqp-<pid>) 를 하나 만들어 SQ의 tail을 계속 들여다봅니다(Polling). Application은 SQE를 쓰고 tail만 올리면 되고, Kernel에 알릴 필요가 없습니다.

File을 20,000번 읽었는데 System Call은 1번입니다(처음에 잠들어 있던 Kernel Thread를 깨운 것). 제출도 완료 확인도 전부 공유 Memory의 읽기/쓰기였습니다.

SQPOLL의 대가
CPU Core 하나를 Polling에 쓴다 iou-sqp Thread가 sq_thread_idle 동안 Busy Loop. top에서 100%로 보인다. L21의 Busy Polling을 Kernel이 대신 하는 것
Idle 후에는 다시 System Call 필요 Thread가 잠들면 SQ의 IORING_SQ_NEED_WAKEUP Flag가 켜지고, 그때는 io_uring_enter(IORING_ENTER_SQ_WAKEUP)이 필요. liburing이 자동 처리
완료를 기다리려면 여전히 System Call 이 예제는 CQ를 Busy Poll해서 피했다. Application 쪽도 CPU를 태운다
권한 Kernel 5.11 미만은 root(CAP_SYS_NICE) 필요

Latency를 위해 CPU를 지불하는 선택입니다. 초당 수십만 건 이상의 I/O를 꾸준히 처리하고 Core에 여유가 있는 Storage Server, Database에 맞습니다. I/O가 뜸한 프로그램에는 낭비입니다. L20의 Spin vs Sleep과 같은 거래입니다.

정리

  • io_uring_register_eventfd 로 완료 통지를 fd로 만들면 Chapter 5의 epoll Event Loop에 그대로 들어갑니다. 256MB를 읽는 동안 Loop가 멈추지 않습니다.
  • 비동기 I/O가 없애는 것은 기다림이지 일이 아닙니다. Buffered I/O의 복사는 여전히 CPU 시간을 씁니다. O_DIRECT + io_uring이 복사도 대기도 없는 조합입니다.
  • SQPOLL: Kernel Thread가 SQ를 Polling합니다. System Call이 0이 되는 대신 Core 하나를 씁니다.
  • Registered Buffer / File: 요청마다 반복되는 Page 고정과 fd 조회를 한 번으로.
  • POLL_ADD, Multishot, TIMEOUT 등으로 io_uring만으로도 Event Loop를 구성할 수 있습니다.
  • I/O 모델은 빠르기의 순서가 아니라 풀려는 문제로 고릅니다. io_uring은 가장 강력하지만 가장 복잡하고, 쓸 수 없는 환경이 많습니다.

✏️ 괄호 넣기 30-2

  1. Kernel Thread 가 SQ 를 Polling 해 제출에 System Call 이 필요 없게 하는 Setup Flag 는 이다.
  2. Buffer 를 미리 Kernel 에 등록해 요청마다 Page 를 고정하는 비용을 없애는 함수는 이다.
  3. io_uring 의 완료를 epoll Event Loop 에 알리려면 Ring 에 를 등록한다.
  4. Docker 기본 seccomp Profile 처럼 io_uring 을 차단하는 환경이 있는 이유는 SQE 로 수행하는 연산이 이다.
