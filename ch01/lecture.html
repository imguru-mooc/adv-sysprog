Lecture 01

User Space에서 Kernel Space까지

영상 16분

printf("hello") 한 줄이 화면에 나오기까지, 프로그램은 몇 번이나 Kernel의 문을 두드릴까요?

학습 목표

1-1. 복습: Library 함수와 System Call

기존 과정에서 이렇게 배웠습니다.

Library 함수 System Call
예 printf, fopen, strlen, malloc write, open, read, fork
실행되는 곳 User Space (내 Process 안) Kernel
Manual man 3 printf man 2 write

이번 Lecture에서 새로 묻는 것은 두 가지입니다.

  1. 프로그램은 왜 Kernel의 함수를 직접 호출하지 못하고 System Call이라는 특별한 절차를 거쳐야 할까?
  2. write()도 C 함수처럼 생겼는데, 정말 Kernel 함수일까?

1-2. 같은 출력, 세 가지 방법

세 프로그램은 모두 hello, kernel을 출력합니다. Source를 먼저 열어 차이를 봅니다.

  • hello1_printf.c: printf() 사용
  • hello2_write.c: write() 사용
  • hello3_syscall.c: syscall(SYS_write, ...) 사용
./hello1_printf
./hello2_write
./hello3_syscall

hello, kernel
hello, kernel
hello, kernel
SYS_write = 1

세 번째 프로그램이 핵심입니다. Kernel은 write라는 이름을 모릅니다. 1번이라는 번호만 압니다. 우리가 부르던 write()는 Kernel 함수가 아니라, 번호 1과 인자를 준비해서 Kernel에 진입해 주는 glibc의 작은 함수(Wrapper)였습니다.

printf()          Library 함수. 문자열을 만들고 Buffer에 모은 뒤 write()를 부른다
   ↓
write()           glibc Wrapper. "1번, 인자 3개"를 준비해서 Kernel에 진입한다
   ↓
── System Call 경계 ──
   ↓
Kernel의 write 처리 함수

📌 NOTE
내가 작성한 System Call은 write 하나뿐인데 30줄 가까이 나옵니다. main()이 시작되기 전에 프로그램을 Memory에 올리고 Library를 연결하는 과정입니다. 이 부분은 L04, L05에서 한 줄씩 해석합니다. 지금은 맨 아래 write 줄만 봅니다.

세 프로그램을 요약(-c)으로 비교합니다.

strace -c ./hello1_printf 2>&1 | tail -n 4
strace -c ./hello2_write  2>&1 | tail -n 4

------ ----------- ----------- --------- --------- ----------------
100.00    0.000000           0        32         1 total
------ ----------- ----------- --------- --------- ----------------
100.00    0.000000           0        29         1 total

printf 쪽이 몇 개 더 많습니다. 무엇이 더 호출되었는지 확인합니다.

strace ./hello1_printf 2>&1 | tail -n 6

fstat(1, {st_mode=S_IFCHR|0620, st_rdev=makedev(0x88, 0), ...}) = 0
getrandom("\x..", 8, GRND_NONBLOCK)     = 8
brk(NULL)                               = 0x5581e9f3c000
brk(0x5581e9f5d000)                     = 0x5581e9f5d000
write(1, "hello, kernel\n", 14)         = 14
exit_group(0)                           = ?
  • fstat(1, ...): printf가 출력 대상이 Terminal인지 File인지 확인합니다. Terminal이면 줄 단위, File이면 Buffer가 찰 때까지 모읍니다(기존 과정의 library buffer).
  • brk: 그 Buffer를 위한 Memory를 확보합니다.
  • 결국 마지막에는 같은 write(1, ..., 14) 가 호출됩니다.

❗ IMPORTANT
정확한 개수(29, 32)는 glibc Version에 따라 다릅니다. 중요한 것은 개수가 아니라 printf도 결국 write System Call로 끝난다는 사실입니다.

이번에는 ltrace로 Library 호출을 봅니다.

ltrace ./hello1_printf

puts("hello, kernel")                   = 14
hello, kernel
+++ exited (status 0) +++

printf를 썼는데 puts가 보입니다. 형식 지정자가 없고 \n으로 끝나는 문자열이면 gcc가 더 가벼운 puts로 바꿔 Compile하기 때문입니다. strace는 Kernel과의 경계를, ltrace는 Library와의 경계를 보여 줍니다.

1-4. Kernel에 한 번도 가지 않는 함수

libonly.c는 strlen, strchr, abs를 100만 번씩 호출합니다.

strace -c ./libonly 2>&1 | tail -n 3
strace -c ./hello2_write 2>&1 | tail -n 3

100.00    0.000000           0        28         1 total
100.00    0.000000           0        29         1 total

함수를 300만 번 호출했는데 System Call 수는 hello2_write보다 오히려 하나 적습니다. strlen은 내 Process의 Memory를 읽기만 하면 됩니다. Kernel에 부탁할 일이 없습니다.

그러면 어떤 일에 Kernel이 필요할까요? 기준은 하나입니다: 내 Process 바깥의 자원을 건드리는가.

하려는 일 Kernel 필요 이유
문자열 길이 계산, 정렬, 수학 계산 아니오 내 Memory 안에서 끝남
화면 출력, File 읽기/쓰기 예 장치는 모든 Process가 공유
Memory 더 받기 (brk, mmap) 예 Physical Memory는 공유 자원
Process 만들기, Signal 보내기 예 다른 Process에 영향
현재 시각 읽기 (L02에서 반전이 있습니다)

1-5. Ring 3에서 특권 명령 실행해 보기

"부탁하지 말고 직접 하면 안 되나?"를 실험합니다. priv.c는 CPU를 멈추는 hlt 명령을 직접 실행합니다.

./priv

Ring 3 에서 hlt 명령을 실행합니다...
Segmentation fault (core dumped)

Kernel Log를 확인합니다.

sudo dmesg | tail -n 3

traps: priv[2417] general protection fault ip:55e1a0c4b16d sp:7ffc3b6f2a10 error:0 in priv[55e1a0c4b000+1000]

일어난 일을 순서대로 보면 다음과 같습니다.

  1. CPU는 지금 실행 중인 코드의 Privilege Level을 알고 있습니다. 우리 프로그램은 Ring 3(User Mode) 입니다.
  2. hlt는 Ring 0(Kernel Mode) 에서만 허용된 명령입니다.
  3. CPU가 실행을 거부하고 General Protection Fault라는 Exception을 일으킵니다.
  4. 제어가 Kernel로 넘어가고, Kernel은 해당 Process에 SIGSEGV를 보냅니다.
Ring 3 (User Mode) Ring 0 (Kernel Mode)
실행되는 코드 Application, glibc Linux Kernel
특권 명령 (hlt, cli, I/O Port) 불가 → Exception 가능
Memory 자기 Process의 User 영역만 전체
장치 접근 불가 가능

📌 NOTE
이 보호는 Kernel이 Software로 검사하는 것이 아니라 CPU Hardware가 강제합니다. 그래서 버그가 있는 프로그램이나 악의적인 프로그램도 System 전체를 망가뜨릴 수 없습니다.

Ring 3에서 Ring 0로 넘어가는 길은 세 가지뿐이고, 모두 Kernel이 미리 정해 둔 입구로만 들어갑니다.

경로 누가 일으키는가 예
System Call 프로그램이 의도적으로 write, open
Exception 명령 실행 중 CPU가 방금 본 General Protection Fault, Page Fault(Chapter 2)
Interrupt 외부 장치가 Timer, Keyboard, Disk 완료

1-7. errno는 어디에서 오는가

errno_demo.c는 열려 있지 않은 fd 99에 write합니다.

./errno_demo
strace -e trace=write ./errno_demo

return = -1
errno  = 9 (Bad file descriptor)

write(99, "x", 1)                       = -1 EBADF (Bad file descriptor)
write(1, "return = -1\n", 12)           = 12
...

Kernel에는 errno라는 변수가 없습니다. 실제 흐름은 이렇습니다.

Kernel      오류 발생 → 결과값으로 -9 (-EBADF) 를 돌려준다
   ↓
glibc       결과가 음수(-4095 ~ -1)이면  errno = 9 로 저장하고  -1 을 return 한다
   ↓
Application return 값 -1 을 보고 errno 를 확인한다

errno는 glibc가 만들어 주는 User Space 변수입니다(Thread마다 따로 있습니다. 기존 과정의 TLS). Kernel이 직접 돌려주는 -9는 L02에서 Wrapper 없이 System Call을 호출해 직접 확인합니다.

정리

  • CPU는 Ring 3과 Ring 0를 Hardware로 구분합니다. Application은 Ring 3에서 실행되며 특권 명령과 장치 접근이 막혀 있습니다.
  • 내 Process 바깥의 자원이 필요하면 System Call로 Kernel에 요청합니다. strlen 같은 함수는 Kernel에 가지 않습니다.
  • write()는 Kernel 함수가 아니라 glibc Wrapper입니다. Kernel은 이름이 아니라 번호로 요청을 구분합니다.
  • printf도 결국 write System Call로 끝납니다. strace는 Kernel 경계를, ltrace는 Library 경계를 보여 줍니다.
  • errno는 Kernel의 음수 결과값을 glibc가 바꿔 저장한 것입니다.

#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>

{

Application 은 Ring 3(User Mode), Kernel 은 Ring 0 에서 실행됩니다. 특권 명령은 CPU Hardware 가 거부하고(General Protection Fault), Kernel 이 SIGSEGV 로 Process 를 종료합니다. strace 는 System Call 경계를, ltrace 는 Library 호출 경계를 보여 줍니다. strlen 은 내 Process 의 Memory 만 읽으므로 Kernel 에 갈 일이 없습니다(🎬 C1-1 strlen 시나리오).

다음 — write() Wrapper가 "번호와 인자를 준비해서 Kernel에 진입한다"고 했습니다. 구체적으로 어떤 Register에 무엇을 넣고, 어떤 CPU 명령을 실행하며, Kernel의 어디로 들어갈까요? L02. System Call Entry는 어떻게 동작하는가에서 Wrapper 없이 직접 해 봅니다.

glibc의 write() Wrapper가 하는 일을 직접 손으로 해 봅니다. Register에 값을 넣고, CPU 명령 하나를 실행하면 Kernel에 들어갑니다.

2-2. Register 규약

Kernel에 진입할 때는 함수 호출처럼 Stack에 인자를 쌓지 않습니다. 정해진 Register에 값을 넣습니다.

Register 역할 write(1, msg, 14)의 경우
rax System Call 번호 1
rdi 인자 1 1 (fd)
rsi 인자 2 msg의 주소
rdx 인자 3 14
r10 인자 4
r8 인자 5
r9 인자 6
rax (복귀 후) 결과값. 오류이면 -errno 14
rcx, r11 CPU가 덮어씀 (복귀 주소, RFLAGS 보관용)

💡 TIP
일반 함수 호출 규약은 rdi, rsi, rdx, rcx, r8, r9 순서입니다. System Call은 네 번째만 rcx 대신 r10 입니다. syscall 명령이 rcx를 복귀 주소 저장에 써 버리기 때문입니다.

2-3. Wrapper 없이 syscall 명령 직접 실행

raw_syscall.c의 핵심 부분입니다.

static long raw_syscall3(long nr, long a1, long a2, long a3)
{
    long ret;

    __asm__ volatile("syscall"
                     : "=a"(ret)                                /* 결과는 rax 에서 */
                     : "0"(nr), "D"(a1), "S"(a2), "d"(a3)       /* rax, rdi, rsi, rdx */
                     : "rcx", "r11", "memory");                 /* CPU 가 덮어쓰는 것 */
    return ret;
}

"D"는 rdi, "S"는 rsi, "d"는 rdx, "0"은 첫 번째 출력과 같은 Register(rax)를 뜻합니다. 실행되는 CPU 명령은 syscall 하나입니다.

./raw_syscall

hello from raw syscall
write  -> 23
write(99) -> -9   (errno가 아니라 -EBADF 가 그대로 돌아온다)
getpid -> 2467

둘째 줄이 1-7의 답입니다. Kernel은 -1과 errno가 아니라 -9를 직접 돌려줍니다. -1과 errno = 9로 바꾸는 것은 glibc Wrapper의 일입니다.

strace로 보면 glibc를 쓴 프로그램과 구별되지 않습니다.

strace -e trace=write,getpid ./raw_syscall

write(1, "hello from raw syscall\n", 23) = 23
...
write(99, "h", 1)                       = -1 EBADF (Bad file descriptor)
...
getpid()                                = 2471

Kernel 입장에서는 누가 Register를 채웠는지 알 수 없고 알 필요도 없습니다. syscall 명령이 실행되는 순간의 Register 값이 전부입니다.

syscall 명령 하나가 하는 일을 정리하면 다음과 같습니다. 모두 CPU Hardware가 한 번에 수행합니다.

동작 내용

2-7. vDSO: Kernel에 가지 않는 System Call

clock_gettime은 man 2에 있는 System Call입니다. strace로 확인합니다.

strace -e trace=clock_gettime ./vdso_time

clock_gettime(CLOCK_MONOTONIC, {tv_sec=5013, tv_nsec=262408102}) = 0
clock_gettime(CLOCK_MONOTONIC, {tv_sec=5013, tv_nsec=262471239}) = 0
... (100만 줄이 계속됩니다. Ctrl+C 로 중단)

vdso_time.c는 clock_gettime()을 100만 번, syscall(SYS_clock_gettime, ...)을 100만 번 호출합니다. strace에 보이는 것은 뒤의 100만 번뿐입니다. 앞의 100만 번은 System Call인데도 보이지 않습니다. 개수로 확인합니다.

strace -c -e trace=clock_gettime ./vdso_time 2>&1 | grep clock_gettime

100.00    0.412345           0   1000000           clock_gettime

200만이 아니라 100만입니다. 비밀은 Process의 Memory Map에 있습니다.

grep -E "vdso|vvar" /proc/self/maps

7ffe1a3f2000-7ffe1a3f6000 r--p 00000000 00:00 0                          [vvar]
7ffe1a3f6000-7ffe1a3f8000 r-xp 00000000 00:00 0                          [vdso]
영역 내용
[vdso] Kernel이 모든 Process에 자동으로 Mapping해 주는 작은 Shared Library. 실행 가능(r-x)
[vvar] Kernel이 계속 갱신하는 시간 Data. 읽기 전용(r--)

glibc의 clock_gettime()은 syscall 명령을 실행하지 않고 [vdso] 안의 함수를 일반 함수처럼 호출합니다. 그 함수는 [vvar]의 값을 읽어 계산만 합니다. Ring 3을 벗어나지 않으므로 strace에 잡히지 않습니다.

📌 NOTE
1-4 표의 "현재 시각 읽기"의 반전이 이것입니다. 시각은 공유 자원이지만 읽기만 하면 되고 매우 자주 호출되므로, Kernel이 읽기 전용 Page로 미리 내어 주는 방식을 택했습니다. gettimeofday, time, getcpu도 같은 방식입니다.

2-8. System Call 한 번의 비용

./vdso_time

vDSO    :     28.7 ns/call
syscall :    166.4 ns/call
ratio   :      5.8 x

❗ IMPORTANT
숫자는 CPU와 VM 설정에 따라 크게 다릅니다. VirtualBox에서는 syscall 쪽이 300~1000ns까지 나올 수 있습니다. 비율이 몇 배인가만 보세요.

같은 일을 하는데 Kernel에 진입하는 쪽이 몇 배 느립니다. 이 차이가 System Call 한 번의 고정 비용입니다: Mode 전환, Stack 전환, Register 저장과 복원, 보안 완화 처리(Spectre/Meltdown 대응), CPU Cache와 TLB에 미치는 영향.

이 비용이 이후 Chapter들의 동기가 됩니다.

나중에 배울 것 System Call 비용과의 관계
stdio Buffer (기존 과정), Page Cache (Ch3) 작은 I/O를 모아서 진입 횟수를 줄인다
futex (Ch4) 경쟁이 없으면 Kernel에 가지 않고 Lock을 잡는다
epoll (Ch5) 한 번의 진입으로 여러 FD의 Event를 받는다
io_uring (Ch6) 여러 I/O 요청을 한 번의 진입으로, 또는 진입 없이 전달한다

정리

  • System Call은 rax에 번호, rdi, rsi, rdx, r10, r8, r9에 인자를 넣고 syscall 명령을 실행하는 것입니다.
  • syscall 명령은 Hardware가 rcx, r11에 복귀 정보를 저장하고 MSR_LSTAR에 등록된 단 하나의 입구(entry_SYSCALL_64)로 점프하며 Ring 0로 전환합니다.
  • Kernel은 Register를 pt_regs로 저장하고 번호로 분기해 __x64_sys_write 같은 함수를 호출한 뒤, 결과를 rax에 담아 sysretq로 복귀합니다.
  • 오류는 -errno로 돌아옵니다. -1과 errno는 glibc가 만듭니다.
  • vDSO는 Kernel이 Process에 Mapping해 주는 코드로, clock_gettime 등을 Kernel 진입 없이 처리합니다.
  • System Call에는 고정 비용이 있고, 이것을 줄이는 것이 이후 여러 기술의 공통 동기입니다.

  2. System Call 의 네 번째 인자는 rcx 가 아니라 에 넣는다.
  3. syscall 명령은 Booting 때 Kernel 이 에 등록해 둔 단 하나의 입구 주소로 점프한다.
  4. clock_gettime() 이 strace 에 보이지 않는 것은 Kernel 이 Mapping 해 준 안의 함수를 일반 함수처럼 호출하기 때문이다.
🔒 정답 보기 2-2
  1. rax
  2. r10
  3. MSR_LSTAR
  4. vDSO

번호는 rax, 인자는 rdi·rsi·rdx·r10·r8·r9 입니다. 네 번째가 r10 인 이유는 syscall 명령이 rcx 를 복귀 주소 저장에 쓰기 때문입니다. 입구 주소는 MSR_LSTAR 에 있고 Ring 0 에서만 쓸 수 있어 아무 주소로나 들어갈 수 없습니다. vDSO 는 Kernel 이 모든 Process 에 넣어 주는 작은 Shared Library 로, 시각처럼 읽기만 하는 정보를 Kernel 진입 없이 제공합니다(🎬 C1-2).

셋째, 코드는 쓰기 금지, Data는 실행 금지입니다. 쓰기와 실행이 동시에 가능한 영역이 없으면 공격자가 Data에 코드를 써 넣고 실행하기 어려워집니다(W^X). GNU_STACK의 RW(E 없음)도 같은 목적입니다.

정리

  • ELF File에는 목차가 두 개 있습니다. Section Header는 Linker와 Debugger를 위한 것이고, Program Header는 Kernel과 Loader를 위한 것입니다.
  • 변수는 종류에 따라 .text, .rodata, .data, .bss로 나뉩니다. 지역 변수는 ELF에 없습니다.
  • .bss는 File에 크기만 기록됩니다(NOBITS). Segment의 MemSiz > FileSiz로 표현됩니다.
  • LOAD Segment 한 줄은 "File의 어디를, Memory의 어디에, 어떤 권한으로 올려라"는 지시입니다. Section은 권한이 같은 것끼리 Segment로 묶입니다.
  • Entry Point는 실행이 시작되는 주소이며 main이 아닙니다.
  • PIE는 DYN Type에 상대 주소, non-PIE는 EXEC에 고정 주소, Static은 INTERP가 없습니다.

int         g_init   = 42;        /* .data   */
int         g_uninit;             /* .bss    */
const int   g_const  = 7;         /* .rodata */
static char big[1 << 20];         /* .bss    File 에는 크기만 기록 (NOBITS) */

static int func(void)             /* .text   */
{
    return g_init + g_uninit + g_const + big[0];
}

int main(void)
{
    return func() == 49 ? 0 : 1;
}

초기값이 있는 전역은 .data, 0 이거나 초기값이 없으면 .bss, const 전역은 .rodata, 함수의 기계어는 .text 입니다. 1MB 배열이 .bss 에 있으므로 실행 File 크기는 거의 늘지 않습니다(size fill_3_1 의 bss 열 확인).

✏️ 괄호 넣기 3-2

  1. ELF 실행 File 의 처음 4 Byte 는 0x7f 와 문자 이다.
  2. Kernel 과 Dynamic Loader 가 읽는 목차는 Table 이다.
  3. .bss 의 Section Type 은 File 에 내용이 없다는 뜻의 이다.
  4. PIE 실행 File 의 ELF Type 은 , -no-pie 로 만든 실행 File 은 EXEC 이다.
🔒 정답 보기 3-2
  1. ELF
  2. Program Header
  3. NOBITS
  4. DYN

Magic Number 7f 45 4c 46 은 0x7f E L F 입니다. Section Header 는 Linker·Debugger 용, Program Header(Segment)는 Kernel·Loader 용입니다. .bss 는 NOBITS 라서 Segment 의 MemSiz 가 FileSiz 보다 큽니다. PIE 는 DYN(상대 주소), non-PIE 는 EXEC(고정 주소)입니다(🎬 C1-3).

4-1. Shared Library 직접 만들기

greet.c는 greet()와 greet_count() 두 함수를 제공합니다. Makefile의 Build 명령을 봅니다.

gcc -Wall -Wextra -Wpedantic -O0 -g -fPIC -shared -o libgreet.so greet.c
Option 의미
-fPIC Position Independent Code. 어느 주소에 올라가도 동작하는 코드를 생성
-shared 실행 File이 아니라 Shared Object를 생성

Shared Library는 여러 Process가 각자 다른 주소에 Mapping해서 씁니다. 그래서 절대 주소를 쓰는 코드는 안 되고 -fPIC가 필요합니다.

file libgreet.so
readelf -h libgreet.so | grep Type
nm -D libgreet.so | grep -E " T | U "

libgreet.so: ELF 64-bit LSB shared object, x86-64, ...
  Type:                              DYN (Shared object file)
                 U printf@GLIBC_2.2.5
0000000000001119 T greet
000000000000115c T greet_count
  • Type이 PIE 실행 File과 같은 DYN입니다. 구조적으로 PIE 실행 File은 "Entry Point가 있는 Shared Object"입니다.
  • T는 이 Library가 제공하는 함수, U는 다른 곳에서 가져와야 하는(Undefined) 함수입니다.

4-4. 호출 주소는 언제 정해지는가: PLT와 GOT

main을 Compile하는 시점에는 greet가 Memory의 어느 주소에 올라갈지 알 수 없습니다(Library는 실행할 때마다 다른 주소에 Mapping됩니다). 그런데 기계어 call 명령에는 주소가 필요합니다.

해결책은 간접 호출입니다. 관찰하기 쉽도록 주소가 고정된 main_lazy(-no-pie -z lazy)를 사용합니다.

objdump -d main_lazy --no-show-raw-insn | grep -A1 "call.*greet@plt"

  401183:       call   401080 <greet@plt>
  401188:       mov    $0x40200f,%edi
  40118d:       call   401080 <greet@plt>

main은 greet가 아니라 greet@plt 라는 곳을 호출합니다. 거기에 무엇이 있는지 봅니다.

objdump -d -j .plt.sec main_lazy | grep -A3 "<greet@plt>:"

0000000000401080 <greet@plt>:
  401080:       f3 0f 1e fa             endbr64
  401084:       ff 25 b6 22 00 00       jmp    *0x22b6(%rip)        # 403340 <greet@Base>

jmp *0x403340: 0x403340 번지에 적혀 있는 주소로 점프하라는 뜻입니다. 이 번지가 어디인지 확인합니다.

readelf -rW main_lazy | grep JUMP_SLOT

0000000000403330  0000000200000007 R_X86_64_JUMP_SLOT     0000000000000000 greet_count + 0
0000000000403338  0000000300000007 R_X86_64_JUMP_SLOT     0000000000000000 printf@GLIBC_2.2.5 + 0
0000000000403340  0000000400000007 R_X86_64_JUMP_SLOT     0000000000000000 greet + 0
이름 위치 역할
PLT (Procedure Linkage Table) 코드 영역(R E) 함수마다 하나씩 있는 작은 점프 코드. "GOT에 적힌 주소로 가라"
GOT (Global Offset Table) Data 영역(RW) 함수마다 8 Byte. 실제 주소가 적히는 칸

코드는 읽기 전용이라 고칠 수 없으므로, 고칠 수 있는 Data 영역에 주소 칸을 두고 코드는 그 칸을 거쳐 가도록 만든 것입니다. 남은 질문은 그 칸에 주소를 누가 언제 적느냐입니다.

  • Lazy Binding: 함수가 처음 호출될 때 Loader가 찾아서 적습니다. 호출되지 않는 함수는 찾지 않으므로 시작이 빠릅니다.
  • BIND_NOW: 프로그램 시작 시점에 모든 칸을 채웁니다.

LD_DEBUG=bindings로 Lazy Binding을 확인합니다.

LD_DEBUG=bindings ./main_lazy 2>&1 >/dev/tty | grep "main_lazy.*greet"

      2611:     binding file ./main_lazy [0] to .../lab/libgreet.so [0]: normal symbol `greet'
[libgreet] hello, first call (1)
[libgreet] hello, second call (2)
      2611:     binding file ./main_lazy [0] to .../lab/libgreet.so [0]: normal symbol `greet_count'

2>&1 >/dev/tty는 Loader의 Debug 출력(stderr)만 grep으로 보내고 프로그램의 출력(stdout)은 Terminal에 바로 찍히게 해서 시간 순서가 섞이지 않게 합니다.

greet의 Binding은 첫 번째 hello 직전에 한 번만 일어나고, 두 번째 호출 때는 일어나지 않습니다. greet_count는 그것이 호출되는 시점(두 번의 hello 뒤)에 Binding됩니다.

4-5. gdb로 GOT가 바뀌는 순간 보기

4-4에서 확인한 greet의 GOT 칸은 0x403340이었습니다. 자신의 출력에 나온 주소를 사용하세요.

gdb -q ./main_lazy

(gdb) break main
(gdb) run
(gdb) x/gx 0x403340

0x403340 <greet@got.plt>:       0x0000000000401050

아직 greet의 실제 주소가 아닙니다. 0x401050은 실행 File 자신의 .plt 안, 즉 "Loader에게 찾아 달라고 요청하는 코드" 의 주소입니다.

(gdb) next
(gdb) x/gx 0x403340

[libgreet] hello, first call (1)
0x403340 <greet@got.plt>:       0x00007ffff7fb9119

첫 번째 호출이 끝나자 값이 0x7ffff7fb9119로 바뀌었습니다. 이 주소가 어디인지 확인합니다.

(gdb) info symbol 0x00007ffff7fb9119
(gdb) next
(gdb) x/gx 0x403340
(gdb) quit

greet in section .text of .../lab/libgreet.so
[libgreet] hello, second call (2)
0x403340 <greet@got.plt>:       0x00007ffff7fb9119

두 번째 호출 뒤에는 값이 그대로입니다. 끝자리 119는 4-1의 nm -D에서 본 greet의 Offset 0x1119와 같습니다.

첫 번째 호출   main → greet@plt → GOT(0x401050) → .plt 의 Resolver 호출 코드 → _dl_runtime_resolve
                                                     → greet 를 찾아 GOT 에 기록 → greet 실행
두 번째 호출   main → greet@plt → GOT(0x7ffff7fb9119) → greet 실행

4-7. BIND_NOW와 RELRO: 최신 Ubuntu의 기본값

4-5를 기본 Option으로 Build한 main_rpath로 해 보면 재현되지 않습니다. 확인합니다.

readelf -d main_rpath | grep -E "BIND_NOW|FLAGS"
readelf -d main_lazy  | grep -E "BIND_NOW|FLAGS"

 0x000000000000001e (FLAGS)              BIND_NOW
 0x000000006ffffffb (FLAGS_1)            Flags: NOW PIE

main_lazy는 아무것도 출력되지 않습니다. 최신 Ubuntu의 gcc는 기본으로 -z now와 -z relro 를 적용합니다(Full RELRO).

이유는 보안입니다. GOT는 "쓰기 가능한 Memory에 있는 함수 포인터 표"입니다. 프로그램에 Buffer Overflow 같은 취약점이 있으면 공격자가 GOT 칸을 덮어써서 printf 호출을 자신의 코드로 돌릴 수 있습니다.

Lazy Binding (-z lazy) Full RELRO (-z now -z relro, Ubuntu 기본)
GOT 채우는 시점 함수별 첫 호출 시 프로그램 시작 시 전부
시작 속도 빠름 조금 느림 (Symbol이 수천 개인 큰 프로그램에서 체감)
실행 중 GOT 쓰기 가능 Loader가 다 채운 뒤 mprotect로 읽기 전용
보안 GOT Overwrite 공격 가능 차단

L03에서 본 GNU_RELRO Segment가 "준비가 끝나면 읽기 전용으로 바꿀 범위"였습니다.

❗ IMPORTANT
ltrace가 동작하지 않는 이유도 이것입니다. ltrace는 PLT를 거치는 Lazy 호출에 끼어드는 방식인데, BIND_NOW로 Build된 실행 File에서는 끼어들 지점을 찾지 못해 출력이 비어 있습니다. 이 과정의 Makefile이 ltrace 실습 대상에 -Wl,-z,lazy를 붙이는 이유입니다.

4-8. LD_PRELOAD로 함수 가로채기

Loader는 Symbol을 찾을 때 Load된 순서대로 검색하고 처음 찾은 것을 씁니다. LD_PRELOAD에 지정한 Library는 다른 모든 Library보다 먼저 Load됩니다. 즉 같은 이름의 함수를 만들어 두면 그것이 선택됩니다.

dice.c는 주사위를 5번 굴립니다.

./dice
./dice

rolling...
2 3 4 1 4
rolling...
5 1 1 6 2

hook.c에는 rand()와 puts()가 정의되어 있습니다. dice를 다시 Build하지 않고 동작을 바꿉니다.

LD_PRELOAD=./libhook.so ./dice

[hook] puts("rolling...")
rolling...
6 6 6 6 6
  • rand(): 완전히 바꿔치기했습니다. 항상 5를 return하므로 5 % 6 + 1 = 6.
  • puts(): 감싸기입니다. Log를 찍은 뒤 dlsym(RTLD_NEXT, "puts")로 찾은 진짜 puts 를 호출합니다. RTLD_NEXT는 "검색 순서에서 나 다음에 있는 것"을 뜻합니다.

📌 NOTE
dice.c에는 puts를 쓴 적이 있지만, printf("...\n")만 쓴 프로그램에서도 puts가 가로채질 수 있습니다. L01에서 본 것처럼 gcc가 printf를 puts로 바꾸기 때문입니다.

실제 활용 예
Memory Debugging malloc/free를 가로채 누수 추적 (jemalloc, tcmalloc 교체도 같은 원리)
Test time(), rand()를 고정해 재현 가능한 Test
분석 특정 함수 호출에 Log 추가

⚠ WARNING
LD_PRELOAD는 Dynamic Link된 Library 함수 호출만 가로챕니다. Static 실행 File, syscall 명령을 직접 실행하는 코드(L02의 raw_syscall)에는 효과가 없습니다. 또한 보안상 setuid 프로그램에서는 무시됩니다.

4-9. dlopen: 실행 중에 Load하기

지금까지는 Loader가 시작할 때 NEEDED 목록을 보고 Load했습니다. 프로그램이 실행 중에 직접 요청할 수도 있습니다. plugin_main.c의 핵심입니다.

handle = dlopen("./libgreet.so", RTLD_NOW);
*(void **)(&fn) = dlsym(handle, "greet");
fn("dlopen");
dlclose(handle);

./plugin_main
ldd plugin_main | grep greet

[libgreet] hello, dlopen (1)

ldd에는 libgreet.so가 나오지 않습니다(NEEDED에 없음). 실행 중에 Load되기 때문입니다. Plugin 구조, Python의 C 확장 Module, Web Server의 Module이 모두 이 방식입니다.

💡 TIP
*(void **)(&fn) = dlsym(...)이라는 낯선 형태는 -Wpedantic 때문입니다. C 표준은 void *를 함수 포인터로 직접 변환하는 것을 허용하지 않아 경고가 나오므로, POSIX가 권장하는 이 방식으로 우회합니다.

정리

  • 실행 File에는 필요한 Library의 이름만 기록됩니다(NEEDED). 실행 시 Dynamic Loader(ld-linux-x86-64.so.2)가 LD_LIBRARY_PATH → RUNPATH → ld.so.cache → 기본 경로 순으로 찾아 Mapping합니다.
  • Library 함수 호출은 PLT(코드의 작은 점프) → GOT(Data의 주소 칸)를 거치는 간접 호출입니다.
  • Lazy Binding은 첫 호출 때 GOT를 채우고, BIND_NOW는 시작 시 모두 채웁니다. 최신 Ubuntu는 보안을 위해 BIND_NOW + RELRO가 기본이며, 채운 뒤 GOT를 읽기 전용으로 바꿉니다.
  • LD_PRELOAD는 Symbol 검색 순서를 이용해 Library 함수를 가로챕니다. dlsym(RTLD_NEXT, ...)으로 원래 함수를 호출할 수 있습니다.
  • dlopen/dlsym으로 실행 중에 Library를 Load할 수 있습니다.

5-3. Kernel이 하는 일: load_elf_binary

strace의 1번 줄 안에서 일어나는 일입니다. strace로는 볼 수 없으므로 Kernel Source의 흐름으로 정리합니다.

execve()  →  do_execveat_common()                     fs/exec.c
   1. 실행 File 을 열고 앞부분(첫 256 Byte)을 읽는다
   2. 형식을 판별한다:  "\177ELF" → load_elf_binary()      fs/binfmt_elf.c
                        "#!"      → load_script()          (Interpreter 를 다시 execve)
   3. Program Header 를 읽는다.  PT_INTERP 가 있으면 그 File(ld.so)도 연다
   ─────────────── 돌아올 수 없는 지점 (point of no return) ───────────────
   4. 기존 주소 공간(mm)을 버린다: 코드, Data, Heap, Stack, mmap 영역 전부
      Thread 가 여럿이었다면 나머지를 종료한다
      Signal Handler 는 기본값으로, FD 는 O_CLOEXEC 인 것만 닫는다
   5. 실행 File 의 PT_LOAD 를 하나씩 mmap 한다 (PIE 이면 Random 주소에)
      MemSiz > FileSiz 인 부분(.bss)은 0 으로 채운 Anonymous 영역으로 만든다
   6. PT_INTERP 가 있으면 ld.so 의 PT_LOAD 도 같은 방식으로 mmap 한다
   7. 새 Stack 을 만들고 argc, argv, envp, auxv 를 채운다            → 5-4
   8. vDSO 를 Mapping 한다                                          → L02
   9. 복귀할 주소(rip)를 설정한다:
        PT_INTERP 있음 → ld.so 의 Entry Point
        PT_INTERP 없음 → 실행 File 의 Entry Point
  10. System Call 에서 "복귀"한다. 그런데 돌아가는 곳은 완전히 새로운 프로그램이다

Q2. ELF File 전체를 읽어 들이는가

아닙니다. 5번은 read가 아니라 mmap 입니다. "이 주소 범위는 이 File의 이 부분에 해당한다"는 대응 관계만 기록하고 끝납니다. 실제 내용은 프로그램이 그 주소를 처음 건드릴 때 Page 단위로 읽어 옵니다. 그래서 수백 MB짜리 실행 File도 execve 자체는 순식간에 끝납니다. 이 동작(Demand Paging, Page Fault)이 Chapter 2의 주제입니다.

새 프로그램은 빈손으로 시작하지 않습니다. Kernel이 새 Stack의 꼭대기에 정보를 쌓아 둡니다.

  │ 문자열들: "./hello", "PATH=…", … │

  │ auxv[n] = { AT_NULL, 0 }   │
  │ …                          │   Auxiliary Vector: (종류, 값) 쌍의 배열

  │ argv[0]                    │

5-6. _start에서 main까지, 그리고 main 이후

_start는 우리가 작성한 적이 없습니다. gcc가 Link할 때 자동으로 넣는 시작 코드(crt1.o)에 들어 있습니다.

_start가 하는 일은 단순합니다. Stack에서 argc와 argv를 꺼내고, main의 주소를 첫 번째 인자로 해서 libc의 __libc_start_main을 호출합니다. main은 특별한 함수가 아니라 __libc_start_main이 호출해 주는 Callback입니다.

마지막 명령이 hlt인 것도 확인하세요. __libc_start_main은 절대 돌아오지 않으므로, 혹시 돌아오면 L01에서 본 것처럼 즉시 죽도록 해 둔 것입니다.

main을 호출한 것이 __libc_start_main이고, 그것을 호출한 것이 _start임이 Backtrace에 그대로 보입니다.

__libc_start_main이 main 앞뒤로 하는 일을 ctor.c로 확인합니다.

./ctor

1. constructor  (main 이전, __libc_start_main 이 호출)
2. main
3. atexit       (exit 처리 중, 등록의 역순)
4. destructor   (exit 처리 중)

__libc_start_main(main, argc, argv, …)
   1. libc 초기화 (stdio, Stack Protector, Thread 기본 구조)
   2. constructor 호출 (.init_array 에 등록된 함수들, C++ 전역 객체 생성자 포함)
   3. result = main(argc, argv, envp)
   4. exit(result)
        → atexit Handler (등록의 역순)
        → destructor (.fini_array)
        → stdio Buffer Flush            ← printf 출력이 사라지지 않는 이유
        → _exit(result) → exit_group System Call

main에서 return 0;만 했는데 Process가 종료되는 이유, 그리고 기존 과정에서 배운 "exit()는 Buffer를 Flush하지만 _exit()는 하지 않는다"의 위치가 여기입니다.

5-7. main 없는 프로그램

Kernel이 아는 것은 Entry Point 주소뿐입니다. main이라는 이름은 libc와의 약속일 뿐입니다. nostart.c는 libc 없이 _start를 직접 작성합니다.

void _start(void)
{
    static const char msg[] = "no main, no libc\n";

    sys3(1 /* write */, 1, (long)msg, (long)(sizeof(msg) - 1));
    sys3(60 /* exit */, 0, 0, 0);
    for (;;) { }
}

정리

execve에서 main까지의 전체 흐름입니다.

[Application]  execve("./hello")
      ↓  syscall
[Kernel]       ELF 확인 → 기존 주소 공간 폐기 → PT_LOAD 를 mmap → ld.so 도 mmap
               → Stack 에 argc/argv/envp/auxv → vDSO → rip = ld.so 의 Entry
      ↓  sysret (새 프로그램으로 "복귀")
[ld.so]        auxv 로 실행 File 위치 파악 → NEEDED 의 Library 를 찾아 mmap
               → Relocation, GOT 채우기 → RELRO(mprotect) → AT_ENTRY 로 점프
      ↓
[_start]       argc, argv 를 꺼내 __libc_start_main(main, …) 호출
      ↓
[libc]         초기화 → constructor → main(argc, argv, envp)
      ↓
[main]         우리가 작성한 코드
      ↓  return
[libc]         exit() → atexit → destructor → stdio Flush → exit_group
  • execve는 ELF를 읽어 들이는 것이 아니라 mmap으로 대응시킵니다. 실제 내용은 접근할 때 올라옵니다(Chapter 2).
  • Kernel이 처음 실행시키는 코드는 main이 아니라 Dynamic Loader의 _start 입니다.
  • main은 __libc_start_main이 호출하는 Callback이고, main의 return 값으로 exit()가 호출됩니다.
  • strace 출력에서 main 이전의 줄들은 ld.so가 Library를 찾고(openat), Segment를 올리고(mmap), 보호하는(mprotect) 과정입니다.

✏️ 빈칸 채우기 5-1

libc 없이 Entry Point 를 직접 작성합니다. 빈칸을 채워 fill_5_1.c 로 저장하고 아래 명령으로 빌드하세요.

static long sys3(long nr, long a1, long a2, long a3)
{
    long ret;

    __asm__ volatile("syscall" : "=a"(ret)
                     : "0"(nr), "D"(a1), "S"(a2), "d"(a3)
                     : "rcx", "r11", "memory");
    return ret;
}

void (void)                            /* Kernel 이 점프해 오는 곳 */
{
    static const char msg[] = "no main, no libc\n";

    sys3(, 1, (long)msg, (long)(sizeof(msg) - 1));   /* write */
    sys3(, 0, 0, 0);                               /* exit  */
    for (;;) { }                            /* return 하면 돌아갈 곳이 없다 */
}

static long sys3(long nr, long a1, long a2, long a3)
{
    long ret;

    __asm__ volatile("syscall" : "=a"(ret)
                     : "0"(nr), "D"(a1), "S"(a2), "d"(a3)
                     : "rcx", "r11", "memory");
    return ret;
}

void _start(void)                            /* Kernel 이 점프해 오는 곳 */
{
    static const char msg[] = "no main, no libc\n";

    sys3(1, 1, (long)msg, (long)(sizeof(msg) - 1));   /* write */
    sys3(60, 0, 0, 0);                               /* exit  */
    for (;;) { }                            /* return 하면 돌아갈 곳이 없다 */
}

Kernel 이 아는 것은 Entry Point 하나이고, 기본 Entry Point 의 Symbol 이름이 _start 입니다. write 는 1번, exit 는 60번입니다. _start 는 call 된 것이 아니라 Kernel 이 점프시킨 것이라 Stack 에 복귀 주소가 없으므로, exit System Call 로 끝내야 합니다. -nostdlib -static 으로 빌드하면 System Call 이 execve, write, exit 세 개뿐입니다.

✏️ 괄호 넣기 5-2

  1. gdb 에서 프로그램의 첫 번째 기계어 명령에서 멈추는 명령은 이다.
  2. Kernel 이 새 Stack 에 넣어 Dynamic Loader 에게 전달하는 (종류, 값) 배열은 이다.
  3. _start 는 main 의 주소를 첫 인자로 libc 의 을 호출한다.
