16-2. 증가가 사라진다

race_counter.c는 Thread 두 개가 같은 전역 변수를 1,000만 번씩 증가시킵니다.

static long counter;

static void *worker(void *arg)
{
    for (i = 0; i < loops; i++)
        counter++;
    return NULL;
}

./race_counter
./race_counter

expected 20000000
actual   13121383   (lost 6878617)

expected 20000000
actual   10344699   (lost 9655301)

기대값보다 작고, 실행할 때마다 다릅니다. 값이 기대값보다 커지는 경우는 없습니다. 증가가 "사라지는" 방향으로만 틀립니다. 이유는 16-3~4에서 설명됩니다.

16-3. `counter++`의 기계어

objdump -d race_counter | awk '/<worker>:/,/ret/' | grep -A2 "<counter>" | head -n 3

    123f:	48 8b 05 ea 2d 00 00 	mov    0x2dea(%rip),%rax        # 4030 <counter>
    1246:	48 83 c0 01          	add    $0x1,%rax
    124a:	48 89 05 df 2d 00 00 	mov    %rax,0x2ddf(%rip)        # 4030 <counter>
단계 명령 의미
Load mov counter, %rax Memory의 값을 Register로 가져온다
Add add $1, %rax Register에서 1을 더한다
Store mov %rax, counter 결과를 Memory에 쓴다

핵심은 %rax입니다. Register는 Thread마다 따로입니다(Context Switch 때 Thread별로 저장/복원되고, Core가 다르면 물리적으로도 다릅니다). 반면 counter는 Thread들이 공유하는 Memory입니다(같은 Process의 Thread는 Page Table이 같습니다).

즉 각 Thread는 공유 값을 자기만의 복사본으로 가져가서 계산하고, 그 결과로 공유 값을 덮어씁니다.

16-4. Animation: 두 Thread의 Interleaving

  1. 순차 실행: A의 세 단계가 끝난 뒤 B가 실행됩니다. 결과는 2.
  2. Lost Update: A가 Load한 직후 B가 Load합니다. 둘 다 0을 가져가 1을 Store합니다. 증가 두 번, 결과는 1.
  3. 오래된 값으로 덮어쓰기: A가 Load한 뒤 멈춰 있는 동안 B가 여러 번 증가시킵니다. A가 돌아와 Store하면 B의 증가가 한꺼번에 사라집니다. 16-2에서 수백만 개가 사라진 이유입니다.
  4. lock add 한 명령: Load-Add-Store가 쪼개지지 않는 경우(L17 미리 보기).

결과가 기대값보다 커질 수 없는 이유도 여기서 보입니다. 모든 Store는 "누군가 Load한 값 + 1"이므로, 잘못될 수 있는 방향은 이미 반영된 증가를 옛 값으로 덮어쓰는 것뿐입니다.

16-5. CPU가 하나여도 발생한다

"두 CPU가 동시에 실행하니까 생기는 문제"라고 생각하기 쉽습니다. CPU 하나에 묶어서 실행해 봅니다.

taskset -c 0 ./race_counter

expected 20000000
actual   10344699   (lost 9655301)

여전히 발생합니다. CPU가 하나여도 Kernel은 Timer Interrupt로 Thread를 아무 명령 사이에서나 중단시키고 다른 Thread를 실행합니다(Preemption). Load와 Store 사이에서 중단되면 16-4의 3번 Scenario가 그대로 일어납니다.

원인
CPU 여러 개 두 Core가 진짜 동시에 Load-Add-Store를 실행
CPU 하나 Load와 Store 사이에서 Preemption

Race Condition은 "동시 실행"의 문제가 아니라 "쪼개질 수 있는 연산"의 문제입니다.

16-6. -O2로 Build하면 "고쳐진" 것처럼 보인다

이 Lab의 Makefile은 -O0입니다. 최적화를 켜 봅니다.

gcc -O2 -pthread -o race_counter_O2 race_counter.c
./race_counter_O2

expected 20000000
actual   20000000   (lost 0)

고쳐졌을까요? 기계어를 봅니다.

objdump -d race_counter_O2 | awk '/<worker>:/,/ret/'

00000000000013a0 <worker>:
    13a0:	f3 0f 1e fa          	endbr64
    13a4:	48 8b 05 65 2c 00 00 	mov    0x2c65(%rip),%rax        # 4010 <loops>
    13ab:	48 85 c0             	test   %rax,%rax
    13ae:	7e 07                	jle    13b7 <worker+0x17>
    13b0:	48 01 05 79 2c 00 00 	add    %rax,0x2c79(%rip)        # 4030 <counter>
    13b7:	31 c0                	xor    %eax,%eax
    13b9:	c3                   	ret

Loop가 사라졌습니다. Compiler가 "1을 1,000만 번 더하는 것은 1,000만을 한 번 더하는 것과 같다"고 판단해 counter += loops 한 번으로 바꿨습니다. Race가 일어날 수 있는 순간이 2,000만 번에서 2번으로 줄어든 것이지 없어진 것이 아닙니다.

⚠ WARNING
"돌려 보니 값이 맞더라"는 Thread 코드가 올바르다는 증거가 되지 못합니다. Race는 Compiler Option, CPU 개수, 부하, Timing에 따라 나타났다 사라집니다. 개발 PC에서 한 번도 안 나던 Bug가 Core가 많은 Server에서 하루에 한 번 나오는 이유입니다.

Compiler가 이렇게 바꿔도 되는 근거는 C 표준입니다. 보호 없이 여러 Thread가 같은 변수에 접근하고 그중 하나라도 쓰기이면 Data Race이고, Data Race가 있는 프로그램은 Undefined Behavior입니다. Compiler는 "이 변수는 다른 Thread가 건드리지 않는다"고 가정하고 최적화합니다. L18에서 이 가정이 만드는 더 놀라운 결과를 봅니다.

16-7. Check-Then-Act: 변수가 Atomic이어도 남는 문제

check_then_act.c는 재고가 1개인 상품을 두 Thread가 동시에 구매합니다.

if (stock > 0) {        /* check */
    sched_yield();      /* 끼어들 틈을 일부러 넓힘 */
    stock--;            /* act   */
    ...구매 성공
}

./check_then_act

buyer 1: 구매 성공
buyer 2: 구매 성공
sold = 2, stock = -1

stock--를 아무리 안전한 연산으로 바꿔도 이 Bug는 남습니다. 문제는 개별 연산이 아니라 "검사"와 "실행" 사이에 다른 Thread가 끼어드는 것입니다.

용어 의미 예
Data Race 보호 없이 같은 Memory에 동시 접근, 하나 이상이 쓰기 counter++
Race Condition 결과가 실행 순서(Timing)에 따라 달라지는 논리 오류 재고 확인 후 차감, File 존재 확인 후 생성

Data Race가 없어도 Race Condition은 있을 수 있습니다. 보호해야 하는 것은 변수 하나가 아니라 하나의 논리적 동작 전체(Critical Section)입니다.

여기서 이 Chapter의 나머지 질문이 나옵니다.

  • 증가 하나를 위해 mutex는 과합니다. Load-Add-Store를 쪼개지지 않게 할 수는 없을까? → L17
  • mutex의 lock은 매번 Kernel에 들어갈까? → L19
  • Thread를 늘리면 빨라질까, 느려질까? → L20

정리

  • counter++는 Load, Add, Store 세 단계입니다. Register는 Thread마다 따로이고 Memory는 공유이므로, 단계 사이에 다른 Thread가 끼어들면 옛 값으로 덮어써서 증가가 사라집니다(Lost Update).
  • CPU가 하나여도 Preemption으로 발생합니다. 문제의 본질은 동시 실행이 아니라 쪼개질 수 있는 연산입니다.
  • Data Race는 C 표준상 Undefined Behavior입니다. 최적화에 따라 증상이 사라진 것처럼 보일 수 있지만 고쳐진 것이 아닙니다.
  • Data Race(Memory 접근의 문제)와 Race Condition(Check-Then-Act 같은 논리의 문제)은 다릅니다. 보호 단위는 논리적 동작 전체입니다.
  • ThreadSanitizer는 실행된 경로의 Data Race를 변수, 줄, Thread 단위로 알려 줍니다.

Lecture 17

Atomic Operation과 Compare-And-Swap

영상 17분

CPU에는 "읽고, 바꾸고, 쓰는" 과정을 쪼개지지 않게 실행하는 명령이 있습니다. mutex를 포함한 모든 동기화 도구가 이 명령 위에 만들어집니다.

17-1. Atomic이란

Atomic Operation은 다른 Thread(와 다른 CPU)가 보기에 "전혀 실행되지 않았거나, 완전히 끝났거나" 둘 중 하나로만 보이는 연산입니다. 중간 상태가 관찰되지 않습니다.

L16의 counter++는 Load와 Store 사이의 중간 상태가 관찰되었기 때문에 Atomic이 아니었습니다.

17-2. atomic_fetch_add와 `lock` Prefix

atomic_counter.c는 L16의 race_counter.c에서 두 줄만 바꾼 것입니다.

#include <stdatomic.h>

static atomic_long counter;                 /* long → atomic_long */
...
    atomic_fetch_add(&counter, 1);          /* counter++ → atomic_fetch_add */

./atomic_counter

expected 20000000
actual   20000000

mutex가 없는데 항상 맞습니다. 기계어를 봅니다.

objdump -d atomic_counter | awk '/<worker>:/,/ret/' | grep lock

    12d9:	f0 48 83 05 36 2d 00 	lock addq $0x1,0x2d36(%rip)        # 4018 <counter>

세 명령이 lock addq 한 명령이 되었습니다. 맨 앞의 Byte f0이 lock Prefix입니다.

-O0의 counter++ atomic_fetch_add
기계어 mov / add / mov (3개) lock addq $1, counter (1개)
Preemption 명령 사이에서 중단 가능 명령 하나는 중간에 중단되지 않음
다른 Core 사이에 끼어들 수 있음 lock이 막음

📌 NOTE
atomic_long x; x++;처럼 연산자를 써도 Atomic으로 처리됩니다. 이 과정에서는 의도가 분명히 보이도록 atomic_fetch_add, atomic_load, atomic_store 함수 형태를 씁니다. GCC 내장 함수 __atomic_fetch_add, __sync_fetch_and_add도 같은 기계어를 만듭니다.

17-3. `lock`은 무엇을 잠그는가

lock 없는 addq $1, counter도 명령은 하나입니다. CPU가 하나라면 Preemption은 명령 사이에서만 일어나므로 안전합니다. 그러나 Core가 여러 개면 부족합니다. 명령 하나도 CPU 내부에서는 "Memory 읽기 → 더하기 → Memory 쓰기"로 실행되고, 그 사이에 다른 Core가 같은 주소를 읽거나 쓸 수 있습니다.

lock Prefix는 그 명령이 실행되는 동안 해당 Cache Line을 이 Core가 독점하게 합니다.

Core 0:  lock addq $1, counter
           ① counter 가 있는 Cache Line 을 독점(Exclusive) 상태로 확보
              → 다른 Core 의 같은 Line 은 무효화된다
           ② 읽기 → +1 → 쓰기                (이 사이 다른 Core 의 접근은 대기)
           ③ 독점 해제

Core 1:  lock addq $1, counter      ← Core 0 의 ③ 이후에 ① 을 시작

옛 CPU는 Memory Bus 전체를 잠갔지만(Bus Lock), 현재는 Cache Line 단위로 처리합니다(Cache Locking). 이 "Cache Line을 빼앗아 오는" 동작은 공짜가 아닙니다. L20의 False Sharing과 Lock Contention이 모두 여기서 나옵니다.

17-4. Compare-And-Swap

lock add는 "더하기"에만 쓸 수 있습니다. "현재 값을 보고 임의의 계산을 해서 바꾸기"를 Atomic하게 하려면 더 일반적인 도구가 필요합니다.

Compare-And-Swap(CAS): "이 변수가 아직 내가 본 값 그대로라면 새 값으로 바꿔라. 아니면 아무것도 하지 말고 실패를 알려라." 이 전체가 Atomic입니다.

bool atomic_compare_exchange_strong(atomic_long *obj, long *expected, long desired);

Atomic {
    if (*obj == *expected) { *obj = desired;   return true;  }
    else                   { *expected = *obj; return false; }     ← 실패하면 현재 값을 알려 준다
}

x86-64에서는 lock cmpxchg 명령 하나입니다.

의미
_strong 값이 같으면 반드시 성공
_weak 값이 같아도 드물게 실패할 수 있음(Spurious Failure). ARM 등에서 더 효율적. Loop 안에서는 weak를 쓴다

x86-64에서는 둘이 같은 명령이 됩니다.

17-5. Animation: CAS 성공, 실패와 재시도, ABA

  1. 경쟁 없음: A가 읽고, 계산하고, CAS가 성공합니다.
  2. 경쟁: A가 읽은 뒤 B가 먼저 CAS에 성공합니다. A의 CAS는 실패하고, 새 값으로 다시 계산해 재시도합니다. L16의 Lost Update와 달리 덮어쓰지 않고 실패하는 것이 핵심입니다.
  3. ABA: A가 값 A를 읽은 뒤, 다른 Thread가 A → B → A로 바꿉니다. A의 CAS는 "그대로"라고 판단해 성공합니다(17-9).

17-6. CAS Loop Pattern

cas_counter.c

old = atomic_load(&counter);                                        /* 1. 읽는다 */
while (!atomic_compare_exchange_weak(&counter, &old, old + 1))      /* 3. 그대로면 교체 */
    my_retries++;                                                   /*    실패: old 가 현재 값으로 갱신됨 → 2 부터 다시 */
                                        /* 2. 새 값 계산: old + 1 */

./cas_counter

expected 10000000
actual   10000000
CAS 재시도 1284377 회

값은 정확하고, 재시도가 100만 번 넘게 있었습니다(횟수는 CPU 수와 Timing에 따라 크게 다릅니다). 재시도 한 번은 L16이었다면 Lost Update 한 번이었을 상황입니다. CAS는 그것을 감지해서 다시 한 것입니다.

objdump -d cas_counter | awk '/<worker>:/,/ret/' | grep cmpxchg

    12fb:	f0 48 0f b1 0d 1c 2d 	lock cmpxchg %rcx,0x2d1c(%rip)        # 4020 <counter>

이 방식을 낙관적(Optimistic) 동시성 제어라고 합니다.

mutex (비관적) CAS Loop (낙관적)
전제 충돌할 것이다 → 먼저 잠근다 충돌하지 않을 것이다 → 일단 해 보고, 충돌했으면 다시 한다
충돌 시 기다린다(Sleep 가능) 다시 계산한다(CPU 사용)
다른 Thread가 중간에 멈추면 Lock을 쥔 채 멈추면 모두 대기 영향 없음. 누군가는 항상 전진한다

17-7. CAS로 Spin Lock 만들기

Atomic 명령 하나로 Lock을 만들 수 있습니다. spinlock_cas.c

static atomic_flag lock_flag = ATOMIC_FLAG_INIT;

static void spin_lock(void)
{
    while (atomic_flag_test_and_set(&lock_flag))    /* 1 로 만들고 "이전 값" 을 return */
        __builtin_ia32_pause();                     /* 이전 값이 1 이면 남이 쥐고 있다 → 다시 */
}

static void spin_unlock(void) { atomic_flag_clear(&lock_flag); }

./spinlock_cas
objdump -d spinlock_cas | awk '/<worker>:/,/ret/' | grep -E "xchg|pause"

expected 10000000
actual   10000000
    12e0:	f3 90                	pause
    12e4:	86 05 36 2d 00 00    	xchg   %al,0x2d36(%rip)        # 4020 <lock_flag>

counter는 일반 long인데 결과가 맞습니다. xchg(Memory 피연산자가 있으면 lock 없이도 항상 Atomic)로 만든 Lock이 보호했기 때문입니다. 기존 과정에서 개념으로 배운 Spin Lock의 실체가 이 몇 줄입니다.

내용
pause "나는 Spin 중"이라고 CPU에 알림. 전력 소모와 Pipeline 낭비를 줄이고 Hyper-Threading의 상대 Thread에 양보
장점 Kernel에 가지 않음. Lock을 쥐는 시간이 아주 짧으면 가장 빠름
단점 기다리는 동안 CPU를 100% 사용. Lock을 쥔 Thread가 Preemption되면 나머지는 Time Slice 내내 헛돈다

User Space에서는 Lock을 쥔 Thread가 언제든 Preemption될 수 있으므로 순수한 Spin Lock은 위험합니다(Kernel 안에서는 Preemption을 끌 수 있어서 널리 씁니다). 그래서 "잠깐 Spin하다가 안 되면 Kernel에서 잔다"가 필요하고, 그것이 L19의 futex입니다.

❗ IMPORTANT

17-9. ABA 문제

CAS는 "값이 같은가"만 봅니다. "그 사이에 아무 일도 없었는가"는 보장하지 않습니다.

Lock-Free Stack:   top → [A] → [B] → [C]

Thread 1: pop 시작.  old = A, next = B 를 읽음. CAS(top, A → B) 직전에 Preemption
Thread 2: pop A,  pop B,  free(B),  push A           →  top → [A] → [C]
Thread 1: 재개. CAS(top, A → B): top 이 여전히 A → 성공!  →  top → [B] (이미 해제된 Memory)

정수 Counter에서는 ABA가 문제되지 않습니다(값이 같으면 결과도 같음). Pointer를 CAS할 때, 특히 Node를 해제하고 재사용할 때 문제가 됩니다.

해결 방법 내용
Version Tag Pointer와 함께 증가하는 Counter를 묶어서 CAS(Double-Width CAS, cmpxchg16b)
Hazard Pointer, Epoch(RCU) 다른 Thread가 참조 중일 수 있는 Node는 해제를 미룸
해제하지 않기 Node를 재사용하지 않으면 ABA가 생기지 않음(L20의 예제가 이 방식)

Lock-Free 자료 구조가 "CAS Loop만 돌리면 되는" 것이 아니라 어려운 이유입니다.

정리

  • Atomic Operation은 중간 상태가 관찰되지 않는 연산입니다. x86-64에서는 lock Prefix가 명령 실행 동안 Cache Line을 독점하게 해서 구현합니다.
  • C11 <stdatomic.h>의 atomic_fetch_add는 lock add 명령 하나가 됩니다.
  • CAS는 "내가 본 값 그대로면 교체, 아니면 실패". lock cmpxchg 명령입니다. 읽기 → 계산 → CAS → 실패하면 재시도 Pattern으로 임의의 갱신을 Lock 없이 할 수 있습니다.
  • Atomic 명령 하나(xchg)로 Spin Lock을 만들 수 있습니다. mutex를 포함한 모든 Lock의 바닥에는 Atomic 명령이 있습니다.
  • CAS는 값만 비교하므로 ABA 문제가 있습니다. Pointer와 Memory 재사용이 있을 때 주의합니다.
  • Atomic은 변수 하나의 단일 연산만 보호합니다. 여러 단계의 논리적 동작에는 Lock이 필요합니다.

static void *worker(void *arg)
{
    long i, old, my_retries = 0;

    (void)arg;
    for (i = 0; i < loops; i++) {
        old = atomic_load(&counter);
        /* counter 가 아직 old 와 같으면 old + 1 로 바꾼다.
         * 그 사이 다른 Thread 가 바꿨다면 실패하고, old 에 현재 값이 들어온다. */
        while (!atomic_compare_exchange_weak(&counter, &old, old + 1))
            my_retries++;
    }
    atomic_fetch_add(&retries, my_retries);
    return NULL;
}

현재 값을 atomic_load 로 읽고, atomic_compare_exchange_weak(&counter, &old, old + 1) 로 "지금도 old 이면 old+1 로 바꿔라" 를 원자적으로 시도합니다. 실패하면 old 가 최신 값으로 갱신되므로 반복합니다. x86 에서는 lock cmpxchg 명령 하나입니다. 재시도 횟수는 경쟁 정도를 보여 줍니다.

    12ea:	85 c0                	test   %eax,%eax
    12ec:	75 02                	jne    12f0 <worker+0x10>
    12ee:	eb fe                	jmp    12ee <worker+0xe>

stop을 딱 한 번 읽고, 0이면 jmp 12ee, 즉 자기 자신으로 점프하는 무한 Loop에 들어갑니다. Compiler가 코드를 이렇게 바꾼 것입니다.

if (!stop)
    for (;;) ;          /* stop 을 다시 읽지 않는다 */

Compiler의 논리: "Loop 안에서 stop을 바꾸는 코드가 없다. 그러면 매번 Memory에서 읽는 것은 낭비다. 한 번만 읽자." L16에서 말했듯 Compiler는 다른 Thread가 이 변수를 바꾸지 않는다고 가정합니다. Data Race는 Undefined Behavior이므로 그렇게 가정해도 표준 위반이 아닙니다.

-O0에서는 매번 읽으므로 잘 동작합니다. "Debug Build에서는 되는데 Release Build에서 멈춘다"의 전형입니다.

18-3. atomic으로 고치기, 그리고 volatile

같은 Source를 -DUSE_ATOMIC으로 Build한 것이 stop_flag_atomic입니다.

static atomic_bool stop;
while (!atomic_load(&stop)) ...
atomic_store(&stop, 1);

./stop_flag_atomic

main  : 정상 종료

atomic_load는 Compiler에게 "이 읽기는 매번 실제로 해야 하고, 다른 Thread의 쓰기와 순서 관계가 정의되어야 한다"고 알려 줍니다.

volatile int stop;으로 바꿔도 이 예제는 동작합니다. 그러나 올바른 해결책이 아닙니다.

volatile _Atomic / atomic_*
원래 목적 Memory-Mapped I/O, Signal Handler Thread 간 공유
Compiler에 대한 효과 읽기/쓰기를 생략하거나 합치지 않음 같음
Atomic 보장 없음. volatile long v; v++는 여전히 Load-Add-Store 있음
CPU 수준의 순서 보장(Barrier) 없음 있음 (18-7)
C 표준상 Data Race 여전히 Data Race(UB) 아님

volatile은 18-2의 문제(Compiler)만 막고, L16의 문제(Atomic)와 다음 Step의 문제(CPU)는 막지 못합니다.

18-4. 이번에는 CPU 차례: Store Buffer

Compiler가 순서를 지켜 줘도 CPU가 남아 있습니다. Memory 쓰기는 느립니다(Cache Line을 독점 상태로 가져와야 함, L17). CPU는 그것을 기다리지 않습니다.

┌──────── Core 0 ────────┐          ┌──────── Core 1 ────────┐
│  실행 Unit              │          │  실행 Unit              │
│    │ 쓰기         ▲ 읽기  │          │    │ 쓰기         ▲ 읽기  │
│    ▼             │      │          │    ▼             │      │
│ [Store Buffer]───┘      │          │ [Store Buffer]───┘      │
│    │ (나중에, 순서대로)     │          │    │                    │
│    ▼                    │          │    ▼                    │
│  L1 Cache  ◄───── Cache Coherence Protocol ─────►  L1 Cache  │
└─────────────────────────┘          └─────────────────────────┘
  • 쓰기는 일단 Core 전용의 Store Buffer에 들어가고, CPU는 바로 다음 명령으로 넘어갑니다.
  • 자기 자신의 읽기는 Store Buffer를 먼저 확인합니다(Store Forwarding). 그래서 Single Thread 프로그램은 아무 차이도 느끼지 못합니다.
  • 다른 Core는 Store Buffer 안을 볼 수 없습니다. Buffer가 Cache로 내려갈 때까지 옛 값을 봅니다.

즉 "내가 쓴 값"이 다른 Core에 보이기까지 수 ns ~ 수십 ns의 틈이 있습니다.

18-5. 불가능해 보이는 결과 관찰하기

store_buffer.c는 두 Thread를 서로 다른 CPU에 고정하고 다음을 10만 번 반복합니다(x, y는 매번 0으로 초기화).

Thread 1 (CPU 0)        Thread 2 (CPU 1)
  x = 1;                  y = 1;
  r1 = y;                 r2 = x;

네 줄을 어떤 순서로 섞어도 (r1, r2) = (0, 0)은 나올 수 없을 것 같습니다. r1 = 0이려면 Thread 1의 읽기가 y = 1보다 먼저여야 하고, 그러면 x = 1은 그보다 더 먼저이므로 Thread 2는 x = 1을 읽어야 합니다.

./store_buffer

rounds 100000
(r1,r2) = (0,1)    48211
(r1,r2) = (1,0)    51402
(r1,r2) = (1,1)      241
(r1,r2) = (0,0)      146   <- 순차적으로는 불가능한 결과

나옵니다(횟수는 환경에 따라 0에 가까울 수도, 훨씬 많을 수도 있습니다). x, y는 volatile이므로 Compiler 탓이 아닙니다.

CPU 0: x = 1  → Store Buffer 에 들어감 (아직 CPU 1 에 안 보임)
CPU 1: y = 1  → Store Buffer 에 들어감 (아직 CPU 0 에 안 보임)
CPU 0: r1 = y → Cache 에서 읽음 → 0
CPU 1: r2 = x → Cache 에서 읽음 → 0
       (이후 두 Store Buffer 가 Cache 로 내려감)

각 CPU 입장에서는 자기 명령을 순서대로 실행했습니다. 그러나 전체로 보면 두 읽기가 두 쓰기보다 먼저 일어난 것과 같습니다. 이것을 Store-Load Reordering이라고 합니다.

📌 NOTE
이것은 장난감 예제가 아닙니다. "내 Flag를 세우고 → 상대 Flag를 확인한다"는 Dekker/Peterson 상호 배제 Algorithm의 핵심 구조입니다. 교과서의 Peterson Algorithm을 일반 변수로 구현하면 실제 Multi-Core CPU에서 깨지는 이유입니다.

18-7. Memory Barrier

Memory Barrier는 CPU에게 "여기서는 순서를 지켜라"고 지시하는 명령입니다. x86-64에서 Store-Load 순서를 강제하는 방법은 두 가지입니다.

방법 동작
mfence 앞선 모든 Store가 Memory에 반영될 때까지 다음 명령을 진행하지 않음
lock 붙은 명령, xchg 실행 자체가 Store Buffer를 비우고 Cache Line을 독점. 부수 효과로 Full Barrier

store_buffer_fixed는 같은 Source를 atomic_store/atomic_load로 Build한 것입니다.

./store_buffer_fixed | tail -n 1
objdump -d store_buffer_fixed | awk '/<t1>:/,/ret/' | grep -E "xchg|mfence"

(r1,r2) = (0,0)        0   <- 순차적으로는 불가능한 결과
    145a:	87 05 2c 2c 00 00    	xchg   %eax,0x2c2c(%rip)        # 408c <x>

atomic_store(&x, 1)이 mov가 아니라 xchg가 되었습니다. 값을 교환할 필요가 없는데도 xchg를 쓰는 이유가 바로 Barrier 효과입니다. C11 Atomic의 기본 Memory Order인 memory_order_seq_cst(Sequentially Consistent)는 "모든 Thread가 하나의 전체 순서에 동의한다"를 보장해야 하고, 그러려면 Store 뒤에 Barrier가 필요합니다.

Linux Kernel 의미
smp_mb() Full Barrier (x86: lock addl $0, (%rsp))
smp_rmb(), smp_wmb() 읽기/쓰기 Barrier (x86에서는 대부분 No-op, 18-8)
READ_ONCE(), WRITE_ONCE() Compiler에 대한 Barrier. 읽기/쓰기를 정확히 한 번 수행 (18-2의 문제)

Kernel이 "Compiler용"과 "CPU용"을 구분해서 제공한다는 점이 이 Lecture의 두 주제와 정확히 대응합니다.

18-8. x86은 관대한 편이다: TSO와 Weak Ordering

x86-64의 Memory Model은 TSO(Total Store Order) 입니다. 허용되는 순서 바뀜은 18-5에서 본 Store → Load 하나뿐입니다.

순서 바뀜 x86-64 (TSO) ARM, RISC-V, POWER (Weak)
Store 뒤의 Load가 먼저 (Store-Load) 가능 가능
Store끼리 순서 바뀜 (Store-Store) 없음 가능
Load끼리, Load 뒤의 Store가 먼저 없음 가능

ARM에서는 다음 코드도 깨질 수 있습니다.

/* Thread 1 */              /* Thread 2 */
data = 42;                  if (ready)
ready = 1;                      use(data);      /* ARM: ready 가 먼저 보이고 data 는 아직 0 일 수 있다 */

x86 PC에서 개발한 Lock-Free 코드가 ARM Server, Raspberry Pi, Apple Silicon에서 깨지는 원인입니다. atomic_*을 쓰면 Compiler가 Architecture에 맞는 Barrier를 넣어 줍니다.

18-9. 실무 규칙

  1. Thread 간에 공유하는 변수는 mutex로 보호하거나 atomic_*으로 접근합니다. 일반 변수 + volatile은 답이 아닙니다.
  2. Memory Order 인자(memory_order_relaxed 등)는 기본값(seq_cst)을 쓰고, 측정으로 병목이 확인된 뒤에만 약화합니다.
  3. mutex를 쓰면 이 Lecture의 문제를 생각하지 않아도 됩니다. pthread_mutex_lock/unlock은 내부에 Atomic 명령(= Full Barrier)이 있어서, Critical Section 안의 일반 변수 접근은 다른 Thread에 올바른 순서로 보입니다.
  4. 이 Lecture의 지식이 직접 필요한 곳은 Lock-Free 코드를 읽거나 Debug할 때입니다.

정리

  • Compiler는 다른 Thread를 고려하지 않고 공유 변수의 읽기를 제거하거나 옮깁니다. -O2의 while (!stop)이 무한 Loop가 되는 이유입니다.
  • CPU는 쓰기를 Store Buffer에 넣고 다음 명령을 실행합니다. 다른 Core는 그 값을 바로 보지 못하므로 Store-Load Reordering이 관찰됩니다.
  • Memory Barrier(mfence, lock 명령, xchg)는 순서를 강제합니다. atomic_store의 기본 Order(seq_cst)는 x86에서 xchg로 구현되어 Barrier를 포함합니다.
  • x86-64(TSO)는 Store-Load만 바뀌지만 ARM 등은 더 많은 순서가 바뀝니다.
  • volatile은 Compiler 문제만 막습니다. Atomic도 아니고 Barrier도 없습니다. Thread 공유에는 atomic_* 또는 mutex를 씁니다.

Lecture 19

Futex 내부 구조

영상 18분

pthread_mutex_lock()은 System Call이 아닙니다. 경쟁이 없으면 Atomic 명령 하나로 끝나고, 경쟁이 있을 때만 futex System Call로 Kernel에 들어가 잠듭니다.

학습 목표

  • mutex의 Fast Path(User Space)와 Slow Path(Kernel)를 구분하고 strace로 확인할 수 있다.
  • FUTEX_WAIT와 FUTEX_WAKE의 의미, 특히 WAIT가 값을 다시 확인하는 이유를 설명할 수 있다.
  • Kernel이 futex 대기 Thread를 관리하는 방식(주소 기반 Hash Table)을 설명할 수 있다.
  • futex와 Atomic 연산으로 간단한 mutex를 직접 구현할 수 있다.
  • condition variable, semaphore, pthread_join도 futex 위에 만들어져 있음을 안다.

19-1. 두 가지 나쁜 선택

방식 경쟁이 없을 때 경쟁이 있을 때
Spin Lock (L17) 빠름. Atomic 명령 하나 나쁨. 기다리는 내내 CPU 100%
매번 Kernel에 요청 (옛 System V Semaphore) 나쁨. Lock을 쓸 때마다 System Call 좋음. 잠들어서 CPU를 양보

실제 프로그램에서 mutex는 대부분 경쟁 없이 획득됩니다. 그렇다면 흔한 경우는 User Space에서 끝내고, 드문 경우에만 Kernel의 도움을 받으면 됩니다. 이것이 futex(Fast Userspace muTEX) 의 발상입니다.

lock:    Atomic CAS 로 시도 ─ 성공 ──────────────────────────→ 끝 (System Call 없음)
                            └ 실패 → futex(FUTEX_WAIT) → Kernel 에서 Sleep

unlock:  Atomic 으로 해제 ─ 기다리는 Thread 없음 ─────────────→ 끝 (System Call 없음)
                          └ 있음 → futex(FUTEX_WAKE) → 하나를 깨움

19-2. 경쟁 없는 mutex: System Call 0회

mutex_nocontend.c는 Thread 하나가 lock/unlock을 100만 번 반복합니다.

% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
  0.00    0.000000           0         0           total

pthread_mutex_lock을 100만 번 호출했는데 futex System Call은 0번입니다. 1회당 십수 ns는 L02에서 측정한 System Call 비용(수백 ns)보다 한 자릿수 이상 작습니다. mutex는 Kernel에 가지 않았습니다.

pthread_mutex_t의 실체는 User Space Memory에 있는 구조체이고, 그 안의 int 하나(__lock)가 Lock 상태입니다. lock은 이 정수에 대한 CAS(0 → 1)입니다.

19-5. WAIT는 왜 값을 다시 확인하는가

FUTEX_WAIT가 단순히 "재워 줘"였다면 이런 일이 생깁니다.

Thread A (lock 시도)                     Thread B (lock 보유)
  state 를 읽음 → 잠겨 있다
  "자야겠다" 고 결정
                                          unlock: state = 0
                                          FUTEX_WAKE → 자는 Thread 없음. 아무도 안 깨움
  futex(WAIT) → 잠든다
  ... 영원히 ...                           (다시는 WAKE 가 오지 않는다)

"확인"과 "잠들기" 사이에 끼어든 Lost Wakeup입니다. L16의 Check-Then-Act와 같은 구조입니다.

그래서 FUTEX_WAIT는 Kernel 안에서 Lock을 잡은 채로 *uaddr == val을 다시 확인하고, 같을 때만 대기 Queue에 넣습니다. B의 state = 0이 먼저 일어났다면 값이 달라져 있으므로 A는 자지 않고 EAGAIN으로 돌아와 다시 lock을 시도합니다. 19-3의 errors 6만 건이 이것입니다. 오류가 아니라 Lost Wakeup을 막은 횟수입니다.

📌 NOTE
기존 과정에서 condition variable을 쓸 때 "pthread_cond_wait는 mutex를 잡은 채 호출하고, 조건은 if가 아니라 while로 다시 확인한다"고 배웠습니다. 같은 문제에 대한 같은 해법입니다. futex도 깨어난 뒤에 값을 다시 확인하는 Loop 안에서 씁니다.

  1. 경쟁 없음: lock과 unlock이 모두 User Space의 Atomic 명령으로 끝납니다. Kernel 영역이 한 번도 켜지지 않는 것을 확인합니다.

  3. Lost Wakeup 방지: B가 잠들기 직전에 A가 unlock합니다. Kernel의 값 재확인 덕분에 B는 잠들지 않고 EAGAIN으로 돌아옵니다.

19-7. futex로 mutex 직접 만들기

my_mutex.c는 Ulrich Drepper의 논문 "Futexes Are Tricky"의 방식입니다. 정수 하나에 세 가지 상태를 둡니다.

state 의미
0 잠겨 있지 않음
1 잠김. 기다리는 Thread 없음
2 잠김. 기다리는 Thread가 있을 수 있음 
static void my_lock(void)
{
    int c = 0;

    if (atomic_compare_exchange_strong(&state, &c, 1))
        return;                             /* Fast Path: 0 → 1. System Call 없음 */
    if (c != 2)
        c = atomic_exchange(&state, 2);     /* "기다리는 Thread 있음" 표시 */
    while (c != 0) {
        syscall(SYS_futex, &state, FUTEX_WAIT, 2, NULL, NULL, 0);   /* state == 2 인 동안 Sleep */
        c = atomic_exchange(&state, 2);     /* 깨어나면 다시 시도. 이전 값이 0 이었으면 획득 성공 */
    }
}

static void my_unlock(void)
{
    if (atomic_fetch_sub(&state, 1) != 1) { /* 1 → 0 이었으면 기다리는 Thread 없음: 끝 */
        atomic_store(&state, 0);            /* 2 였다 */
        syscall(SYS_futex, &state, FUTEX_WAKE, 1, NULL, NULL, 0);
    }
}

1과 2를 구분하는 이유는 unlock의 Fast Path 때문입니다. 상태가 "잠김/안 잠김" 둘뿐이라면 unlock은 누가 기다리는지 알 수 없어 매번 FUTEX_WAKE를 호출해야 합니다.

19-8. Kernel 안에서는

futex(uaddr, FUTEX_WAIT, val)                              kernel/futex/waitwake.c
  1. uaddr 로 Key 를 만든다
       PRIVATE: (mm, Virtual Address)            같은 Process 의 Thread 끼리
       SHARED : (inode 또는 Page, Offset)         mmap 으로 공유한 Memory 의 Process 끼리
  2. Key 를 Hash → Bucket 을 찾고 Bucket 의 Spin Lock 을 잡는다
  3. *uaddr 를 읽어 val 과 비교한다. 다르면 → Lock 해제, -EAGAIN          ← 19-5 의 재확인
  4. 현재 Thread 를 Bucket 의 대기 List 에 넣고 상태를 Sleep 으로 바꾼다
  5. Bucket Lock 해제 → schedule() → 다른 Thread 가 CPU 를 쓴다

futex(uaddr, FUTEX_WAKE, n)
  1. 같은 방법으로 Bucket 을 찾아 Lock 을 잡는다
  2. 대기 List 에서 Key 가 같은 Thread 를 최대 n 개 꺼내 Runnable 로 만든다
  • mutex를 만들 때도 없앨 때도 Kernel에 알리지 않습니다. 경쟁이 생기기 전까지 Kernel은 그 mutex의 존재조차 모릅니다. mutex를 100만 개 만들어도 Kernel 자원은 0입니다.
  • strace에 보이던 _PRIVATE 접미사는 "같은 Process 안에서만 쓴다"는 뜻이고, Key 계산이 단순해져 더 빠릅니다. Process 간에 쓰려면 mutex를 MAP_SHARED 영역(L10)에 두고 PTHREAD_PROCESS_SHARED 속성을 줍니다.
  • 3번에서 *uaddr를 읽다가 Page Fault가 날 수도 있습니다. Chapter 2의 내용이 여기서도 이어집니다.

정리

  • futex는 "흔한 경우는 User Space에서, 드문 경우만 Kernel에서" 처리하는 설계입니다. 경쟁 없는 mutex의 lock/unlock은 System Call이 0회입니다.
  • Lock의 상태는 User Space의 정수에 있고 Atomic 연산으로 다룹니다. Kernel은 재우기(FUTEX_WAIT)와 깨우기(FUTEX_WAKE) 만 담당하며 값의 의미를 모릅니다.
  • FUTEX_WAIT는 Kernel 안에서 값을 다시 확인한 뒤에만 재웁니다. 확인과 잠들기 사이의 Lost Wakeup을 막기 위해서이며, 값이 달라졌으면 EAGAIN입니다.
  • Kernel은 주소를 Key로 하는 Hash Table로 대기 Thread를 관리합니다. 경쟁이 없는 mutex는 Kernel 자원을 쓰지 않습니다.
  • state를 0/1/2로 두면 unlock도 Fast Path를 가질 수 있습니다.
  • condition variable, semaphore, pthread_join, 다른 언어의 mutex도 모두 futex 위에 있습니다.

20-1. Cache Line과 MESI

CPU는 Memory를 Byte 단위가 아니라 64Byte 덩어리(Cache Line) 로 Cache에 가져옵니다.

getconf LEVEL1_DCACHE_LINESIZE

64

Core마다 자기 Cache가 있으므로 같은 Line의 복사본이 여러 Core에 있을 수 있습니다. 복사본들이 어긋나지 않도록 Hardware가 Line마다 상태를 관리합니다(MESI Protocol).

상태 의미 쓰려면
Modified 나만 갖고 있고, 수정했다 바로 쓴다
Exclusive 나만 갖고 있고, 수정 전이다 바로 쓴다
Shared 다른 Core도 갖고 있다. 읽기만 가능 다른 Core의 복사본을 무효화해야 한다
Invalid 내 복사본은 쓸 수 없다 가진 Core에게서 가져와야 한다

규칙은 하나입니다. 쓰려면 그 Line을 독점해야 한다. 다른 Core에 복사본이 있으면 Core 간 통신으로 무효화하고, 상대는 다음에 접근할 때 다시 가져와야 합니다. 이 왕복이 수십 ~ 100ns 이상이며, L1 Cache 접근(약 1ns)의 수십 배입니다.

중요한 점은 단위가 변수가 아니라 Line이라는 것입니다.

20-2. False Sharing 재현

false_sharing.c에서 두 Thread는 서로 다른 변수를 증가시킵니다. 공유하는 Data가 없으므로 Lock도 필요 없고 Race도 없습니다.

struct packed_pair { volatile long a; volatile long b; };      /* a 와 b 가 8 Byte 거리 */

Thread A:  for (...) packed.a++;
Thread B:  for (...) packed.b++;

결과는 정확합니다. 그런데 a와 b는 같은 Cache Line 안에 있습니다.

Core 0: a++  → Line 을 독점(M)으로 확보 → Core 1 의 복사본 무효화
Core 1: b++  → 내 복사본이 Invalid → Core 0 에서 가져와 독점 → Core 0 의 복사본 무효화
Core 0: a++  → 내 복사본이 Invalid → Core 1 에서 가져와 ...

논리적으로는 아무것도 공유하지 않는데 Hardware 수준에서는 Line 하나를 계속 주고받습니다. False Sharing입니다.

20-3. Animation: Cache Line Ping-Pong

  1. 같은 Cache Line: Core 0과 Core 1이 번갈아 쓸 때마다 Line의 상태가 M ↔ I로 뒤집히고 무효화 횟수가 올라갑니다.
  2. Padding 적용: a와 b가 다른 Line에 있습니다. 두 Core 모두 M 상태를 유지하고 통신이 없습니다.
  3. True Sharing (lock add): 같은 변수를 Atomic으로 증가시키는 경우. 올바른 코드이지만 Line이 오가는 것은 똑같습니다(20-5의 복선).

  • global: Thread를 늘릴수록 느려집니다. 한 번에 한 Thread만 Critical Section에 들어가므로 병렬성이 0이고, 거기에 futex Sleep/Wakeup, Context Switch, Lock이 든 Cache Line의 이동 비용이 더해집니다.
  • atomic: Lock이 없는데도 빨라지지 않습니다. lock add는 실행할 때마다 Cache Line을 독점해야 하므로(L17) Core들이 Line 하나를 두고 줄을 섭니다. Lock-Free라고 해서 Contention이 없는 것이 아닙니다.
  • local: 유일하게 Thread 수에 비례해 빨라집니다. 공유하는 것이 없기 때문입니다.

20-6. Contention을 줄이는 설계

더 빠른 Lock을 찾기 전에 덜 공유하는 구조를 먼저 찾습니다.

방법 내용 예
공유하지 않기 Thread별 Data + 마지막에 합산. TLS 활용 lock_scale의 local, Kernel의 per-CPU 변수
Critical Section 줄이기 Lock 안에서 I/O, malloc, 긴 계산을 하지 않는다 계산은 밖에서, 결과 반영만 안에서
Lock 쪼개기 자료 구조 전체가 아니라 부분별 Lock Hash Table의 Bucket별 Lock
읽기와 쓰기 구분 읽기가 압도적이면 pthread_rwlock, RCU 설정 값, Routing Table
Batch 처리 한 번 잠그고 여러 개 처리 Queue에서 여러 항목을 한 번에 꺼냄

20-7. Lock-Free Stack

L17의 CAS Loop Pattern을 Pointer에 적용합니다. lockfree_stack.c (Treiber Stack)

static _Atomic(struct node *) top;

static void push(struct node *n)
{
    struct node *old = atomic_load(&top);
    do {
        n->next = old;                                          /* 1. 내가 본 top 을 next 로 */
    } while (!atomic_compare_exchange_weak(&top, &old, n));     /* 2. top 이 그대로면 나로 교체 */
}

static struct node *pop(void)
{
    struct node *old = atomic_load(&top);
    while (old != NULL && !atomic_compare_exchange_weak(&top, &old, old->next))
        ;
    return old;
}

Thread 4개가 동시에 100만 개를 push하고, 이어서 동시에 pop합니다.

./lockfree_stack

pushed 1000000, popped 1000000
sum expected 500000500000
sum actual   500000500000

mutex 없이 개수와 합계가 정확합니다. 하나도 잃어버리거나 중복되지 않았습니다.

❗ IMPORTANT
이 예제는 Node를 미리 할당해 두고 해제도 재사용도 하지 않기 때문에 안전합니다. pop한 Node를 free하거나 다시 push하면 L17의 ABA 문제가 발생하고, old->next를 읽는 순간 이미 해제된 Memory일 수도 있습니다. 실용적인 Lock-Free 자료 구조에는 Hazard Pointer나 Epoch 기반의 안전한 Memory 회수가 반드시 필요합니다.

20-8. Lock-Free의 의미와 한계

Lock-Free는 "Lock을 안 쓴다"가 아니라 진행 보장에 대한 용어입니다.

용어 보장
Blocking (mutex) Lock을 쥔 Thread가 멈추면 모두 멈춘다
Lock-Free 어떤 Thread가 언제 멈추더라도 누군가는 항상 전진한다 (CAS가 실패했다는 것은 다른 Thread가 성공했다는 뜻)
Wait-Free 모든 Thread가 유한한 단계 안에 끝난다
Lock-Free의 장점 Lock-Free의 한계
Deadlock이 없다 구현과 검증이 매우 어렵다 (ABA, Memory 회수, Memory Ordering)
Lock을 쥔 Thread의 Preemption에 영향받지 않는다 빠르다는 보장이 없다. Cache Line Contention은 그대로이고(20-5), 경쟁이 심하면 재시도로 CPU를 낭비한다
Signal Handler, Interrupt Context에서 쓸 수 있다 여러 변수를 함께 바꾸는 복합 연산에는 맞지 않는다

선택 기준입니다.

  1. 기본은 mutex입니다. 경쟁이 없으면 십수 ns이고(L19), 올바르게 쓰기 쉽습니다.
  2. Counter, Flag, 통계 같은 단일 변수는 atomic_*.
  3. 느리다면 Lock 종류를 바꾸기 전에 공유를 줄입니다(20-6).
  4. Lock-Free 자료 구조가 정말 필요하면 직접 만들지 말고 검증된 Library(liburcu, Concurrency Kit, 언어의 표준 Concurrent Collection)를 씁니다.

정리

  • CPU는 Memory를 64Byte Cache Line 단위로 다루고, 쓰려면 그 Line을 독점해야 합니다(MESI).
  • False Sharing: 서로 다른 변수라도 같은 Line에 있으면 Core들이 Line을 계속 주고받습니다. alignas(64)로 떨어뜨립니다.
  • 하나의 Lock이나 하나의 Atomic 변수를 여러 Thread가 두드리면 Thread를 늘려도 빨라지지 않습니다. 공유하지 않는 설계(Thread별 Data)만이 선형으로 확장됩니다.
  • Lock-Free는 "누군가는 항상 전진한다"는 보장입니다. CAS Loop로 Stack을 만들 수 있지만 ABA와 Memory 회수 때문에 실용 구현은 어렵고, 빠르다는 보장도 없습니다.
  • 기본은 mutex, 단일 변수는 atomic, 느리면 공유를 줄이고, Lock-Free는 검증된 Library로.
