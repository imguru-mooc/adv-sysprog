Lecture 06

Process Virtual Address Space

영상 16분

malloc(1GB)는 성공하는데 Memory 사용량은 늘지 않습니다. Process가 보는 "주소"는 Physical Memory의 주소가 아니기 때문입니다.

학습 목표

  • /proc/PID/maps의 각 열을 읽고, 변수의 주소가 어느 영역에 속하는지 찾을 수 있다.
  • Kernel이 주소 공간을 VMA(vm_area_struct) 단위로 관리함을 설명할 수 있다.
  • Heap(brk)과 mmap 영역, Stack이 각각 어떻게 커지는지 관찰할 수 있다.
  • VSZ(Virtual Size)와 RSS(Resident Set Size)의 차이를 설명할 수 있다.
  • ASLR이 무엇이고 어떻게 끄고 켜는지 안다.

L03의 readelf -l과 비교해 보세요. LOAD의 Offset 0x1000, 권한 R E가 그대로 00001000, r-xp로 나타납니다.

Kernel 안에서 이 한 줄은 struct vm_area_struct(VMA) 객체 하나입니다.

task_struct ──→ mm_struct ──┬─ VMA { 0x5556711f9000 ~ 0x5556711fa000, r-x, file=addr_map, off=0x1000 }
  (Process)     (주소 공간)   ├─ VMA { 0x55569dc4b000 ~ 0x55569dc6c000, rw-, file=없음 }     [heap]
                            ├─ VMA { 0x7f35cea28000 ~ 0x7f35cebb0000, r-x, file=libc.so.6 }
                            └─ VMA { 0x7ffdcb77b000 ~ 0x7ffdcb79c000, rw-, file=없음 }     [stack]

이것이 Chapter 1에서 말한 "대응 관계의 기록"입니다. mmap()이 하는 일은 VMA를 하나 만들어 목록에 넣는 것이 전부입니다. 아직 Physical Memory는 한 Byte도 쓰지 않았습니다.

📌 NOTE
VMA는 "이 주소 범위는 유효하다, 여기에 접근하면 이런 내용이 보여야 한다"는 약속입니다. 약속을 실제로 이행하는 시점이 L09의 Page Fault입니다.

6-4. Heap은 brk로, 큰 할당은 mmap으로

heap_grow.c는 malloc 전후의 [heap] 줄을 출력합니다.

./heap_grow

== start  (program break = 0x55a622a5a000)
   ([heap] 없음)
== after malloc(1000)  (program break = 0x55a622a7b000)
   55a622a5a000-55a622a7b000 rw-p 00000000 00:00 0                          [heap]
   small = 0x55a622a5a2a0
== after malloc(4MB)  (program break = 0x55a622a7b000)
   55a622a5a000-55a622a7b000 rw-p 00000000 00:00 0                          [heap]
   big   = 0x7f12535ff010

세 가지를 확인합니다.

  1. 시작할 때는 [heap]이 없습니다. Heap은 처음부터 있는 영역이 아닙니다.
  2. 1000 Byte를 요청했는데 132KB(0x21000)가 생겼습니다. glibc는 brk System Call로 program break를 넉넉히 올려 두고, 이후의 작은 malloc은 System Call 없이 그 안에서 나눠 줍니다(L02의 "System Call 비용 줄이기").
  3. 4MB 요청에는 [heap]이 변하지 않았고 주소가 0x7f...입니다. 큰 요청(기본 128KB 이상)은 mmap으로 별도 영역을 만듭니다.

strace로 확인합니다.

strace -e trace=brk,mmap,munmap ./heap_grow 2>&1 | tail -n 8

...

...
munmap(0x7f12535ff000, 4198400)         = 0

free 하면 glibc 내부 목록으로 돌아감. Kernel에 반환되지 않을 수 있음 즉시 munmap으로 반환

💡 TIP
"free 했는데 Process의 Memory 사용량이 줄지 않는다"는 흔한 질문의 답이 이 표에 있습니다. brk로 올린 Heap은 맨 끝이 비어야만 내릴 수 있습니다.

📌 NOTE
이 프로그램은 printf 대신 write로 출력합니다. printf와 fopen은 내부에서 malloc을 호출해 Heap을 먼저 만들어 버리기 때문입니다. 관찰 도구가 관찰 대상을 바꾸는 사례입니다.

6-5. Stack은 저절로 커진다

stack_grow.c는 호출마다 16KB의 지역 변수를 쓰는 함수를 256번 재귀 호출합니다.

./stack_grow

start          [stack] 7fff880ad000-7fff880ce000     132 KB
depth 256      [stack] 7fff87cc6000-7fff880ce000    4128 KB
after return   [stack] 7fff87cc6000-7fff880ce000    4128 KB
  • 끝 주소(...0ce000)는 그대로이고 시작 주소가 아래로 내려갔습니다. Stack은 낮은 주소 방향으로 자랍니다.
  • brk나 mmap 같은 System Call을 부른 적이 없습니다. [stack] VMA 바로 아래 주소를 건드리면 Kernel이 Page Fault 처리 중에 VMA를 자동으로 확장해 줍니다(L09).
  • 함수에서 돌아온 뒤에도 줄어들지 않습니다.

한계는 ulimit -s입니다.

ulimit -s

8192

8MB를 넘어 확장하려고 하면 Kernel이 거부하고 SIGSEGV를 보냅니다. 무한 재귀가 "Segmentation fault"로 끝나는 이유입니다. Thread의 Stack은 다릅니다. pthread_create가 mmap으로 고정 크기(기본 8MB)를 미리 잡아 두며 자동 확장되지 않습니다.

6-6. 1GB를 할당해도 Memory가 줄지 않는 이유

vsz_rss.c는 1GB를 malloc하고, 그중 256MB만 건드립니다.

./vsz_rss

== start
   VmSize:	    2688 kB
   VmRSS:	    1544 kB
== after malloc(1GB)          : 주소 범위만 예약
   VmSize:	 1051268 kB
   VmRSS:	    1548 kB
== after touching 256MB       : 건드린 만큼만 Physical Memory
   VmSize:	 1051268 kB
   VmRSS:	  263692 kB
== after free
   VmSize:	    2688 kB
   VmRSS:	    1544 kB
의미 malloc(1GB) 직후 256MB 건드린 뒤
VmSize (VSZ) VMA 크기의 합계. "약속한 주소 범위" +1GB 그대로
VmRSS (RSS) 지금 Physical Memory에 올라와 있는 양 변화 없음 +256MB

malloc(1GB)는 1GB짜리 VMA 하나를 만들었을 뿐입니다. Physical Memory는 Page를 처음 건드리는 순간 4KB씩 배정됩니다. 이것을 Demand Paging이라고 합니다.

ps, top에서도 같은 값을 봅니다.

ps -o pid,vsz,rss,comm -p $$

    PID    VSZ   RSS COMMAND
   1873  11284  5632 bash

❗ IMPORTANT
"이 Process가 Memory를 얼마나 쓰는가"를 볼 때는 RSS를 봅니다. VSZ가 수십 GB인 프로그램(Java, Go Runtime, Chrome)은 주소 범위를 넉넉히 예약했을 뿐이고 이상이 아닙니다. 다만 RSS도 완벽하지는 않습니다. libc처럼 여러 Process가 공유하는 Page가 중복으로 세어집니다. 이를 보정한 값이 smaps의 PSS이며 Chapter 7에서 다룹니다.

📌 NOTE
Physical Memory가 4GB뿐인 VM에서 malloc(100GB)도 성공할 수 있습니다. Linux는 기본적으로 "약속은 넉넉히, 이행은 나중에"(Overcommit) 방식입니다. 실제로 다 건드려서 Memory가 바닥나면 OOM Killer가 Process를 종료시킵니다. 이 주제는 Chapter 8(Cgroup)에서 이어집니다.

6-7. ASLR

addr_map을 두 번 실행해 주소를 비교합니다.

./addr_map | head -n 8 > a.txt; ./addr_map | head -n 8 > b.txt; paste a.txt b.txt | awk '{print $2, $3, $6}'

main 0x5556711f9369 0x55d8c2a41369
g_ro 0x5556711fa0d4 0x55d8c2a420d4
...
local 0x7ffdcb79a6d4 0x7ffe0b1c4a14

실행할 때마다 모든 영역의 위치가 바뀝니다. ASLR(Address Space Layout Randomization) 입니다. 공격자가 "libc의 system 함수는 이 주소에 있다"고 미리 알 수 없게 합니다. 끝 3자리(369)가 같은 이유는 Random화가 Page(4KB = 0x1000) 단위이기 때문입니다.

cat /proc/sys/kernel/randomize_va_space

2
값 의미
0 끔
1 Stack, mmap, vDSO
2 1 + Heap (기본)

System 설정을 바꾸지 않고 한 번의 실행만 ASLR 없이 하려면 setarch를 씁니다.

setarch -R ./addr_map | head -n 1
setarch -R ./addr_map | head -n 1

text   main    0x555555555369
text   main    0x555555555369

Chapter 1에서 gdb 안의 주소가 늘 0x5555555...였던 이유입니다. gdb가 같은 방식으로 ASLR을 끄고 실행합니다.

정리

  • Process가 보는 주소는 Process마다 따로 주어지는 Virtual Address입니다. User Space만 128TB입니다.
  • Kernel은 주소 공간을 VMA 단위로 관리합니다. /proc/PID/maps의 한 줄이 VMA 하나이고, mmap()은 VMA를 만드는 일입니다.
  • 작은 malloc은 brk로 [heap]을 늘리고, 큰 malloc은 mmap으로 별도 영역을 만듭니다. Stack은 접근하면 Kernel이 자동으로 확장합니다.
  • VSZ는 약속한 주소 범위, RSS는 실제 올라온 Physical Memory입니다. Page를 처음 건드릴 때 Physical Memory가 배정됩니다(Demand Paging).
  • ASLR은 실행할 때마다 영역의 위치를 Page 단위로 바꿉니다. setarch -R로 한 번만 끌 수 있습니다.

7-1. 왜 Byte 단위가 아니라 Page 단위인가

Virtual Address마다 Physical Address를 따로 기록한다면 변환표가 Memory보다 커집니다. 그래서 주소 공간을 고정 크기 조각으로 나누고 조각 단위로 대응시킵니다.

getconf PAGESIZE

4096
용어 의미
Page Virtual 주소 공간의 4KB 조각
Frame (Page Frame) Physical Memory의 4KB 조각
VPN (Virtual Page Number) Virtual Address ÷ 4096
PFN (Page Frame Number) Physical Address ÷ 4096
Offset 조각 안에서의 위치. 하위 12bit. 변환되지 않고 그대로 복사 
Virtual Address  = [        VPN        ][ Offset 12bit ]
                             │ Page Table 이 바꿔 준다        │ 그대로
                             ▼                              ▼
Physical Address = [        PFN        ][ Offset 12bit ]

L06에서 본 것들이 모두 4KB 단위였던 이유입니다: maps의 주소 범위, ASLR의 끝 3자리(0x369 = Offset), ELF LOAD의 Align 0x1000, 권한이 Page 단위로만 부여되는 것.

7-2. 주소를 쪼개 보기

x86-64는 (기본 설정에서) 64bit 중 48bit만 주소로 사용합니다. VPN 36bit를 다시 9bit씩 4개로 나눕니다.

 63      48 47    39 38    30 29    21 20    12 11         0
┌──────────┬────────┬────────┬────────┬────────┬────────────┐
│ 부호 확장 │  PGD   │  PUD   │  PMD   │  PTE   │   Offset   │
│  16bit   │  9bit  │  9bit  │  9bit  │  9bit  │   12bit    │
└──────────┴────────┴────────┴────────┴────────┴────────────┘

va_split.c로 분해합니다.

./va_split 7ffd1234abcd

VA            = 0x00007ffd1234abcd
  PGD index   = 255   (bit 47..39)
  PUD index   = 500   (bit 38..30)
  PMD index   = 145   (bit 29..21)
  PTE index   = 330   (bit 20..12)
  Offset      = 0xbcd (bit 11..0)
  VPN         = 0x7ffd1234a

9bit이므로 각 Index는 0~511입니다. 각 Level의 Table은 Entry 512개 × 8Byte = 4096Byte, 정확히 Page 하나입니다. 우연이 아니라 그렇게 되도록 설계한 숫자입니다.

L06의 addr_map이 출력한 주소들도 넣어 보세요. Stack 주소(0x7ffd...)는 PGD Index가 255(User 영역의 맨 끝), 실행 File(0x55...)은 170 근처가 나옵니다.

📌 NOTE
Linux의 이름은 PGD(Page Global Directory) → P4D → PUD(Upper) → PMD(Middle) → PTE입니다. 4-Level에서는 P4D가 접혀서 없는 것처럼 동작합니다. Intel 문서의 이름은 PML4 → PDPT → PD → PT입니다. 57bit 주소를 쓰는 5-Level Paging도 있지만 일반 환경에서는 4-Level을 씁니다.

7-3. 왜 4-Level인가

VPN 36bit를 한 단계로 찾는 Table을 만들면 2^36개 × 8Byte = 512GB가 Process마다 필요합니다. 대부분의 Process는 128TB 중 극히 일부만 쓰는데도 그렇습니다.

Table을 나무 구조로 나누면 쓰지 않는 범위의 하위 Table은 만들지 않아도 됩니다.

CR3 ──→ PGD (4KB)
         ├─ [170] ──→ PUD ──→ PMD ──→ PTE Table ──→ 실행 File, Heap 의 Frame 들
         ├─ [171..253]  비어 있음 → 하위 Table 없음 (Memory 0)
         ├─ [254] ──→ PUD ──→ PMD ──→ PTE Table ──→ libc, mmap 의 Frame 들
         └─ [255] ──→ PUD ──→ PMD ──→ PTE Table ──→ Stack 의 Frame 들
Level Entry 하나가 담당하는 범위
PGD 512GB
PUD 1GB
PMD 2MB
PTE 4KB

hello 같은 작은 Process의 Page Table은 Table 10여 개(수십 KB)로 충분합니다.

CR3 Register에는 현재 Process의 PGD가 있는 Physical Address가 들어 있습니다. Context Switch 때 Kernel이 CR3를 바꾸면 주소 공간 전체가 바뀝니다. 서로 다른 Process가 같은 Virtual Address 0x555555555369를 써도 충돌하지 않는 이유입니다.

❗ IMPORTANT
변환은 Kernel Software가 아니라 CPU 안의 MMU(Memory Management Unit) Hardware가 Memory 접근마다 수행합니다. Kernel의 역할은 Table의 내용을 채우고 CR3를 설정하는 것까지입니다.

7-5. PTE에는 무엇이 들어 있는가

PTE 하나는 64bit입니다. PFN과 함께 Flag가 들어 있고, MMU는 변환할 때 이 Flag를 검사합니다.

 63  62..52  51 ............ 12  11..9  8  7  6  5  4  3  2   1   0
┌───┬───────┬──────────────────┬──────┬──┬──┬──┬──┬──┬──┬───┬───┬───┐
│NX │       │       PFN        │      │G │  │D │A │  │  │U/S│R/W│ P │
└───┴───────┴──────────────────┴──────┴──┴──┴──┴──┴──┴──┴───┴───┴───┘
Flag 의미 위반하면 이 과정에서 만난 곳
P Present 이 Page가 Physical Memory에 있다 Page Fault Demand Paging (L06, L09)
R/W 1이면 쓰기 허용 Page Fault .rodata 쓰기, RELRO(L04), COW
U/S 1이면 Ring 3 접근 허용 Page Fault Kernel 영역 보호 (L01)
NX 1이면 실행 금지 Page Fault W^X, GNU_STACK (L03)
A Accessed 접근하면 CPU가 1로 설정 Kernel이 "최근에 쓴 Page"를 판단 (Reclaim)
D Dirty 쓰면 CPU가 1로 설정 File로 되돌려 써야 하는가 (Chapter 3)

maps에서 본 r-xp, rw-p 같은 VMA의 권한이 이 Flag로 옮겨져 Hardware에 의해 강제됩니다.

VMA PTE
누가 읽는가 Kernel (Software) MMU (Hardware)
단위 연속된 주소 범위 Page 하나
의미 "이렇게 되어야 한다"는 약속 "지금 이렇게 되어 있다"는 현재 상태
만들어지는 때 mmap, brk, execve 그 Page를 처음 접근할 때 (Page Fault)

둘이 다를 수 있다는 점이 핵심입니다. VMA는 rw-인데 PTE의 R/W가 0이면? 그것이 COW입니다(7-8).

7-6. pagemap으로 Physical Frame 확인

/proc/PID/pagemap은 Virtual Page마다 8Byte씩, 그 Page의 상태를 알려 주는 File입니다. pagemap.c는 VPN × 8 위치를 pread로 읽습니다.

./pagemap

page0 (건드리기 전) VA 0x7fac90828000  present=0
page0 (쓴 뒤)        VA 0x7fac90828000  present=1  PFN (root 권한 필요)
page1 (건드리지 않음) VA 0x7fac90829000  present=0
main 함수의 코드  VA 0x565363eb8407  present=1  PFN (root 권한 필요)

mmap으로 3 Page를 받았지만 건드리기 전에는 present=0, 즉 PTE가 없습니다. 한 Byte를 쓰자 그 Page만 present=1이 되었고 옆 Page는 여전히 0입니다. L06의 VSZ/RSS 차이를 Page 단위로 본 것입니다.

PFN은 보안상 root에게만 보입니다(Rowhammer 같은 Hardware 공격에 Physical 위치 정보가 악용되기 때문).

sudo ./pagemap

page0 (건드리기 전) VA 0x7fac90828000  present=0
page0 (쓴 뒤)        VA 0x7fac90828000  present=1  PFN 0x12e39d  PA 0x12e39d000
page1 (건드리지 않음) VA 0x7fac90829000  present=0
main 함수의 코드  VA 0x565363eb8407  present=1  PFN 0x12987e  PA 0x12987e407

PA = PFN × 4096 + Offset입니다. main의 VA 끝 3자리 407이 PA의 끝 3자리와 같습니다. Offset은 변환되지 않습니다.

7-7. Page Table도 Memory를 쓴다

vmpte.c는 1GB를 mmap하고 절반을 Page마다 건드린 뒤 VmPTE(이 Process의 Page Table이 차지하는 Memory)를 출력합니다.

./vmpte

mmap(1GB) 직후                    VmRSS:	    1552 kB  VmPTE:	      44 kB
512MB 를 Page 마다 건드린 뒤  VmRSS:	  525840 kB  VmPTE:	    1072 kB
munmap 뒤                          VmRSS:	    1552 kB  VmPTE:	      44 kB
  • mmap(1GB) 직후에는 VmPTE가 늘지 않습니다. VMA만 만들었고 Page Table은 건드리지 않았습니다.
  • 512MB = 131,072 Page. PTE 하나가 8Byte이므로 131,072 × 8 = 1,048,576Byte ≈ 1MB. 늘어난 양(약 1028KB)과 일치합니다.

Page Table 비용은 Data의 약 1/512(0.2%) 입니다. 작아 보이지만 Process가 수백 개이고 각자 수 GB를 Mapping하는 Database Server에서는 Page Table만 수 GB가 되기도 합니다. Huge Page(L08)가 해결책 중 하나입니다.

7-8. fork와 COW를 PFN으로 확인

기존 과정에서 "fork는 Memory를 복사하지 않고, 쓰는 순간 복사한다(Copy On Write)"고 배웠습니다. 이제 증거를 볼 수 있습니다. cow_pfn.c

sudo ./cow_pfn

VA 0x557306d73000 는 Parent 와 Child 에서 동일합니다
[parent] fork 전        PFN 0x124dc9
[child ] fork 직후      PFN 0x124dc9   <- Parent 와 같은 Frame
[child ] 쓰기 후        PFN 0x124dcc   <- 새 Frame 으로 복사됨
[parent] Child 종료 후  PFN 0x124dc9   p[0] = 'P'

fork가 실제로 하는 일을 Page Table 관점에서 정리합니다.

fork()
  1. Child 용 mm_struct 와 VMA 목록을 복사한다                (약속의 복사)
  2. Parent 의 Page Table 을 복사한다. Frame 은 복사하지 않는다  (같은 PFN 을 가리킴)
  3. 쓰기 가능한 Private Page 는 Parent 와 Child 양쪽 PTE 의 R/W 를 0 으로 바꾼다

Child 가 p[0] = 'C' 실행
  4. MMU: PTE 의 R/W = 0 인데 쓰기 → Page Fault
  5. Kernel: VMA 를 확인한다. rw- 이다 → 잘못된 접근이 아니라 COW 다
  6. 새 Frame 을 할당해 4KB 를 복사하고, Child 의 PTE 를 새 PFN + R/W = 1 로 바꾼다
  7. 같은 명령을 다시 실행한다 → 이번에는 성공

5번이 7-5에서 말한 "VMA(약속)와 PTE(현재 상태)가 다른 경우"입니다. fork가 Process 크기와 거의 무관하게 빠른 이유, 그리고 fork 직후 exec하는 Shell의 방식이 낭비가 아닌 이유입니다.

💡 TIP
cow_pfn.c에는 fork() 직전과 Child의 _exit() 직전에 fflush(stdout)이 있습니다. 출력을 Pipe로 보낼 때 stdio Buffer가 Child에 복제되어 중복 출력되거나, _exit이 Flush를 건너뛰어 출력이 사라지는 것을 막기 위해서입니다(L05의 exit vs _exit).

정리

  • 주소 변환은 4KB Page 단위입니다. VPN이 PFN으로 바뀌고 Offset 12bit는 그대로입니다.
  • x86-64는 48bit 주소를 9 + 9 + 9 + 9 + 12로 나눠 4-Level Table(PGD → PUD → PMD → PTE)을 따라갑니다. 쓰지 않는 범위의 Table은 만들지 않으므로 Memory가 절약됩니다.
  • CR3가 PGD의 Physical Address를 가리키고, 변환은 MMU Hardware가 수행합니다. Process마다 CR3가 다르므로 같은 Virtual Address가 다른 Frame을 가리킵니다.
  • PTE에는 PFN과 Flag(Present, R/W, U/S, NX, Accessed, Dirty)가 있습니다. VMA가 약속이라면 PTE는 현재 상태입니다.
  • PTE는 Page를 처음 접근할 때 만들어집니다. Page Table 자체도 Data의 약 1/512만큼 Memory를 씁니다.
  • fork는 Page Table만 복사하고 R/W를 0으로 만듭니다. 쓰는 순간의 Page Fault에서 복사가 일어납니다.

TLB와 Address Translation

Memory 접근 한 번에 Page Table을 네 번 읽어야 한다면 너무 느립니다. CPU는 최근의 변환 결과를 TLB라는 작은 Cache에 기억해 둡니다.

8-1. 문제: Memory 접근이 5배 느려진다

L07에서 본 변환 과정입니다.

mov (%rax), %ebx        ← Memory 에서 4 Byte 를 읽는 명령 하나

  ① PGD Entry 읽기     (Memory 접근)
  ② PUD Entry 읽기     (Memory 접근)
  ③ PMD Entry 읽기     (Memory 접근)
  ④ PTE 읽기           (Memory 접근)
  ⑤ 실제 Data 읽기      (Memory 접근)

명령어를 가져오는 것(Fetch)도 Memory 접근이므로 같은 과정을 거칩니다. Main Memory 접근이 약 100ns라면 변환만으로 400ns가 추가됩니다.

다행히 프로그램에는 지역성(Locality) 이 있습니다. 방금 접근한 Page를 곧 다시 접근합니다. 같은 Page 안의 4096개 주소는 모두 같은 변환 결과(VPN → PFN)를 씁니다. 그렇다면 결과를 기억해 두면 됩니다.

8-2. TLB의 구조

TLB(Translation Lookaside Buffer) 는 CPU Core 안에 있는 작은 Hardware Cache입니다.

           ┌─────────────── CPU Core ───────────────┐
 VA ──→    │  TLB:  VPN → PFN + 권한 Flag            │
           │   ├─ Hit  ─────────────────────────────┼──→ PA   (1ns 미만, Memory 접근 0회)
           │   └─ Miss → Page Table Walker (Hardware)│
           └──────────────┬─────────────────────────┘
                          ▼
                 Memory 의 Page Table 을 4 단계로 읽음 → 결과를 TLB 에 채움 → PA
내용
저장하는 것 VPN → PFN, 그리고 PTE의 권한 Flag(R/W, U/S, NX)
크기 매우 작음. L1 TLB 수십 개(Data 64개 안팎), L2 TLB 1,000~2,000개 수준
담당 범위 Entry 64개 × 4KB = 256KB, 2,048개 × 4KB = 8MB
Miss 때 x86-64는 Hardware(Page Walker)가 Page Table을 읽어 TLB를 채움. Kernel은 관여하지 않음
위치 Core마다 따로 있음

수 GB의 Memory를 쓰는 프로그램에 비하면 TLB가 한 번에 기억하는 범위는 아주 작습니다. 그래서 접근 Pattern이 중요해집니다.

자신의 CPU 정보는 다음 명령으로 일부 확인할 수 있습니다.

lscpu | grep -E "Model name|Address sizes"

Model name:                           Intel(R) Core(TM) i7-...
Address sizes:                        39 bits physical, 48 bits virtual

48 bits virtual이 L07의 48bit 주소입니다.

8-3. Animation: TLB Hit / Miss Simulator

Entry 4개짜리 작은 TLB(LRU 교체)로 동작을 확인합니다. Step 하나가 Memory 접근 한 번입니다.

  1. 지역성이 좋은 접근: 같은 Page들을 반복 접근합니다. 처음 몇 번만 Miss이고 이후 Hit가 이어지는 것을 봅니다.
  2. Page를 넓게 오가는 접근: 접근할 때마다 다른 Page입니다. TLB가 계속 교체되고 Hit Rate가 0에 가깝습니다.
  3. Context Switch: 중간에 다른 Process로 전환되면서 TLB가 비워집니다. 돌아온 뒤 다시 Miss가 나는 것을 확인합니다.
  4. Huge Page (2MB): 2번과 같은 주소들을 2MB Page로 Mapping한 경우입니다. 같은 접근인데 Hit Rate가 어떻게 달라지는지 비교합니다.

8-4. 접근 Pattern에 따른 차이 측정

tlb_stride.c는 같은 횟수(약 210만 회) 의 Memory 읽기를 두 가지 방식으로 수행합니다.

for (i = 0; i < NPAGES; i++) sum += p[i];           /* dense : 연속 주소. 64 Pages 안에서만 */
for (i = 0; i < NPAGES; i++) sum += p[i * PAGE];    /* sparse: 접근마다 다른 Page. 262,144 Pages */

Page Fault의 영향을 없애기 위해 측정 전에 모든 Page를 미리 건드려 둡니다.

접근 횟수      : 2097152 회씩
dense  (64 Pages)     :     0.8 ms

❗ IMPORTANT
이 차이가 전부 TLB 때문은 아닙니다. sparse 접근은 CPU Data Cache Miss도 함께 일으킵니다(접근마다 새 Cache Line). 또 dense 쪽은 Compiler가 SIMD 명령으로 최적화하기 쉽습니다. 이 실험이 보여 주는 것은 "접근 횟수가 같아도 몇 개의 Page를 오가는가에 따라 수십 배 차이가 난다"는 사실입니다. TLB만의 효과는 8-7에서 분리합니다.

8-5. TLB Miss ≠ Page Fault

혼동하기 쉬운 두 가지를 구분합니다.

TLB Miss Page Fault
의미 변환 결과가 TLB에 없다 유효한 변환이 Page Table에 없다 (Present=0 또는 권한 위반)
처리 주체 CPU Hardware (Page Walker) Kernel (Exception Handler)
비용 수십~수백 ns 최소 수 µs (Minor), Disk I/O가 있으면 ms 단위 (Major)
Kernel 진입 없음 있음 (L01의 Exception 경로)
프로그램에 보이는가 시간으로만 getrusage, /proc/PID/stat, perf의 page-faults로 셀 수 있음 
Memory 접근
   │
   ├─ TLB Hit ──────────────────────────────────────────→ 접근 완료
   │
   └─ TLB Miss → Hardware 가 Page Table Walk
                   ├─ PTE 유효 → TLB 에 채움 ────────────→ 접근 완료
                   └─ PTE 없음 / 권한 위반 → Page Fault → Kernel (L09)

8-4에서 Page를 미리 건드려 둔 것은 측정 구간에 Page Fault(오른쪽 아래 경로)가 섞이지 않게 하기 위해서였습니다.

8-6. Context Switch와 TLB

TLB에 있는 VPN 0x555555555 → PFN 0x12987e는 Process A의 변환입니다. Process B도 같은 VPN을 쓰지만 다른 Frame을 가리킵니다. Process가 바뀌었는데 TLB가 그대로라면 B가 A의 Memory를 읽게 됩니다.

방법 동작 비용
Flush CR3를 바꾸면 TLB 전체를 비운다 전환 직후 한동안 모든 접근이 TLB Miss
PCID (Process Context ID) TLB Entry마다 12bit Tag를 붙여 주소 공간을 구분한다 비우지 않아도 됨. 돌아왔을 때 Entry가 남아 있을 수 있음
Global bit (PTE의 G) Kernel 영역의 변환은 모든 Process에서 같으므로 Flush에서 제외 
grep -o -w pcid /proc/cpuinfo | head -n 1

pcid

이 Chapter의 관점에서 기억할 것은 세 가지입니다.

  • Thread 간 전환은 Process 간 전환보다 가볍습니다. 같은 Process의 Thread는 주소 공간(CR3)이 같아서 TLB를 비울 필요가 없습니다. 기존 과정에서 배운 "Thread가 Process보다 가볍다"의 Hardware적 이유 중 하나입니다.
  • Context Switch의 진짜 비용은 Register 저장이 아니라 그 이후의 Cache/TLB Miss입니다. Chapter 4의 Lock Contention, Chapter 5의 "Thread를 많이 만드는 대신 epoll"로 이어지는 배경입니다.
  • munmap, mprotect처럼 Mapping을 바꾸면 Kernel은 다른 Core의 TLB에 남은 옛 변환도 지워야 합니다(TLB Shootdown, Core 간 Interrupt 사용). Thread가 많은 프로그램에서 mmap/munmap을 자주 반복하면 느려지는 이유입니다.

8-7. Huge Page로 TLB 범위 넓히기

TLB Entry 수를 늘릴 수 없다면 Entry 하나가 담당하는 범위를 키우면 됩니다. L07의 표에서 PMD Entry 하나가 2MB를 담당했습니다. PMD Entry가 PTE Table 대신 2MB짜리 Frame을 직접 가리키게 하면 그것이 Huge Page입니다.

4KB Page 2MB Huge Page
512MB에 필요한 TLB Entry 131,072개 256개
Page Table Walk 4단계 3단계
Page Table 크기 약 1MB 약 4KB
단점 연속된 2MB Physical Memory 필요, 1Byte만 써도 2MB 소비

Linux의 THP(Transparent Huge Page) 는 프로그램 수정 없이(또는 madvise 한 줄로) Kernel이 알아서 Huge Page를 써 주는 기능입니다.

cat /sys/kernel/mm/transparent_hugepage/enabled

always [madvise] never

[madvise]이면 프로그램이 madvise(addr, len, MADV_HUGEPAGE)로 요청한 영역에만 적용됩니다. thp_compare.c는 512MB를 Page 단위로 흩어진 순서로 방문합니다. 4KB와 2MB에서 접근 주소와 순서가 완전히 같으므로 Data Cache의 조건은 같고, 차이는 주소 변환 비용에서 나옵니다.

정리

  • TLB는 VPN → PFN 변환 결과를 기억하는 CPU 안의 작은 Cache입니다. Hit면 Memory 접근 없이 변환이 끝나고, Miss면 Hardware가 Page Table을 4단계로 읽습니다.
  • TLB가 담당하는 범위는 수백 KB ~ 수 MB에 불과합니다. 접근 횟수가 같아도 오가는 Page 수에 따라 성능이 크게 달라집니다.
  • TLB Miss는 Hardware가, Page Fault는 Kernel이 처리합니다. 전혀 다른 사건입니다.
  • Process가 바뀌면 TLB의 내용이 무효가 됩니다(Flush 또는 PCID로 구분). Thread 간 전환은 주소 공간이 같아 이 비용이 없습니다.
  • Huge Page는 TLB Entry 하나의 담당 범위를 4KB에서 2MB로 키웁니다. THP와 madvise(MADV_HUGEPAGE)로 적용할 수 있습니다.

    madvise((void *)p, NPAGES * PAGE, MADV_NOHUGEPAGE);

    for (i = 0; i < NPAGES; i++)            /* 준비: 모든 Page 를 미리 Physical Memory 에 올린다 */
        p[i * PAGE] = 1;

    t0 = now();
    for (r = 0; r < ROUNDS; r++)
        for (i = 0; i < NPAGES; i++)        /* dense: 앞쪽 64 Pages 안에서만 접근 */
            sum += p[i];
    t1 = now();
    for (r = 0; r < ROUNDS; r++)
        for (i = 0; i < NPAGES; i++)        /* sparse: 접근마다 다른 Page */
            sum += p[i * PAGE];
    t2 = now();

Huge Page 가 섞이면 Page 수 비교가 의미 없어지므로 MADV_NOHUGEPAGE 로 막습니다. dense 는 p[i] 로 연속 주소를 읽어 4096번에 한 번만 새 Page 를 만나고(TLB Hit 대부분), sparse 는 p[i * PAGE] 로 접근마다 다른 Page 를 만나 TLB Miss 와 Page Walk 가 일어납니다. 접근 횟수는 같은데 수십 배 차이가 납니다.

✏️ 괄호 넣기 8-2

  1. TLB 가 없다면 4-Level Paging 에서 Memory 접근 한 번에 Page Table 을 번 더 읽어야 한다.
  2. TLB 가 효과적인 이유는 방금 접근한 Page 를 곧 다시 접근하는 때문이다.
  3. 2MB 크기의 Page 를 쓰면 TLB Entry 하나가 덮는 범위가 512배 넓어진다. 이 Page 를 라고 한다.
  4. Context Switch 때 TLB 전체를 비우지 않도록 Entry 에 주소 공간 번호를 붙이는 기능은 이다.

9-1. Page Fault는 언제 일어나는가

MMU가 주소를 변환하다가 그대로 진행할 수 없는 PTE를 만나면 Exception(#PF, 14번)을 일으킵니다.

MMU가 본 것 예
Present = 0 (또는 상위 Table이 아예 없음) malloc 후 처음 접근, 아직 읽어 오지 않은 File Page
쓰기인데 R/W = 0 COW, .rodata에 쓰기
Ring 3인데 U/S = 0 User 프로그램이 Kernel 주소에 접근
실행인데 NX = 1 Stack이나 Heap의 Data를 실행하려는 시도

CPU는 두 가지 정보를 남기고 Kernel의 Page Fault Handler로 들어갑니다(L01의 "Exception" 경로).

  • CR2 Register: Fault를 일으킨 Virtual Address
  • Error Code: 읽기/쓰기, User/Kernel Mode, Present 여부, 명령어 Fetch 여부

중요한 것은 그다음입니다. Kernel이 문제를 해결하고 돌아오면 CPU는 Fault를 일으킨 바로 그 명령을 처음부터 다시 실행합니다. 프로그램은 아무 일도 없었던 것처럼 계속됩니다.

9-2. 처음 건드릴 때마다 한 번씩

fault_count.c는 10,000 Page를 mmap하고, 모든 Page에 두 번씩 씁니다. 구간마다 getrusage로 Fault 횟수를 읽습니다.

./fault_count

Page 수                 : 10000
mmap() 호출             : minor +0
첫 번째 쓰기 (10000 회) : minor +10000  major +0
두 번째 쓰기 (10000 회) : minor +0  major +0
  • mmap() 자체는 Fault를 일으키지 않습니다. VMA만 만들었기 때문입니다(L06).
  • 첫 번째 쓰기에서 정확히 Page 수만큼 Fault가 발생했습니다. Page마다 한 번씩 Kernel에 들어가 Frame을 받아 온 것입니다.
  • 두 번째 쓰기에서는 0입니다. PTE가 이미 있습니다.

10,000번의 Kernel 진입은 공짜가 아닙니다. 큰 Memory를 할당한 직후 첫 번째 순회가 두 번째보다 눈에 띄게 느린 이유이고, Latency가 중요한 프로그램이 시작할 때 Memory를 미리 건드려 두는(pre-fault) 이유입니다. mmap의 MAP_POPULATE Flag가 같은 일을 한 번의 System Call로 해 줍니다.

9-3. Kernel Handler의 판단 흐름

Handler가 하는 일은 한 문장으로 요약됩니다: "이 주소에 대해 VMA(약속)는 뭐라고 하는가?"

#PF 발생 (CR2 = 주소, Error Code)                       arch/x86/mm/fault.c : do_user_addr_fault()
  │
  ├─ 주소를 포함하는 VMA 를 찾는다
  │     ├─ 없음 ─┬─ 바로 위가 [stack] VMA 이고 ulimit 이내 → Stack VMA 를 확장하고 계속
  │     │        └─ 그 외 ────────────────────────────→ SIGSEGV (SEGV_MAPERR)
  │     └─ 있음
  │
  ├─ 접근 종류가 VMA 권한에 맞는가  (쓰기인데 VMA 가 r-- 등)
  │     └─ 아니오 ───────────────────────────────────→ SIGSEGV (SEGV_ACCERR)
  │
  └─ 정당한 접근이다 → handle_mm_fault()                 mm/memory.c
        ├─ Anonymous, 첫 읽기   → Zero Page 를 읽기 전용으로 Mapping              Minor
        ├─ Anonymous, 첫 쓰기   → 새 Frame 할당, 0 으로 채움                       Minor
        ├─ File Mapping        → Page Cache 에 있으면 그것을 Mapping              Minor
        │                        없으면 Disk 에서 읽어 온 뒤 Mapping              Major
        ├─ 쓰기 + PTE R/W=0 + VMA 는 rw-  → COW: 새 Frame 에 복사                  Minor
        └─ Swap 된 Page        → Swap 에서 읽어 옴                                Major
  │
  └─ PTE 갱신 → Exception 에서 복귀 → 같은 명령 재실행

L07에서 "VMA는 약속, PTE는 현재 상태"라고 했습니다. Page Fault Handler는 현재 상태를 약속에 맞게 고치는 곳입니다. 고칠 수 있으면 조용히 고치고, 약속 자체에 없는 접근이면 SIGSEGV를 보냅니다.

9-4. Animation: 네 가지 Page Fault

Scenario를 바꿔 가며 Handler의 판단이 어떻게 갈리는지 비교합니다.

  1. Minor (Anonymous 첫 쓰기): Frame 할당 → 0으로 채움 → PTE 기록 → 명령 재실행.
  2. Major (Cache에 없는 File Page): Disk I/O를 기다리는 동안 Process가 Sleep 상태가 되는 단계를 확인합니다.
  3. COW (fork 후 쓰기): PTE는 있는데(Present=1) R/W=0이어서 발생합니다. VMA 권한과 비교하는 단계에 주목합니다.
  4. Invalid (잘못된 주소): VMA를 찾지 못해 SIGSEGV로 끝납니다.

9-5. 읽기만 하면 Memory가 늘지 않는다: Zero Page

zero_page.c는 256MB를 mmap하고, 먼저 모든 Page를 읽기만 한 뒤, 다음에 씁니다.

./zero_page

mmap(256MB) 직후         RSS    1420 kB
모든 Page 읽기         RSS    1744 kB   minor +65548   (sum=0)
모든 Page 쓰기         RSS  263888 kB   minor +65536
  • 읽기에서 Fault가 65,536번(= 256MB ÷ 4KB) 발생했지만 RSS는 거의 늘지 않았습니다.
  • Kernel은 "어차피 0만 보일 Page"에 Frame을 새로 주지 않습니다. System에 하나뿐인 Zero Page(0으로 채워진 Frame)를 65,536개의 PTE가 읽기 전용으로 함께 가리키게 합니다.
  • 쓰기에서 Fault가 또 65,536번 발생했습니다. 이번에는 R/W=0인 PTE에 쓰려 했기 때문이고, Kernel은 그제서야 Page마다 진짜 Frame을 줍니다. COW와 같은 원리입니다.

calloc으로 큰 Memory를 받아도 RSS가 바로 늘지 않는 이유, Sparse한(대부분 0인) 큰 배열이 생각보다 Memory를 적게 쓰는 이유입니다.

9-6. Minor Fault와 Major Fault

Minor Fault Major Fault
조건 필요한 내용이 이미 Memory에 있거나, 새로 만들면 됨 Disk I/O가 필요함
예 Anonymous 첫 접근, COW, Page Cache에 있는 File Page Page Cache에 없는 File Page, Swap된 Page
비용 수 µs 수백 µs ~ 수십 ms
Process 상태 계속 실행 I/O가 끝날 때까지 Sleep (D state)

major_fault.c는 128MB File을 mmap해 Page마다 1Byte씩 읽습니다.

File은 반드시 Home Directory 아래(현재 lab Directory)에 만드세요. Ubuntu 26.04의 /tmp는 Memory 기반 File System(tmpfs)이어서 Disk I/O가 발생하지 않습니다.

sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
./major_fault
./major_fault

big.dat (128 MB) 생성
3
minor +98   major +421   312.6 ms   (sum=3932160)
minor +145   major +0   1.0 ms   (sum=3932160)

drop_caches는 Kernel이 Memory에 보관 중인 File 내용(Page Cache)을 비웁니다.

  • 첫 번째 실행: File 내용이 Memory에 없습니다. Fault가 나면 Disk에서 읽어 와야 합니다 → Major, 수백 ms.
  • 두 번째 실행: 방금 읽은 내용이 Page Cache에 남아 있습니다. PTE만 연결하면 됩니다 → Minor, 1ms.

같은 프로그램, 같은 File인데 300배 차이입니다. "처음 실행할 때만 느린 프로그램"의 정체입니다.

📌 NOTE
32,768 Page를 읽었는데 Fault 횟수가 수백 번뿐입니다. Kernel은 Fault가 나면 그 Page만이 아니라 주변 Page까지 한꺼번에 처리합니다. Disk에서 읽을 때는 Readahead(연속된 Block을 미리 읽음), 이미 Cache에 있을 때는 Fault-around(주변 16개 Page의 PTE를 함께 채움)입니다. 정확한 횟수는 Kernel Version과 File System에 따라 다릅니다. Page Cache는 Chapter 3의 주제입니다.

9-7. COW Fault 세어 보기

L07에서 PFN으로 확인한 COW를 이번에는 Fault 횟수로 확인합니다. cow_fault.c는 Parent가 10,000 Page를 채운 뒤 fork하고, Child가 전부 읽은 다음 10%만 씁니다.

./cow_fault

[child] 10000 Pages 읽기        : minor +0
[child] 1000 Pages 쓰기         : minor +1000   <- 쓴 Page 만 복사
[parent] p[0] = 'P'  (Child 의 쓰기는 Parent 에 보이지 않는다)
  • 읽기는 Fault가 0입니다. fork가 Page Table을 복사해 주었으므로 PTE가 이미 있습니다.
  • 쓰기는 쓴 Page 수만큼만 Fault가 발생합니다. 40MB 중 4MB만 복사되었습니다.

💡 TIP
Redis가 fork로 Snapshot을 저장하는 방식이 이것입니다. Child는 fork 시점의 Memory를 그대로 보면서 File로 쓰고, Parent는 계속 요청을 처리합니다. Parent가 수정한 Page만 복사되므로 수십 GB의 Data도 순간적으로 Snapshot을 뜰 수 있습니다. 반대로 저장 중에 쓰기가 몰리면 COW로 Memory 사용량이 급증합니다.

9-8. 잘못된 접근: SIGSEGV의 두 종류

Handler가 "약속에 없는 접근"이라고 판단하면 SIGSEGV를 보냅니다. segv_info.c는 SA_SIGINFO Handler로 Kernel이 알려 주는 정보를 출력합니다.

./segv_info null
./segv_info ro

Mapping 이 없는 주소 0x10 에 씁니다
SIGSEGV  si_addr=0x10  si_code=1 (SEGV_MAPERR: 그 주소를 포함하는 VMA 가 없음)

읽기 전용 영역 0x559cb498d130 에 씁니다
SIGSEGV  si_addr=0x559cb498d130  si_code=2 (SEGV_ACCERR: VMA 는 있지만 권한이 없음)
si_code 의미 흔한 원인
SEGV_MAPERR 그 주소를 포함하는 VMA가 없다 NULL Pointer, 해제된 mmap 영역, 쓰레기 Pointer
SEGV_ACCERR VMA는 있지만 권한이 맞지 않다 문자열 Literal 수정, const 변수에 쓰기, RELRO된 GOT에 쓰기

si_addr는 CR2의 값입니다. si_addr가 0x10처럼 작은 값이면 "NULL인 구조체 포인터의 멤버에 접근"(p->field, Offset 0x10)했을 가능성이 높습니다. Core Dump 분석(Chapter 7)에서 가장 먼저 보는 정보입니다.

⚠ WARNING
SIGSEGV Handler에서 그냥 return하면 같은 명령이 다시 실행되어 같은 Fault가 무한히 반복됩니다(9-1의 "명령 재실행"). 그래서 이 예제는 Handler 안에서 _exit합니다. Handler 안에서는 printf가 아니라 write를 쓴 것도 확인하세요(기존 과정의 Reentrant 함수).

page-faults는 Kernel이 세는 Software Event이므로 VirtualBox에서도 동작합니다. 실행 중인 Process는 ps로 봅니다.

   1873   3512      2  5632 bash
관찰 의심할 것
Minor Fault가 매우 많고 시간이 그곳에서 소모됨 큰 Memory를 반복해서 할당/해제 (mmap/munmap 반복). 재사용하거나 pre-fault

시작 직후에만 Major Fault 실행 File과 Library를 Disk에서 읽어 오는 정상 동작

정리

  • Page Fault는 MMU가 유효하지 않은 PTE(Present=0, 권한 위반)를 만났을 때 발생하는 Exception입니다. 주소는 CR2에 남고, 처리 후 같은 명령이 다시 실행됩니다.
  • Handler는 VMA를 찾아 정당한 접근인지 판단합니다. 정당하면 PTE를 고치고, 아니면 SIGSEGV(MAPERR: VMA 없음, ACCERR: 권한 불일치)를 보냅니다.
  • Anonymous Memory의 첫 접근, Zero Page에서 실제 Frame으로의 전환, COW, Stack 확장이 모두 Page Fault로 구현됩니다.
  • Minor Fault는 Disk I/O 없이 끝나고, Major Fault는 Disk에서 읽어 와야 하므로 수백 배 느리며 그동안 Process는 Sleep합니다.
  • getrusage, /usr/bin/time -v, perf stat -e page-faults, ps -o min_flt,maj_flt로 측정합니다.

note.txt에 대한 read가 없습니다. p[0]에 처음 접근하는 순간 일어난 일은 L09 그대로입니다.

p[0] 읽기 → PTE 없음 → Page Fault → VMA 확인: "note.txt 의 Offset 0"
         → Page Cache 에서 그 Page 를 찾는다 (없으면 Disk 에서 읽어 온다)
         → 그 Frame 을 PTE 에 연결 → 명령 재실행 → 'h' 가 읽힌다

핵심은 Page Cache의 Frame을 그대로 연결한다는 점입니다. read()는 Page Cache에서 내 Buffer로 복사하지만, mmap은 복사하지 않습니다.

read() mmap
Data 경로 Disk → Page Cache → 복사 → User Buffer Disk → Page Cache ← PTE가 직접 가리킴
System Call 읽을 때마다 처음 mmap 한 번. 이후는 Memory 접근
비용이 드는 곳 System Call + 복사 Page Fault + TLB Miss

어느 쪽이 빠른지는 접근 Pattern에 따라 다릅니다. 정량 비교는 Chapter 3 L14에서 합니다.

File 크기는 17Byte인데 Mapping은 4KB 단위입니다. p[17]부터 p[4095]까지는 접근해도 오류가 나지 않고 0이 읽힙니다. p[4096]은 VMA 밖이므로 SIGSEGV입니다.

정리

  • mmap은 VMA를 만드는 System Call입니다. 인자가 maps의 각 열과 대응합니다. Process의 주소 공간 전체가 mmap으로 만들어집니다.
  • File Mapping은 Page Fault 때 Page Cache의 Frame을 PTE에 직접 연결합니다. read와 달리 User Buffer로의 복사가 없습니다.
  • MAP_PRIVATE는 쓰는 순간 COW로 복사되어 File이 바뀌지 않습니다. MAP_SHARED는 Page Cache를 직접 수정하므로 다른 Process에 즉시 보이고, Disk 반영은 msync 또는 Kernel의 Writeback이 합니다.
  • MAP_SHARED | MAP_ANONYMOUS는 fork한 Process 간의 가장 간단한 공유 Memory입니다. 동기화는 별도로 필요합니다.
  • Mapping 뒤의 File이 줄어들거나 I/O 오류가 나면 SIGBUS가 발생합니다. 실패는 MAP_FAILED로 검사합니다.

쓰기 가능한 MAP_SHARED Mapping 은 File 을 O_RDWR 로 열어야 합니다. Memory 에 쓰는 것(toupper 결과 대입)이 곧 Page Cache 의 Page 를 바꾸는 것이고, 다른 Process 의 read() 에도 즉시 보입니다. msync(MS_SYNC) 는 Disk 기록까지 기다립니다(Chapter 3 L15 의 fsync 와 같은 역할). MAP_PRIVATE 였다면 쓰는 순간 COW 로 복사되어 File 은 바뀌지 않습니다.
