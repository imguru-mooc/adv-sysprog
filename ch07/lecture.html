Lecture 31

/proc를 이용한 Process 내부 분석

영상 17분

도구를 설치하기 전에, 이미 있는 것부터 봅니다. /proc은 Kernel이 자신의 자료 구조를 Text File처럼 보여 주는 창이고, ps, top, free, lsof가 모두 이것을 읽어서 만들어집니다.

학습 목표

  • "프로그램이 느리다"에서 출발하는 조사 순서를 설명할 수 있다.
  • /proc/PID 아래의 주요 File(status, stat, task, fd, io, maps, smaps_rollup, wchan, stack, limits)을 읽고 해석할 수 있다.
  • 두 번의 Sample 차이로 CPU 사용률과 초당 I/O 횟수를 계산할 수 있다.
  • /proc만 읽어서 동작하는 Process Monitor를 작성할 수 있다(Final Project의 구성 요소).

31-1. 이 Chapter의 지도: 무엇부터 조사하는가

Chapter 6에서 "측정했더니 예상과 달랐다"를 여러 번 겪었습니다. 이 Chapter는 추측 대신 관찰하는 도구들입니다. 도구는 많지만 질문의 순서는 정해져 있습니다.

"프로그램이 느리다 / 이상하다"

   ├─ 1. CPU 를 쓰고 있는가, 기다리고 있는가?                    top, /proc/PID/stat, status        L31

도구 관찰 대상 Overhead 운영 환경
/proc Kernel이 이미 집계해 둔 숫자 거의 없음 언제나 가능
strace System Call 하나하나 매우 큼 (수 배~수십 배) 주의
gdb 변수, Stack, Thread 붙는 동안 정지 주의
perf CPU가 어디에 있는가 (Sampling) 작음 (1~5%) 가능
ftrace Kernel 함수와 Event 설정에 따라 가능
eBPF 원하는 지점에서 원하는 집계 작음 가능

항목 의미 읽는 법

voluntary_ctxt_switches 스스로 CPU를 내놓은 횟수 (Sleep, I/O 대기, Lock 대기) 많으면 기다리는 프로그램
nonvoluntary_ctxt_switches 시간을 다 써서 빼앗긴 횟수 많으면 CPU를 다투는 프로그램

📌 NOTE
/proc/PID/status의 Context Switch 횟수는 그 Thread(여기서는 main)만의 값입니다. Thread별 값은 31-4의 task/TID/status에 있습니다. 반면 VmRSS는 Process 전체의 값입니다(Thread들은 주소 공간을 공유하므로).

31-4. task: Thread별로 보기

for t in /proc/$P/task/*; do
    echo "$(basename $t) $(cat $t/comm) $(awk '{print $3, $14, $15}' $t/stat) $(cat $t/wchan)"
done

566 target S 0 0 hrtimer_nanosleep
568 burner S 148 2 hrtimer_nanosleep
569 logger S 0 1 hrtimer_nanosleep

(열: TID, 이름, 상태, utime, stime, wchan. utime/stime의 단위는 Clock Tick = 1/100초)

  • Thread마다 Directory가 있고 그 안의 구조는 /proc/PID와 같습니다. Linux에서 Thread는 주소 공간을 공유하는 Process이기 때문입니다.
  • comm에 pthread_setname_np로 붙인 이름이 보입니다. Thread에 이름을 붙여 두면 이런 조사가 훨씬 쉬워집니다.
  • CPU를 쓰는 것은 burner뿐입니다(utime 148 Tick = 1.48초). top -H -p $P가 보여 주는 것이 이 값입니다.

stat은 공백으로 구분된 52개의 숫자입니다. 자주 쓰는 것만 기억합니다.

번호 이름 의미
3 state
10, 12 minflt, majflt Page Fault (L09)
14, 15 utime, stime User / Kernel Mode에서 쓴 CPU 시간 (Tick)
20 num_threads
22 starttime 부팅 후 시작 시각
23, 24 vsize, rss
39 processor 마지막으로 실행된 CPU

⚠ WARNING
stat을 Parsing할 때 두 번째 필드 (comm)에 공백이나 괄호가 들어갈 수 있습니다(예: (tmux: server)). 앞에서부터 공백으로 자르면 안 되고, 마지막 )를 찾아 그 뒤부터 읽습니다. procmon.c가 그렇게 합니다.

cat /proc/$P/io

rchar: 4092
wchar: 456
syscr: 8
syscw: 57
read_bytes: 0
write_bytes: 4096
cancelled_write_bytes: 0
항목 의미
rchar / wchar read/write 계열 System Call로 오간 Byte 수. Page Cache Hit도 포함
syscr / syscw read/write 계열 System Call 횟수
read_bytes / write_bytes 실제로 Block Device에 요청된 Byte 수

wchar 456인데 write_bytes 4096입니다. L15에서 배운 대로 write()는 Page Cache에 쓰고, Disk에는 Page 단위(4KB)로 나갑니다. wchar는 큰데 write_bytes가 작다면 Page Cache가 흡수하고 있는 것이고, rchar는 큰데 read_bytes가 0이면 전부 Cache Hit입니다.

wchar / syscw = 8Byte. write 한 번에 평균 8Byte입니다. L11의 "너무 작은 I/O"를 Source 없이 찾아냈습니다.

정리

  • /proc/PID는 Kernel의 자료 구조를 읽는 순간 문자열로 만들어 주는 창입니다. 대상을 건드리지 않고 Overhead가 거의 없습니다.

  • stat은 마지막 ) 뒤부터 Parsing합니다.

Source 를 보지 않고 /proc 만으로 Process 를 관찰하는 procmon 의 두 함수입니다. (src/L31/procmon.c 19~59행)

static int read_stat(int pid, struct sample *s)
{
    char  path[64], buf[1024], *p;
    FILE *fp;

    snprintf(path, sizeof(path), "", pid);
    fp = fopen(path, "r");
    if (fp == NULL)
        return -1;
    if (fgets(buf, sizeof(buf), fp) == NULL) {
        fclose(fp);
        return -1;
    }
    fclose(fp);
    p = (buf, ')');                              /* comm 에 공백이나 ')' 가 있을 수 있으므로 마지막 ')' 뒤부터 */
    if (p == NULL)
        return -1;
    /* (3)state ... (14)utime (15)stime : ')' 뒤의 첫 필드가 3 번 */
    if (sscanf(p + 2, "%c %*d %*d %*d %*d %*d %*u %*u %*u %*u %*u %lu %lu", &s->state, &s->utime, &s->stime) != 3)
        return -1;

Option 효과
-e trace=write,openat 볼 System Call만. 분류도 가능: %file, %network, %process, %memory, %signal, %desc
-T 각 호출에 걸린 시간 <0.000021>

-s 200 문자열 표시 길이(기본 32)

-Z / -z 실패한 / 성공한 호출만

32-4. 오류 주입: inject

"Disk가 가득 찼을 때 내 프로그램은 제대로 동작하는가?"를 Disk를 채우지 않고 시험합니다.

strace -e trace=write -e inject=write:error=ENOSPC:when=3 ./chatty slow 2>&1 | head -n 4

write(3, "record 0\n", 9)               = 9
write(3, "record 1\n", 9)               = 9
write(3, "record 2\n", 9)               = -1 ENOSPC (No space left on device) (INJECTED)
+++ exited with 1 +++

세 번째 write에 strace가 가짜 실패를 주입했고, chatty는 오류 검사를 하고 있으므로 종료 Code 1로 끝났습니다. when=3+(세 번째부터 계속), when=10+5(10번째부터 5번마다), delay_enter=100000(100ms 지연 주입), signal=SIGINT도 가능합니다. 오류 처리 경로는 평소에 실행되지 않으므로 이렇게 강제로 실행해 보지 않으면 검증되지 않은 채로 남습니다.

32-5. strace는 어떻게 동작하는가, 그리고 그 비용

strace는 ptrace() System Call을 씁니다. 한 Process(Tracer)가 다른 Process(Tracee)를 관찰하고 제어하게 해 주는 Kernel 기능입니다.

Tracee: write() 호출 → Kernel 진입
   1. "추적 중" 이므로 Tracee 를 멈추고 Tracer(strace) 를 깨운다            ← Context Switch
   2. strace: ptrace 로 Register 를 읽어 System Call 번호와 인자를 알아내고, Tracee 의 Memory 에서 문자열을 읽는다
   3. strace: "계속해" → Tracee 가 실제 System Call 을 수행                 ← Context Switch
   4. System Call 이 끝나면 다시 Tracee 를 멈추고 strace 를 깨운다           ← Context Switch
   5. strace: return 값을 읽어 한 줄 출력 → "계속해"                        ← Context Switch

System Call 한 번에 Context Switch 4번과 ptrace 호출 여러 번이 듭니다.

time strace -c -o /dev/null ./chatty slow

real	0m1.339s   user	0m0.270s   sys	0m1.067s

0.073초 → 1.339초, 18배 느려졌습니다. System Call이 많은 프로그램일수록 심합니다.

⚠ WARNING
운영 중인 Service에 strace -p를 붙이는 것은 신중해야 합니다. 초당 수만 번의 System Call을 하는 Server는 수십 배 느려져 Timeout과 장애로 이어질 수 있습니다. 붙이더라도 -e trace=로 범위를 좁히고 짧게 끝냅니다. 운영 환경에서 System Call을 관찰하는 데는 Overhead가 훨씬 작은 perf trace나 eBPF(L35)가 맞습니다.

또한 한 Process에는 Tracer가 하나만 붙을 수 있습니다. gdb가 붙어 있으면 strace를 붙일 수 없습니다(/proc/PID/status의 TracerPid, L31). Ubuntu는 기본 설정(kernel.yama.ptrace_scope = 1)에서 자신의 Child가 아닌 Process에 붙으려면 root가 필요합니다.

32-6. ltrace: Library 함수 호출

ltrace는 System Call이 아니라 Shared Library 함수 호출(fprintf, malloc, strlen …)을 보여 줍니다. L04의 PLT에 Breakpoint를 거는 방식입니다.

ltrace -c ./chatty fast

% time     seconds  usecs/call     calls      function
------ ----------- ----------- --------- --------------------

  0.00    0.000367         367         1 fclose
  0.00    0.000133          66         2 strcmp

fprintf가 20만 번 호출되었다는 것은 알 수 있지만 0.014초짜리 프로그램이 12.8초 걸렸습니다(약 900배). ltrace는 호출마다 Breakpoint Trap을 거치기 때문입니다. 호출 횟수가 적은 프로그램에서 "어떤 Library 함수를 어떤 인자로 부르는가"를 확인하는 용도로만 씁니다. 최근 배포판의 Binary(-z now, PIE)에서는 동작하지 않는 경우도 있습니다. 같은 일은 L35의 uprobe가 훨씬 가볍게 합니다.

32-7. Core Dump: 죽은 프로그램 부검

33-8. Hardware Counter: 왜 느린가

"어느 함수가 느린가"를 찾았다면 다음은 "왜 느린가"입니다. rowcol.c는 64MB 배열을 행 우선과 열 우선으로 더합니다. 계산량은 완전히 같습니다.

./rowcol row
./rowcol col

행(row) 우선: sum = 282578800082944, 8.6 ms
열(col) 우선: sum = 282578800082944, 143.6 ms

17배 차이입니다. perf record로 보면 두 경우 모두 "main이 100%"일 뿐입니다. 이유는 CPU 안의 PMU(Performance Monitoring Unit)가 세는 Hardware Counter가 알려 줍니다. Native Linux에서 실행한 결과입니다.

perf stat -e cycles,instructions,cache-references,cache-misses ./rowcol col

       512,304,118      cycles
       203,551,902      instructions              #    0.40  insn per cycle
        18,204,331      cache-references
        16,911,204      cache-misses              #   92.90 % of all cache refs
row col
instructions 거의 같다 거의 같다
IPC (insn per cycle) 약 3.1 0.40
cache-misses 약 1% 93%

실행한 명령어 수는 같은데 Cycle을 8배 썼습니다. CPU가 Memory를 기다리며 놀고 있었다는 뜻입니다. 열 우선은 16KB씩 건너뛰며 접근하므로 매번 Cache Miss입니다(L20의 Cache Line, L08의 TLB와 같은 이야기).

자주 쓰는 Event 알려 주는 것
cycles, instructions → IPC 1 미만이면 Memory 또는 분기 예측에 막혀 있다
cache-misses, LLC-load-misses Memory 접근 Pattern
branch-misses 예측하기 어려운 분기
dTLB-load-misses TLB (L08)
page-faults, context-switches, cpu-migrations Software Event. VM에서도 동작

❗ IMPORTANT
VirtualBox에서는 Hardware Counter가 <not supported>입니다. perf record는 cpu-clock(Software Timer)으로 자동 전환되어 Sampling은 정상 동작하지만, IPC와 Cache Miss는 볼 수 없습니다. 이 Step의 perf stat -e 출력은 Native Linux의 예시입니다. (KVM, VMware, 최근의 Cloud Instance 일부는 vPMU를 지원합니다.)

33-9. perf가 보지 못하는 것: Off-CPU

offcpu.c는 100번의 Loop에서 계산하고, 외부 응답을 기다리고(usleep 20ms), Record를 저장합니다(write + fsync).

time ./offcpu
perf stat ./offcpu 2>&1 | grep -E "task-clock|elapsed"

real	0m2.101s   user	0m0.028s   sys	0m0.014s

             41.60 msec task-clock                       #    0.020 CPUs utilized
       2.094298391 seconds time elapsed

2.1초 걸렸는데 CPU는 0.04초(2%)만 썼습니다. 이 프로그램에 perf record를 쓰면:

perf record ./offcpu; perf report --stdio | head -n 8

    65.78%  offcpu   offcpu                [.] compute
     9.09%  offcpu   [kernel.kallsyms]     [k] iowrite16
     7.49%  offcpu   [kernel.kallsyms]     [k] finish_task_switch.isra.0

"compute가 66%"라고 나옵니다. 틀린 말은 아니지만 0.04초의 66% 입니다. 이것을 보고 compute를 최적화해 봐야 2.1초는 그대로입니다. perf의 Sampling은 CPU 위에 있을 때만 찍힙니다. 자고 있는 98%의 시간은 보이지 않습니다.

L31의 첫 질문으로 돌아갑니다. "기다리는" 프로그램에는 다른 도구입니다.

strace -c -w ./offcpu 2>&1 | head -n 6

% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 97.90    2.015514       20155       100           clock_nanosleep
  2.01    0.041411         414       100           fsync
  0.07    0.001387          13       101           write

-w(벽시계 시간)로 보니 98%가 clock_nanosleep, 즉 외부 응답 대기입니다. 그 다음이 fsync. 최적화할 곳은 compute가 아니라 기다림을 줄이는 것(병렬 요청, 비동기 I/O, Group Commit)입니다.

증상 의미 도구
CPUs utilized ≈ 1.0 (× Thread 수) On-CPU perf record
CPUs utilized ≪ 1, voluntary_ctxt_switches 많음 Off-CPU: Sleep, I/O, Lock 대기 strace -c -w, /proc/PID/wchan, perf trace, Off-CPU Profiling(eBPF의 offcputime, L35)
sys 시간이 크다 Kernel에서 시간 소모 strace -c, perf record의 [k] 항목 
make clean

정리

  • perf stat: Event를 센다. CPUs utilized로 On-CPU인지 먼저 확인합니다.
  • perf record -g → perf report: 초당 수천 번 IP와 Stack을 Sampling. Sample 수의 비율 = 시간의 비율. Overhead 1~5%, Source 수정 불필요, 실행 중인 Process에도 가능.
  • Self(자기 코드) vs Children(호출한 것 포함). Library 함수가 뜨겁다면 Call Graph로 누가 불렀는지를 봅니다.
  • 정확한 Call Graph에는 -fno-omit-frame-pointer, 측정은 -O2 로.
  • perf annotate는 명령어 수준(Skid 주의). Flame Graph: 가로 폭 = 시간, 윗면이 넓은 상자 = 최적화 대상, 가로는 시간 순이 아님.
  • Hardware Counter(IPC, cache-misses)는 "왜 느린가"를 알려 주지만 VirtualBox에서는 지원되지 않습니다.
  • perf는 Off-CPU 시간을 보지 못합니다. 기다리는 프로그램에는 strace -c -w, wchan, eBPF.

__attribute__((noinline)) static unsigned long process_batch(int round)

    char          out[2048];

영상 17분

Lecture 35

eBPF와 bpftrace

영상 19분

eBPF는 검증된 작은 프로그램을 Kernel 안에서 실행하는 기술입니다. 관측 지점에 내 코드를 붙여, 필요한 것만 골라 Kernel 안에서 집계하고 결과만 가져옵니다. bpftrace는 그것을 한 줄로 쓰게 해 주는 언어입니다.

학습 목표

  • eBPF 프로그램이 Load되고 실행되는 과정(Compile → Verifier → JIT → Attach → Map)을 설명할 수 있다.
  • Probe의 종류(tracepoint, kprobe, uprobe, profile, interval)를 구분할 수 있다.
  • bpftrace로 System Call 집계, File 열기 추적, Histogram, 함수 실행 시간 측정을 할 수 있다.
  • strace, perf, ftrace, eBPF의 용도와 비용을 비교해 상황에 맞는 도구를 고를 수 있다.

35-1. 왜 또 다른 도구인가

L32에서 chatty slow의 write 20만 번을 strace로 세는 데 18배의 시간이 들었습니다. 알고 싶었던 것은 "write가 몇 번, 어떤 크기로"라는 숫자 몇 개였는데, strace는 20만 건을 하나하나 멈춰 세우고 User Space로 옮겼습니다.

사건마다 하는 일 집계하는 곳
strace Process를 멈춤 → Tracer로 Context Switch × 4 User Space (strace)
ftrace Ring Buffer에 기록 User Space (사람이 읽음)
eBPF Kernel 안에서 작은 함수 하나 실행(수십~수백 ns) Kernel 안 (Map)

eBPF는 관측 지점에서 "Counter를 1 올린다", "Histogram의 해당 칸을 올린다" 같은 일을 그 자리에서 하고, User Space에는 최종 결과만 넘깁니다.

                                     ▼
                               ③ Verifier : 안전한가?  (무한 Loop 없음, 잘못된 Memory 접근 없음, 반드시 종료)
                                     │ 통과하지 못하면 Load 거부
                                     ▼

                                     │

                                     │       tracepoint / kprobe / uprobe / perf event / …
      Event 발생 ──→ eBPF Program 실행 ──→ ⑥ BPF Map (Hash, Array, Histogram, Ring Buffer)

                                                     ▼
                                       ⑦ bpftrace 가 Map 을 읽어 출력
구성 요소 역할
eBPF Program 제한된 명령어 집합으로 된 작은 함수. Event가 발생할 때마다 Kernel 안에서 실행된다
Verifier Load 전에 모든 실행 경로를 정적 분석. Kernel Module과의 결정적 차이: Module은 Bug 하나로 Kernel 전체를 죽이지만 eBPF는 검증을 통과해야만 실행된다
JIT Bytecode → 기계어. Interpreter가 아니라 Native 속도
Map Kernel 안의 Key-Value 저장소. Program 실행 사이에 상태를 유지하고, User Space와 Data를 주고받는 통로
Helper 함수 eBPF Program이 부를 수 있는 Kernel 함수의 제한된 목록 (현재 시각, 현재 PID, Map 조회, 문자열 복사 …)

35-7. uprobe: 내 프로그램의 함수

uprobe는 User Space 프로그램의 함수 진입(과 uretprobe로 복귀)에 붙습니다. Source를 고치지 않고, 다시 Compile하지 않고. funclat.bt

{

35-9. Verifier: 왜 안전한가

Kernel 안에서 임의의 코드를 실행한다는 것은 위험한 일입니다. Verifier가 Load 전에 다음을 증명하지 못하면 거부합니다.

검사 이유
반드시 종료한다 (무한 Loop 없음, Loop는 상한이 증명되어야 함) Kernel이 멈추면 안 된다
모든 Memory 접근이 범위 안 Kernel Memory를 망가뜨리거나 유출하면 안 된다
Pointer를 쓰기 전에 NULL 검사
Kernel Memory는 Helper 함수로만 읽는다 (bpf_probe_read_*). 실패해도 Fault가 아니라 오류 Code bpftrace의 str()이 이것을 호출
초기화되지 않은 값을 읽지 않는다
Program 크기와 Stack(512Byte) 제한
허용된 Helper 함수만 호출

bpftrace는 Verifier를 통과하는 코드를 생성해 주므로 평소에는 의식할 일이 없습니다. C로 직접 작성하면(libbpf) Verifier의 거부 Message와 씨름하게 됩니다.

정리

  • eBPF: 검증된 작은 프로그램을 Kernel 안의 관측 지점에서 실행합니다. Verifier(안전성 증명) → JIT(Native 속도) → Attach → Map(Kernel 안에서 집계, User Space와 공유).
  • strace가 사건마다 Process를 멈추고 User Space로 옮기는 것과 달리, eBPF는 그 자리에서 집계하고 결과만 넘깁니다. 그래서 운영 환경에 쓸 수 있습니다.
  • bpftrace: probe /filter/ { action }. Map(@), count(), hist(), 진입과 복귀를 @start[tid]로 잇는 Pattern.
  • Probe: tracepoint(안정적, 먼저 찾을 것), kprobe(어디든, Version 의존), uprobe(내 프로그램과 Library, Source 수정 없이), profile(Sampling), interval.
  • uprobe는 perf가 모르는 호출 횟수와 호출당 시간을 알려 주지만 호출마다 수 µs가 듭니다.
  • 조사는 /proc → (On-CPU면) perf / (Off-CPU면) strace -w·wchan → 필요하면 ftrace·eBPF 순서로 좁혀 갑니다.
