Lecture 21

Blocking과 Non-Blocking I/O

영상 16분

read()는 Data가 올 때까지 잠듭니다. 입력이 하나일 때는 편리하지만 둘 이상이면 문제가 됩니다. 이 Chapter는 그 문제를 푸는 과정입니다.

학습 목표

  • Blocking I/O에서 Process가 잠들고 깨어나는 과정을 Wait Queue로 설명할 수 있다.
  • O_NONBLOCK을 설정하고 EAGAIN을 올바르게 처리할 수 있다.
  • Busy Polling이 왜 나쁜지 CPU 시간으로 확인할 수 있다.
  • Blocking I/O로는 여러 입력을 동시에 기다릴 수 없음을 재현하고, 가능한 해법들을 비교할 수 있다.

21-2. Blocking read: 잠든다

block_read.c에서 Child는 2초 뒤에 Pipe에 쓰고, Parent는 바로 read()합니다.

./block_read

read() 호출... (ps 로 보면 이 Process 는 S 상태)
read() = 5, 2.00 초 동안 Block 되었습니다

기다리는 2초 동안 다른 Terminal에서 상태를 봅니다.

./block_read & sleep 0.5; ps -o pid,stat,wchan:20,comm -C block_read; wait

    PID STAT WCHAN                COMMAND
   2412 S    pipe_read            block_read
   2413 S    hrtimer_nanosleep    block_read

STAT의 S는 Interruptible Sleep, WCHAN은 Kernel의 어느 함수에서 잠들어 있는가입니다. Parent는 pipe_read에서, Child는 sleep의 hrtimer_nanosleep에서 자고 있습니다. 둘 다 CPU를 전혀 쓰지 않습니다.

Blocking의 장점은 분명합니다. 코드가 단순하고(read가 return하면 Data가 있다), 기다리는 동안 CPU를 쓰지 않습니다.

21-3. 잠든다는 것의 실체: Wait Queue

Reader: read(pfd[0])                                   fs/pipe.c : pipe_read()
  1. Pipe Buffer 가 비어 있는가? → 비어 있다
  2. 자신을 이 Pipe 의 Wait Queue(pipe->rd_wait)에 등록한다
  3. 상태를 TASK_INTERRUPTIBLE 로 바꾸고 schedule() → 다른 Process 가 CPU 를 쓴다

Writer: write(pfd[1], "hello", 5)                      pipe_write()
  4. Buffer 에 Data 를 넣는다
  5. wake_up(&pipe->rd_wait) → Wait Queue 에 있던 Reader 를 Runnable 로 만든다

Reader: (Scheduler 가 다시 실행시켜 줌)
  6. schedule() 에서 return → 1 번으로 돌아가 다시 확인 → Data 가 있다 → 복사하고 return

L19의 futex와 같은 구조입니다. "조건이 안 되면 Wait Queue에 자신을 걸고 잔다. 조건을 만든 쪽이 깨운다." Kernel 안의 모든 Blocking이 이 Pattern입니다.

이 Wait Queue는 L12에서 본 file_operations의 .poll 칸과 연결되어 있습니다. "이 fd가 지금 읽을 수 있는 상태인가? 아니라면 나를 어느 Wait Queue에 걸어야 하는가?"를 묻는 함수입니다. select, poll, epoll은 모두 이 .poll을 통해 동작합니다(L22, L23).

21-4. O_NONBLOCK과 EAGAIN

O_NONBLOCK은 L11에서 본 struct file의 Flag입니다. 설정하면 "조건이 안 되면 자지 말고 즉시 돌아와라"가 됩니다.

flags = fcntl(fd, F_GETFL);                 /* 기존 Flag 를 읽어서 */
fcntl(fd, F_SETFL, flags | O_NONBLOCK);     /* O_NONBLOCK 을 더한다. 덮어쓰지 않는다 */

만들 때부터 지정할 수도 있습니다: open(path, O_RDONLY | O_NONBLOCK), pipe2(pfd, O_NONBLOCK), eventfd(0, EFD_NONBLOCK).

nonblock_read.c

./nonblock_read

첫 read() = -1, errno = 11 (Resource temporarily unavailable)
read() 를 12574142 번 호출한 끝에 5 Byte 를 읽었습니다
그동안 사용한 CPU 시간: user 0.72 초 + system 1.27 초
read()의 return Blocking Non-blocking
Data 있음 n > 0 n > 0
Data 없음, Writer는 살아 있음 잠든다 -1, errno = EAGAIN (= EWOULDBLOCK)
Data 없음, Writer가 모두 닫음 0 (EOF) 0 (EOF)

EAGAIN은 오류가 아니라 "지금은 없다. 나중에 다시 해라" 입니다. -1이라고 해서 perror 후 종료하면 안 됩니다.

📌 NOTE
O_NONBLOCK은 일반 File에는 효과가 없습니다. Disk의 File은 "언제나 읽을 수 있는 상태"로 취급되며, Page Cache Miss로 Disk를 기다리는 것은 Non-blocking의 대상이 아닙니다(L11). File I/O를 정말로 비동기로 하려면 Chapter 6의 io_uring이 필요합니다.

21-5. Busy Polling의 비용

위 결과를 다시 보세요. 2초 동안 read()를 1,250만 번 호출했고 CPU를 2초(user 0.72 + system 1.27) 썼습니다. 기다린 2초 내내 CPU 하나를 100% 사용한 것입니다.

./nonblock_read & sleep 1; top -b -n 1 -p $! | tail -n 1; wait

   2431 user      20   0    2680   1024    936 R  99.9   0.0   0:01.00 nonblock_read

Blocking에서는 같은 2초 동안 CPU 시간이 0이었습니다.

절충안 문제
Loop 안에 usleep(10000) CPU는 줄지만 반응이 최대 10ms 늦다. 짧게 하면 CPU 낭비, 길게 하면 지연

Non-blocking은 그 자체로는 해법이 아닙니다. "언제 다시 시도하면 되는지"를 알려 주는 장치와 짝이 되어야 합니다.

21-6. 쓰기에도 Blocking이 있다

pipe_full.c는 아무도 읽지 않는 Pipe에 계속 씁니다.

./pipe_full

write 가 멈춘 시점: 누적 65536 Byte, errno = 11 (Resource temporarily unavailable)
F_GETPIPE_SZ = 65536
Blocking Mode 였다면 이 지점에서 write() 가 영원히 잠들었을 것입니다.

Pipe의 Buffer는 기본 64KB입니다. 가득 차면 Blocking write는 Reader가 읽어 줄 때까지 잠들고, Non-blocking write는 EAGAIN입니다. 기존 과정에서 "Pipe의 양쪽을 한 Process가 다 쓰면 Deadlock이 날 수 있다"고 한 이유입니다.

읽기 가능(EPOLLIN)뿐 아니라 쓰기 가능(EPOLLOUT) 도 기다려야 할 Event인 이유이기도 합니다.

21-9. 해법의 후보들

방법 내용 문제
fd마다 Thread (또는 Process) 각 Thread가 자기 fd에서 Blocking read 단순하고 수십 개까지는 좋다. 수천 개면 Stack Memory(Thread당 8MB 예약), Context Switch, Lock Contention (L20)
Non-blocking + Busy Polling 모든 fd를 돌아가며 시도 CPU 100% (21-5)
Signal-driven I/O (SIGIO) 준비되면 Signal Signal Handler의 제약, 어느 fd인지 알기 어려움. 거의 쓰지 않음
I/O Multiplexing "이 fd들 중 하나라도 준비되면 깨워 줘"를 한 번의 System Call로 select → poll → epoll로 발전 (L22~L24)
비동기 I/O 요청만 하고 완료 통지를 받음 Chapter 6의 io_uring

I/O Multiplexing의 핵심은 기다리는 곳을 한 군데로 모으는 것입니다. 하나의 Thread가 Wait Queue 여러 개에 동시에 자신을 걸어 두고, 어느 하나라도 깨우면 일어납니다.

정리

  • Blocking read는 Data가 없으면 그 fd의 Wait Queue에 자신을 걸고 잠듭니다. Writer가 wake_up으로 깨웁니다. CPU를 쓰지 않지만 한 번에 하나만 기다릴 수 있습니다.
  • O_NONBLOCK은 struct file의 Flag입니다. 조건이 안 되면 자지 않고 EAGAIN 으로 즉시 return합니다. 오류가 아닙니다. 일반 File에는 효과가 없습니다.
  • Non-blocking만으로 기다리면 Busy Polling이 되어 CPU를 100% 씁니다.
  • 쓰기도 Block됩니다(Pipe Buffer 64KB). 읽기 가능과 쓰기 가능 모두 기다릴 Event입니다.
  • 해법은 I/O Multiplexing: 여러 fd의 Wait Queue에 동시에 걸어 두고 한 곳에서 기다리는 것.

select와 poll 내부 구조

여러 fd를 한 번에 기다리는 첫 번째 방법입니다. 동작은 단순합니다. 호출할 때마다 목록 전체를 Kernel에 넘기고, Kernel은 전부 검사합니다. 그 단순함이 곧 한계입니다.

22-4. Kernel 안에서 일어나는 일

poll(pfds, N, timeout)                                          fs/select.c : do_sys_poll()
  1. pfds 배열 전체(N × 8 Byte)를 User → Kernel 로 복사
  2. N 개의 fd 를 하나씩 순회:
        file->f_op->poll(file, wait)    ─ "지금 준비됐는가?" 를 묻고
                                        ─ 동시에 이 Process 를 그 fd 의 Wait Queue 에 등록한다   (L21)
  3. 준비된 것이 하나도 없으면 Sleep
  4. 어느 fd 의 Wait Queue 가 깨워 주면 (누가 깨웠는지는 모른다)
        → 2 번의 순회를 처음부터 다시 한다
  5. N 개의 Wait Queue 에서 자신을 모두 제거
  6. revents 를 채운 배열 전체를 Kernel → User 로 복사
(User) 7. N 개를 순회하며 revents != 0 인 것을 찾는다

Event가 하나 발생할 때마다 드는 비용입니다.

작업 횟수
배열 복사 (User ↔ Kernel) 2 × N
f_op->poll 호출 N (잠들었다 깨면 2N)
Wait Queue 등록과 해제 N + N
User의 결과 검색 N

Kernel은 호출 사이에 아무것도 기억하지 않습니다(Stateless). 그래서 "어제도 넘겼던 그 목록"을 매번 다시 받고, 다시 검사하고, 다시 Wait Queue에 걸었다가 풉니다.

영상 18분

epoll은 관심 목록을 Kernel 안에 보관합니다. 등록은 한 번, 기다릴 때는 준비된 것만 돌려받습니다. 비용이 감시하는 fd 수가 아니라 활동하는 fd 수에 비례합니다.

  • poll과 epoll의 호출 비용을 N에 따라 측정하고 차이의 원인을 설명할 수 있다.
  • epoll_event.data의 용도와 /proc/PID/fdinfo로 epoll Instance를 들여다보는 방법을 안다.
  • epoll 사용 시의 주의점(close와 dup, 일반 File 불가)을 설명할 수 있다.

23-2. 세 개의 System Call

System Call 역할 호출 빈도

poll이 한 System Call에 섞어 놓았던 "무엇을 감시할지 알려 주기" 와 "기다리기" 를 분리한 것이 설계의 핵심입니다.

23-3. Kernel 안의 구조: Interest List와 Ready List

epfd ──→ struct eventpoll                                          fs/eventpoll.c
           ├─ rbr    : Interest List   (Red-Black Tree. Key = fd)      ← epoll_ctl 이 수정
           │            epitem(fd 3)   epitem(fd 4)   epitem(fd 7) …
           ├─ rdllist: Ready List      (Linked List)                   ← Event 가 발생하면 Callback 이 추가
           │            epitem(fd 4)
           └─ wq     : epoll_wait 로 잠든 Thread 의 Wait Queue

epoll_ctl(ADD, fd) 가 하는 일:

1. epitem 을 만들어 Interest List(Tree)에 넣는다                              O(log N)
2. file->f_op->poll() 을 한 번 호출해 그 fd 의 Wait Queue 에 Callback 을 "영구히" 걸어 둔다
      Callback = ep_poll_callback
3. 지금 이미 준비된 상태면 바로 Ready List 에 넣는다

Event가 발생하면 (예: 누군가 Pipe에 write):

pipe_write() → wake_up(&pipe->rd_wait)
   → Wait Queue 에 걸려 있던 ep_poll_callback(epitem) 실행
        1. 이 epitem 을 Ready List 에 추가                                     O(1)
        2. epoll_wait 에서 자고 있는 Thread 가 있으면 깨운다

epoll_wait 가 하는 일:

1. Ready List 가 비어 있으면 잠든다
2. Ready List 의 항목을 꺼내 events[] 에 복사해 준다                           O(준비된 수)
      (Level Trigger 에서는 f_op->poll 로 상태를 한 번 더 확인한다. L24)

L22의 poll과 비교합니다.

poll epoll
관심 목록의 위치 User의 배열. 매번 Kernel로 복사 Kernel 안 (Interest List)
Wait Queue 등록 호출마다 N개 등록, N개 해제 epoll_ctl(ADD) 때 한 번. 계속 걸려 있음
누가 준비됐는지 아는 방법 깨어난 뒤 N개를 다시 검사 Event를 일으킨 쪽이 Callback으로 직접 Ready List에 추가
결과 N개 배열에 표시. User가 검색 준비된 것만 돌려줌
호출당 비용 O(N) O(준비된 수)

"전부에게 물어보기"에서 "일이 생기면 알려 주기" 로 바뀐 것입니다.

주의점 내용

정리

  • epoll은 "알려 주기"(epoll_ctl)와 "기다리기"(epoll_wait)를 분리하고 관심 목록을 Kernel 안에 둡니다.
  • Interest List(Red-Black Tree): 감시 중인 fd 전체. Ready List(Linked List): 지금 준비된 fd.
  • epoll_ctl(ADD) 때 각 fd의 Wait Queue에 Callback을 한 번 걸어 둡니다. Event가 발생하면 그 Callback이 Ready List에 추가하고 잠든 Thread를 깨웁니다.
  • epoll_wait는 Ready List만 봅니다. 비용은 O(준비된 수). N = 10,000에서 poll의 1,600배.
  • data는 그대로 돌려받는 8Byte. 실전에서는 data.ptr에 연결별 구조체를 넣습니다.
  • 일반 File은 등록 불가, close 전에 EPOLL_CTL_DEL, Linux 전용.

Lecture 24

Level Trigger와 Edge Trigger

영상 16분

Level Trigger는 "읽을 것이 있는 동안 계속" 알려 주고, Edge Trigger는 "읽을 것이 새로 생긴 순간 한 번" 알려 줍니다. Edge Trigger에서 Data를 남겨 두면 그 Data는 다시 통지되지 않습니다.

학습 목표

  • Level Trigger와 Edge Trigger의 통지 조건을 설명하고 같은 상황에서의 차이를 재현할 수 있다.
  • Edge Trigger에서 Data를 끝까지 읽어야 하는 이유를 Ready List의 동작으로 설명할 수 있다.
  • Edge Trigger의 올바른 사용 Pattern(Non-blocking + EAGAIN까지 반복)을 작성할 수 있다.
  • 두 방식의 장단점과 EPOLLONESHOT의 용도를 설명할 수 있다.

24-3. Kernel에서의 차이: Ready List에 다시 넣는가

L23에서 Event가 발생하면 Callback이 epitem을 Ready List에 넣는다고 했습니다. 거기까지는 LT와 ET가 같습니다. 차이는 epoll_wait가 그 epitem을 꺼낸 뒤입니다.

epoll_wait: Ready List 에서 epitem 을 꺼낸다                           fs/eventpoll.c : ep_send_events()
   ├─ f_op->poll() 로 지금 상태를 확인. 준비 안 됨 → 버린다
   ├─ 준비됨 → events[] 에 복사
   │
   ├─ Level Trigger: 그 epitem 을 Ready List 에 다시 넣는다
   │       → 다음 epoll_wait 에서 또 꺼내지고, 또 상태를 확인받는다
   │       → Data 를 다 읽어서 "준비 안 됨" 이 되면 그때 버려진다
   │
   └─ Edge Trigger : 다시 넣지 않는다
           → 다음에 Ready List 에 들어오는 것은 Callback 이 다시 불릴 때뿐
           → Callback 은 Writer 가 wake_up 할 때, 즉 "새 Data 가 도착할 때" 불린다

ET에서 남은 8Byte가 통지되지 않는 이유입니다. Kernel이 잊은 것이 아니라 다시 알려 줄 계기가 없는 것입니다.

LT가 epoll_wait 때마다 f_op->poll을 한 번 더 부르는 것도 보입니다. ET가 조금 더 가벼운 이유입니다.

24-5. Edge는 "새 Data의 도착"이다

et_rearm.c는 ET로 등록한 Pipe에 단계별로 조작을 가하고 epoll_wait(Timeout 0.3초)의 결과를 봅니다.

./et_rearm

1. 비어 있음                       epoll_wait = 0   (Pipe 에  0 Byte)
2. write 11 Byte  (없음 → 있음)    epoll_wait = 1   (Pipe 에 11 Byte)
3. 3 Byte 만 읽음  (변화 없음)     epoll_wait = 0   (Pipe 에  8 Byte)
4. write 1 Byte   (새 Data 도착)   epoll_wait = 1   (Pipe 에  9 Byte)
5. 아무 일도 없음                  epoll_wait = 0   (Pipe 에  9 Byte)

4번을 보세요. Pipe는 이미 "비어 있지 않은" 상태였는데(8Byte) 1Byte가 더 오자 Event가 발생했습니다. epoll의 Edge는 엄밀히 "없음 → 있음"의 전환이 아니라 "Writer가 wake_up을 부를 때마다" 입니다.

이것이 ET Bug를 찾기 어렵게 만듭니다. Data가 계속 들어오는 동안에는 남은 Data가 다음 Event 때 함께 읽혀서 문제가 드러나지 않습니다. 마지막 Message를 덜 읽었을 때만 멈춥니다. Test에서는 잘 되다가 운영에서 가끔 멈추는 이유입니다.

24-6. ET의 올바른 Pattern: EAGAIN까지 읽는다

규칙은 두 가지이고 반드시 함께 씁니다.

  1. fd를 O_NONBLOCK 으로 만든다.
  2. Event를 받으면 EAGAIN이 나올 때까지 반복해서 읽는다(쓴다).

et_drain.c

for (;;) {
    got = read(fd, buf, sizeof(buf));
    if (got > 0) {
        /* 처리 */
    } else if (got < 0 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
        break;                          /* 다 읽었다. epoll_wait 로 돌아간다 */
    } else {
        /* 0: EOF, 그 외: 오류 → close */
        break;
    }
}

epoll_wait #2: Timeout — 남은 Data 가 없으므로 정상

EAGAIN을 받았다는 것은 "Buffer가 비었음을 Kernel이 확인해 주었다"는 뜻입니다. 그 뒤에 도착하는 Data는 반드시 새 Edge를 만듭니다.

⚠ WARNING
O_NONBLOCK 없이 이 Loop를 돌리면 마지막 read에서 영원히 Block됩니다. Event Loop 전체가 그 fd 하나 때문에 멈춥니다. "ET = Non-blocking + EAGAIN까지"는 떼어 놓을 수 없는 한 쌍입니다.

ET에서 주의할 점 내용
Starvation 한 fd에 Data가 끊임없이 들어오면 EAGAIN이 나오지 않아 다른 fd를 처리하지 못한다. 한 번에 읽는 양에 상한을 두고, 남았으면 직접 "아직 처리할 것 있음" 목록에 넣어 다음 차례에 이어서 읽는다
쓰기(EPOLLOUT) write가 EAGAIN을 return한 뒤에야 EPOLLOUT Edge를 기다릴 의미가 있다
Short Read ≠ 비었음 요청보다 적게 읽혔다고 Buffer가 비었다고 가정하지 않는다. Stream에서는 대체로 맞지만 EAGAIN까지 확인하는 것이 안전

24-7. 왜 굳이 ET를 쓰는가

Level Trigger Edge Trigger
안전성 덜 읽어도 다시 알려 준다. 실수에 관대 덜 읽으면 멈춘다
epoll_wait 횟수 Data가 남아 있으면 즉시 또 return. 조금씩 처리하면 호출이 많아진다 Event당 한 번
Kernel 비용 매번 Ready List에 되넣고 f_op->poll 재확인 없음
EPOLLOUT Socket/Pipe는 대부분의 시간에 "쓸 수 있는 상태"이므로, LT로 EPOLLOUT을 걸어 두면 epoll_wait가 쉬지 않고 return한다(Busy Loop). 쓸 것이 있을 때만 EPOLL_CTL_MOD로 켜고 꺼야 한다 상태가 바뀔 때만 통지되므로 걸어 둔 채로 둘 수 있다
Multi-Thread 여러 Thread가 같은 epfd를 기다리면 같은 Event에 여러 Thread가 깨어날 수 있다 한 번만 통지되므로 중복이 적다. 확실히 하려면 EPOLLONESHOT
쓰는 곳 libevent 기본, Redis, 대부분의 Application nginx, Envoy, Go Runtime(netpoller), Rust의 tokio/mio

EPOLLONESHOT: 한 번 통지한 뒤 그 fd를 Interest List에 둔 채 비활성화합니다. 처리를 마친 Thread가 EPOLL_CTL_MOD로 다시 켭니다. Worker Thread Pool에서 "한 연결은 한 번에 한 Thread만 처리한다"를 보장하는 표준적인 방법입니다.

24-8. 선택 기준

  1. 기본은 Level Trigger입니다. 실수해도 멈추지 않고, 성능 차이는 대부분의 프로그램에서 측정되지 않습니다.
  2. ET는 Event 수가 매우 많고 EPOLLOUT을 자주 다루는 고성능 Server, 또는 Runtime/Library를 만들 때 선택합니다.
  3. ET를 쓴다면 O_NONBLOCK + EAGAIN까지를 예외 없이 지킵니다.
  4. L25의 eventfd, timerfd, signalfd는 read 한 번으로 상태가 완전히 소진되므로 LT로 충분합니다.

정리

  • Level Trigger(기본): fd가 준비된 동안 계속 통지. Edge Trigger(EPOLLET): 새 Event가 도착한 순간에만 통지.
  • Kernel에서의 차이는 epoll_wait가 epitem을 꺼낸 뒤 Ready List에 다시 넣는가입니다. ET는 넣지 않으므로 다음 통지는 Writer의 다음 wake_up 때입니다.
  • ET에서 Data를 남기면 그 Data는 다시 통지되지 않습니다. 마지막 Message에서만 드러나므로 찾기 어려운 Bug가 됩니다.
  • ET의 규칙: O_NONBLOCK + EAGAIN이 나올 때까지 반복.
  • ET는 epoll_wait 횟수가 적고 EPOLLOUT을 걸어 둘 수 있습니다. LT는 안전합니다. 기본은 LT.
  • EPOLLONESHOT은 Multi-Thread에서 한 fd를 한 Thread만 처리하게 합니다.

25-1. 기다려야 하는 것이 fd가 아닐 때

epoll_wait에서 자고 있는 Thread를 깨울 수 있는 것은 fd의 Event뿐입니다. 그런데 실제 프로그램이 기다리는 것은 fd만이 아닙니다.

기다리는 것 전통적인 방법 Event Loop와 함께 쓸 때의 문제
다른 Thread의 "끝났어요" condition variable pthread_cond_wait와 epoll_wait를 동시에 기다릴 수 없다
1초마다 할 일 alarm/setitimer → SIGALRM, 또는 epoll_wait의 Timeout 계산 Signal Handler의 제약. Timer가 여러 개면 Timeout 계산이 복잡
SIGINT, SIGTERM Signal Handler 아무 때나 끼어든다. async-signal-safe 함수만 쓸 수 있다
File이 바뀌었는가 주기적으로 stat Polling (L21의 Busy Polling과 같은 문제)

Linux의 답은 일관됩니다. "전부 fd로 만들어 줄 테니 epoll에 넣어라."

25-2. eventfd: Kernel 안의 Counter 하나

int efd = eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC);      /* 초기값 0 인 64bit Counter */
동작 효과
write(efd, &n, 8) Counter += n. 기다리는 쪽을 깨운다
read(efd, &v, 8) v = Counter, 그리고 Counter = 0. Counter가 0이었으면 Block(또는 EAGAIN)
epoll Counter > 0이면 EPOLLIN
EFD_SEMAPHORE Flag read가 1만 return하고 Counter를 1만 줄인다

read/write는 반드시 8Byte여야 합니다(아니면 EINVAL).

eventfd_worker.c에서 Worker Thread는 0.1초마다 작업을 끝내고 write로 1을 더합니다. main은 일부러 0.25초씩 늦게 읽습니다.

통지는 5번이었지만 read는 2번이었고 하나도 잃어버리지 않았습니다. 읽기 전에 온 통지는 Counter에 합산됩니다.

fd 개수 1 2

통지가 밀리면 합산된다. 넘치지 않는다 Buffer가 차면 Writer가 Block

25-4. signalfd: Signal을 read로 받는다

기존 과정에서 배운 Signal Handler의 제약을 떠올려 보세요. 아무 명령 사이에나 끼어들고, 그래서 Handler 안에서는 printf도 malloc도 쓸 수 없고(async-signal-safe 함수만), 할 수 있는 일은 volatile sig_atomic_t Flag를 세우는 정도였습니다.

signalfd는 Signal을 일반 Data처럼 받습니다.

sigemptyset(&mask); sigaddset(&mask, SIGINT); sigaddset(&mask, SIGTERM); sigaddset(&mask, SIGUSR1);
sigprocmask(SIG_BLOCK, &mask, NULL);                    /* 1. 먼저 Block: 기본 동작과 Handler 를 막는다 */
int sfd = signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC);      /* 2. Block 된(Pending) Signal 을 fd 로 */
...
struct signalfd_siginfo si;
read(sfd, &si, sizeof(si));                             /* 3. Signal 하나 = 구조체 하나 */

signalfd_demo.c를 실행하고 다른 Terminal에서 Signal을 보냅니다.

kill -TERM $(pgrep signalfd_demo)

Signal 10 (User defined signal 1), 보낸 pid 2590
   → 설정을 다시 읽습니다 (printf, malloc 등을 마음대로 써도 됩니다)
Signal 15 (Terminated), 보낸 pid 2590
   → 정리 후 종료합니다 (Graceful Shutdown)

Signal 처리가 Event Loop 안의 평범한 코드가 되었습니다. 끼어들기가 없으므로 Race Condition도, 함수 제약도 없습니다. ssi_pid로 누가 보냈는지도 알 수 있습니다.

❗ IMPORTANT
sigprocmask로 Block하는 것을 잊으면 안 됩니다. Block하지 않으면 Signal은 signalfd로 오지 않고 기본 동작(종료)이나 Handler로 갑니다. Multi-Thread 프로그램에서는 Thread를 만들기 전에 pthread_sigmask로 Block해야 모든 Thread가 그 Mask를 상속합니다. 그렇지 않으면 Block하지 않은 Thread가 Signal을 받아 Process가 종료됩니다.

주의점 내용
SIGKILL, SIGSTOP Block할 수 없으므로 signalfd로도 받을 수 없다
SIGSEGV, SIGBUS, SIGFPE 동기적으로 발생하는 Signal은 그 명령을 실행한 Thread에 즉시 전달되어야 한다. signalfd에 적합하지 않다
fork + exec Signal Mask는 exec 후에도 유지된다. Child에서 exec 전에 Mask를 복원해야 Child가 Ctrl+C에 반응한다
표준 Signal 같은 Signal이 Pending 중에 여러 번 와도 한 번으로 합쳐진다 (Signal의 원래 성질)

event_loop.c는 네 가지 fd를 하나의 epoll에 넣습니다. data.u32에 출처를 넣어 switch로 분기합니다(L23 25-6).

while (running) {
    n = epoll_wait(epfd, events, 8, -1);                /* 프로그램 전체에서 기다리는 곳은 여기 하나 */
    for (i = 0; i < n; i++)

        }
}

이 구조의 성질을 정리합니다.

  • Block되는 곳이 epoll_wait 하나뿐입니다. 어떤 Event가 와도 즉시 반응합니다.
  • Handler들은 한 Thread에서 순서대로 실행됩니다. ticks, jobs 같은 공유 상태에 Lock이 필요 없습니다(Chapter 4의 문제가 생기지 않음).
  • 대신 Handler 하나가 오래 걸리면 전체가 멈춥니다. 오래 걸리는 일은 Worker Thread로 보내고 완료를 eventfd로 받습니다. 그래서 eventfd가 필요합니다.
  • Ctrl+C가 "아무 때나 죽는 것"이 아니라 Loop를 빠져나와 정리 코드를 거치는 종료가 되었습니다.

정리

  • eventfd: Kernel 안의 64bit Counter. write로 더하고 read로 읽으며 0으로 만든다. Thread → Event Loop 통지에 쓰며 통지가 밀려도 합산되어 유실되지 않는다.
  • timerfd: 만료되면 읽을 수 있게 되는 Timer. read는 놓친 만료 횟수를 알려 주고 주기는 밀리지 않는다.
  • signalfd: Block해 둔 Signal을 read로 받는다. Handler의 제약 없이 일반 코드로 처리. 먼저 Block, Multi-Thread에서는 Thread 생성 전에.
  • inotify: Directory를 Watch하고 IN_CLOSE_WRITE를 기다린다. rename으로 교체되는 File은 Directory 단위로 감시.
  • 모두 file_operations의 .read와 .poll을 구현한 anon_inode입니다. .poll만 있으면 무엇이든 epoll에 넣을 수 있습니다.
  • 하나의 epoll_wait에서만 기다리는 Single Thread Event Loop는 Lock이 필요 없고 Graceful Shutdown이 자연스럽습니다. 오래 걸리는 일은 Worker + eventfd로.
