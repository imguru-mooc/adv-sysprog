read/write 뒤에서 실제로 일어나는 일

영상 17분

read(fd, buf, n) 한 줄이 Disk에 도달하기까지 여섯 개의 층을 지납니다. 그리고 대부분의 경우 Disk까지 가지 않습니다.

학습 목표

  • read()/write() 호출이 지나는 Kernel 계층(VFS, Page Cache, File System, Block Layer, Driver)을 순서대로 설명할 수 있다.
  • fd, open file description(struct file), inode의 관계를 설명하고 Offset이 어디에 있는지 말할 수 있다.
  • Buffer 크기에 따른 System Call 횟수와 처리량의 관계를 측정할 수 있다.
  • Short Read / Short Write를 올바르게 처리하는 Loop를 작성할 수 있다.

11-2. read() 한 번이 지나는 길

User     read(fd, buf, 4096)
           │ glibc Wrapper → syscall 명령                                   (L02)
───────────┼──────────────────────────────────────────────────────────────────────
Kernel     ▼
  ① System Call 계층     ksys_read()      fd 번호 → struct file 을 찾는다, Offset 을 읽는다
  ② VFS                  vfs_read()       권한 확인 → file->f_op->read_iter() 호출   (L12)
  ③ Page Cache           filemap_read()   이 File 의 이 Offset 이 Cache 에 있는가?    (L13)
           ├─ 있음(Hit) ────────────────→ Cache → buf 로 복사하고 return   ← 대부분 여기서 끝난다
           └─ 없음(Miss)
  ④ File System (ext4)   "File 의 N 번째 Block 은 Disk 의 몇 번 Block 인가" (Extent 조회)
  ⑤ Block Layer          I/O 요청(bio) 생성, 병합, Scheduling, Queue
  ⑥ Device Driver        virtio-blk / NVMe / SATA → Hardware 에 명령
───────────┼──────────────────────────────────────────────────────────────────────
Hardware   ▼  Disk 가 Data 를 Memory(Page Cache 의 Page)로 전송 → Interrupt
           그동안 Process 는 Sleep. 깨어나면 ③ 으로 돌아가 Cache → buf 복사

기억할 점 세 가지입니다.

  1. buf로 들어오는 Data는 항상 Page Cache에서 복사된 것입니다. Disk에서 buf로 직접 오지 않습니다(O_DIRECT 제외, L14).
  2. Cache Hit면 ④~⑥과 Hardware는 전혀 관여하지 않습니다. read()는 Memory 복사입니다.
  3. Cache Miss면 Process는 Disk를 기다리며 Sleep합니다. L09의 Major Fault와 같은 상황입니다.

11-4. fd는 무엇을 가리키는가

fd는 그냥 정수입니다. Kernel 안에는 세 단계의 구조가 있습니다.

Process A                         Kernel 전체에서 공유
┌─ fd Table ─┐
│ 0 ─────────┼──→ struct file { f_pos, f_flags, f_op, ... } ──→ struct inode (터미널)
│ 1 ─────────┼──→   (같은 것)
│ 3 ─────────┼──→ struct file { f_pos = 5,  O_RDONLY }  ─┐
│ 4 ─────────┼──→   (3 과 같은 것: dup)                   ├──→ struct inode (/etc/passwd)
│ 5 ─────────┼──→ struct file { f_pos = 0,  O_RDONLY }  ─┘      └─ Page Cache (address_space)
└────────────┘
구조 단위 담고 있는 것
fd Table Process마다 정수 → struct file 포인터
struct file (open file description) open() 호출마다 현재 Offset, 열기 Flag(O_RDONLY, O_APPEND, O_NONBLOCK...), f_op
struct inode File마다 하나 크기, 권한, 시간, Disk 위치, 그리고 그 File의 Page Cache

실행 중인 Process의 fd는 /proc에서 볼 수 있습니다.

ls -l /proc/$$/fd
cat /proc/$$/fdinfo/0

lrwx------ 1 user user 64 ... 0 -> /dev/pts/0
lrwx------ 1 user user 64 ... 1 -> /dev/pts/0
lrwx------ 1 user user 64 ... 2 -> /dev/pts/0
lr-x------ 1 user user 64 ... 255 -> /dev/pts/0

pos:	0
flags:	02002
mnt_id:	28
ino:	3

pos가 Offset, flags가 열기 Flag(8진수)입니다. 둘 다 struct file에 있는 값입니다.

11-5. Offset은 어디에 있는가

fd_share.c는 같은 File을 가리키는 fd 세 개를 만듭니다.

a = open("/etc/passwd", O_RDONLY);
b = dup(a);                             /* 같은 struct file */
c = open("/etc/passwd", O_RDONLY);      /* 새로운 struct file, 같은 inode */

./fd_share

a 에서 5 Byte 를 읽은 뒤:
  a          fd=3  offset=5
  b = dup(a) fd=4  offset=5
  c = open() fd=5  offset=0
Child 가 a 에서 7 Byte 를 읽은 뒤 (Parent 에서 확인):
  a          fd=3  offset=12
  c          fd=5  offset=0
  • a에서 읽었는데 b의 Offset도 움직였습니다. dup은 struct file을 공유합니다.
  • c는 같은 File인데 Offset이 독립적입니다. open을 다시 하면 struct file이 새로 만들어집니다.
  • Child가 읽은 것이 Parent의 Offset을 움직였습니다. fork는 fd Table을 복사할 뿐 struct file은 공유합니다.

기존 과정에서 배운 것들이 이 구조로 설명됩니다.

현상 이유
Shell의 cmd > out.txt 2>&1에서 stdout과 stderr가 서로를 덮어쓰지 않는다 2>&1은 dup2. 같은 struct file, 같은 Offset
fork 후 Parent와 Child가 같은 File에 쓰면 이어서 기록된다 struct file 공유
두 Process가 각자 open해서 같은 Log File에 쓰면 서로 덮어쓴다 struct file이 달라 Offset이 독립. 해결: O_APPEND(쓰기 직전에 Kernel이 Offset을 File 끝으로 Atomic하게 이동)

11-7. read는 요청한 만큼 주지 않을 수 있다

read(fd, buf, 4096)의 return 값은 "4096" 또는 "0(EOF)"만 있는 것이 아닙니다. short_io.c

(sleep 1; echo hello; sleep 1; echo world) | ./short_io

read() #1: 4096 요청 → 6 Byte
hello
read() #2: 4096 요청 → 6 Byte
world
read() = 0 → EOF
return 의미
요청한 크기 전부 읽음
0 < n < 요청 Short Read. 오류가 아님. 지금 줄 수 있는 만큼만 준 것
0 EOF (Pipe/Socket: 상대가 닫음)
-1 오류. errno == EINTR이면 Signal로 중단된 것이므로 다시 시도

Short Read/Write가 일어나는 경우: Pipe, Terminal, Socket, File의 끝부분, Signal에 의한 중단, Disk Full(write). 일반 File에서는 드물지만 코드는 항상 Loop로 작성합니다.

static ssize_t write_all(int fd, const void *buf, size_t count)
{
    const char *p = buf;
    size_t left = count;

    while (left > 0) {
        ssize_t n = write(fd, p, left);
        if (n < 0) {
            if (errno == EINTR) continue;
            return -1;
        }
        p += n;
        left -= (size_t)n;
    }
    return (ssize_t)count;
}

11-8. write가 return했다는 것의 의미

Animation의 세 번째 Scenario에서 봤듯이 write()의 경로는 read()의 Cache Hit와 같습니다.

write(fd, buf, n)
  → ① fd → struct file    → ② VFS    → ③ Page Cache: buf 의 내용을 Cache 의 Page 로 복사
                                          그 Page 에 Dirty 표시
  ← return n                             ← 여기서 끝. ④~⑥ 은 호출되지 않았다

write()가 성공했다는 것은 "Data가 Kernel의 Page Cache에 복사되었다" 는 뜻입니다. Disk에는 아직 가지 않았을 수 있습니다.

이 시점에 결과
같은 File을 다른 Process가 read() 새 내용이 보인다 (같은 Page Cache)
프로그램이 Crash하거나 kill -9 안전. Data는 Kernel에 있고 Kernel이 나중에 Disk에 쓴다
전원이 꺼지거나 Kernel Panic 유실

Dirty Page가 언제 Disk로 가는지, 그것을 어떻게 보장받는지는 L15에서 다룹니다.

make clean

정리

  • read()는 System Call 계층 → VFS → Page Cache → File System → Block Layer → Driver 순으로 내려갑니다. Cache Hit면 Page Cache에서 끝나고 Memory 복사만 일어납니다.
  • fd는 Process별 Table의 번호이고, Offset과 열기 Flag는 struct file에, File의 속성과 Page Cache는 inode에 있습니다. dup과 fork는 struct file을 공유하고 open은 새로 만듭니다.
  • 작은 Buffer의 I/O는 System Call 고정 비용이 지배합니다. strace -c에 수백만 번의 read/write가 보이면 I/O 단위를 의심합니다.
  • read/write는 요청보다 적게 처리할 수 있습니다. 항상 Loop로 작성하고 EINTR을 처리합니다.
  • write()의 성공은 Page Cache에 복사되었다는 뜻이지 Disk에 저장되었다는 뜻이 아닙니다.

read/write 는 요청보다 적게 처리할 수 있어 반복문으로 끝까지 처리해야 합니다(short_io). fd → fd table → struct file(Offset, Flag) → inode 구조에서 Offset 은 struct file 에 있으므로 fork/dup 한 fd 는 Offset 을 공유합니다(fd_share). 성능은 System Call 횟수가 좌우합니다(🎬 C3-1).

"read()를 호출하면 항상 Disk를 읽는가?"의 답은 아니오입니다. 오히려 Disk를 읽는 경우가 예외입니다.

13-2. Page Cache의 구조

질문 답
왜 필요한가 DRAM은 약 100ns, NVMe SSD는 약 100µs, HDD는 약 10ms. 1,000배 ~ 100,000배 차이
어디에 있는가 inode마다 하나씩(inode->i_mapping, struct address_space). File Offset → Page를 찾는 Tree(XArray)
단위 4KB Page(최근 Kernel은 여러 Page를 묶은 Folio). File의 Offset 0~4095가 Page 0
누가 공유하는가 그 File을 읽는 모든 Process. read()도 mmap도 같은 Page를 본다
크기 제한 없음. 남는 Memory 전부. 다른 용도로 Memory가 필요해지면 즉시 내어 준다 
                       inode #573813 (cache.dat)
                         └─ address_space ─┬─ Page 0   (offset 0 ~ 4095)       ← Process A 의 read()
                                           ├─ Page 1                             ← Process B 의 mmap PTE
                                           ├─ (Page 2 는 Cache 에 없음)
                                           └─ Page 3   [Dirty]                   ← 누군가 write() 함

L10에서 "mmap은 Page Cache의 Frame을 PTE에 직접 연결한다"고 했던 그 Page가 이것입니다. L09의 Minor/Major Fault도 "이 Tree에 Page가 있는가"의 차이였습니다.

Page Cache가 inode에 붙어 있다는 점이 중요합니다. 서로 다른 Process가, 서로 다른 fd로, 심지어 Hard Link된 다른 이름으로 열어도 같은 Cache를 씁니다.

13-5. File의 어느 부분이 Cache에 있는가

mincore() System Call은 Mapping된 영역의 각 Page가 Memory에 있는지를 접근하지 않고 알려 줍니다. resident.c는 File을 mmap하고 mincore로 상주 Page 수를 셉니다(공통 코드는 cachelib.h).

./resident cache.dat /usr/bin/gcc /usr/lib/x86_64-linux-gnu/libc.so.6

cache.dat                                   65536 /    65536 pages  100.0%
/usr/bin/gcc                                  250 /      250 pages  100.0%
/usr/lib/x86_64-linux-gnu/libc.so.6           412 /      555 pages   74.2%

방금 make를 했으므로 gcc가 통째로 Cache에 있습니다. libc는 실제로 쓰인 부분만 올라와 있습니다(Demand Paging, L06).

이 File만 Cache에서 내보낼 수도 있습니다. root 권한이 필요 없습니다.

./resident -e cache.dat

cache.dat                                       0 /    65536 pages    0.0%

-e는 posix_fadvise(fd, 0, 0, POSIX_FADV_DONTNEED)를 호출합니다. "이 File의 Cache는 더 필요 없다"는 Hint입니다. cache_hit.c가 첫 번째 읽기 전에 쓴 방법이고, System 전체에 영향을 주는 drop_caches보다 안전합니다.

같은 일을 하는 표준 도구가 fincore입니다.

13-6. Readahead

readahead.c는 Cache를 비운 뒤 1Byte만 읽고 Cache 상태를 봅니다.

./readahead

시작 (Cache 비움)                        cache      0 pages (0 KB)
1 Byte 읽음 (offset 0)                     cache      4 pages (16 KB)
순차로 256KB 읽음                       cache     80 pages (320 KB)
FADV_RANDOM 후 무작위로 4KB × 64 읽음 cache     64 pages (256 KB)
  • 1Byte를 요청했는데 4 Page(16KB) 가 올라왔습니다. Disk I/O는 "얼마나 읽는가"보다 "몇 번 요청하는가"가 비쌉니다. 어차피 Disk에 가는 김에 뒤쪽도 함께 가져옵니다.
  • 순차로 256KB를 읽었더니 320KB가 올라와 있습니다. Kernel이 순차 접근을 감지하고 요청보다 앞서 읽어 두고 있습니다. 순차 접근이 계속되면 Window를 점점 키웁니다(최대 read_ahead_kb, 기본 128KB).
  • POSIX_FADV_RANDOM으로 "무작위로 읽겠다"고 알려 주니 정확히 읽은 만큼(64 Page)만 올라왔습니다. 쓸모없는 Readahead를 하지 않습니다.
cat /sys/block/sda/queue/read_ahead_kb

128

(Disk 이름은 lsblk로 확인합니다. VirtualBox에서는 보통 sda입니다.)

L09에서 32,768 Page를 읽는데 Major Fault가 수백 번뿐이었던 이유가 이것입니다. 순차 읽기가 무작위 읽기보다 훨씬 빠른 이유는 Disk의 물리적 특성만이 아니라 Readahead가 I/O 대기를 숨겨 주기 때문이기도 합니다.

13-7. Cache가 가득 차면: Reclaim

Page Cache는 남는 Memory를 전부 쓰므로 언젠가는 가득 찹니다. 새 Page가 필요하면 Kernel은 기존 Page를 회수합니다(Reclaim).

Page의 상태 회수 방법 비용
Clean File Page 그냥 버린다. 필요하면 Disk에서 다시 읽으면 된다 거의 없음
Dirty File Page 먼저 Disk에 써야 버릴 수 있다 Disk 쓰기
Anonymous Page (Heap, Stack) 되돌릴 File이 없다. Swap에 써야 한다 Disk 쓰기 + 나중에 Major Fault

어느 Page를 버릴지는 L07의 Accessed bit와 Active/Inactive 두 개의 LRU List로 정합니다. 한 번만 읽힌 Page는 Inactive에, 다시 접근된 Page는 Active로 승격됩니다. 큰 File을 한 번 훑는 작업(Backup 등)이 자주 쓰는 Page를 전부 밀어내지 못하게 하는 장치입니다.

grep -E "^(Active\(file\)|Inactive\(file\)):" /proc/meminfo

Active(file):    1204816 kB
Inactive(file):  1782772 kB

📌 NOTE
Memory가 넉넉한데도 Swap이 조금씩 쓰이는 것은 이상이 아닙니다. 오랫동안 접근되지 않은 Anonymous Page를 Swap으로 보내고 그 Memory를 Page Cache로 쓰는 편이 전체 성능에 이롭다고 Kernel이 판단한 것입니다. 이 경향은 vm.swappiness로 조절합니다.

13-8. Application이 Cache에 줄 수 있는 Hint

int posix_fadvise(int fd, off_t offset, off_t len, int advice);
advice 효과 쓰는 곳
POSIX_FADV_SEQUENTIAL Readahead Window를 2배로 큰 File을 처음부터 끝까지 처리
POSIX_FADV_RANDOM Readahead 끔 Database의 Index 접근
POSIX_FADV_WILLNEED 지정 범위를 지금 비동기로 읽어 둠 곧 필요할 Data를 미리
POSIX_FADV_DONTNEED 지정 범위의 Clean Page를 Cache에서 내보냄 한 번 쓰고 다시 안 볼 큰 File(Backup, Log 압축)이 다른 Cache를 밀어내지 않게

mmap 영역에는 같은 역할의 madvise()(MADV_SEQUENTIAL, MADV_RANDOM, MADV_WILLNEED, MADV_DONTNEED)가 있습니다.

정리

  • Page Cache는 File 내용을 Page 단위로 Memory에 보관합니다. inode마다 있고, 그 File을 쓰는 모든 Process와 read/mmap이 공유합니다.
  • 남는 Memory는 전부 Page Cache로 쓰입니다. Memory 여유는 free가 아니라 available로 판단합니다.
  • Cache Hit인 read()는 Memory 복사입니다. 같은 File의 두 번째 읽기가 수십 배 빠른 이유입니다.
  • mincore/fincore로 상주 상태를 보고, posix_fadvise(DONTNEED)로 특정 File만 비울 수 있습니다. drop_caches는 실험용입니다.
  • Readahead: Kernel은 순차 접근을 감지해 미리 읽습니다. 접근 Pattern을 posix_fadvise로 알려 줄 수 있습니다.
  • Cache가 가득 차면 Clean Page는 버리고, Dirty Page는 기록 후 버리고, Anonymous Page는 Swap으로 보냅니다.

"O_DIRECT는 Cache를 거치지 않으니 빠르다"는 흔한 오해입니다. O_DIRECT는 Kernel의 Cache와 Readahead라는 이점을 포기하는 것입니다. 빨라지는 것은 Application이 그보다 나은 자기만의 Cache와 I/O Scheduling을 갖고 있을 때뿐입니다.

14-8. 선택 기준

  1. 기본은 Buffered I/O입니다. 적절한 Buffer 크기(64KB~1MB)와 posix_fadvise Hint면 대부분 충분합니다.
  2. 읽기 위주의 무작위 접근 + 반복 + Memory에 들어가는 크기이면 mmap을 검토합니다.
  3. 자체 Cache를 구현했고 I/O 시점을 직접 제어해야 하면 O_DIRECT. 이 경우 비동기 I/O(Chapter 6의 io_uring)와 함께 쓰는 것이 일반적입니다. O_DIRECT의 read()는 Cache Hit가 없어 매번 Disk를 기다리며 Block하기 때문입니다.
  4. 어느 쪽이든 측정합니다. Cold와 Warm, 순차와 무작위를 구분해서.

정리

  • Buffered: Disk → Page Cache → (복사) → User Buffer. 기본이고 대부분의 경우 최선.
  • Direct(O_DIRECT): Disk → User Buffer. Page Cache를 거치지 않으므로 복사가 없지만 Cache Hit도 Readahead도 없다. Buffer 주소, 크기, Offset의 정렬이 필요.
  • mmap: Page Cache를 주소 공간에 직접 연결. 복사와 System Call이 없어 작은 단위의 무작위 반복 접근에 강하다. 오류는 SIGBUS, 쓰기 시점은 Kernel이 결정.
  • Disk가 병목인 Cold 상황에서는 셋이 비슷하고, 차이는 Warm에서 난다.
  • 자체 Cache를 가진 Database는 O_DIRECT, 읽기 위주의 공유 Data는 mmap, 그 외에는 Buffered.

15-1. write() 직후 Data는 어디에 있는가

dirty_watch.c는 200MB를 write()하고, 그 전후로 /proc/meminfo의 Dirty(아직 Disk에 쓰지 않은 Page Cache의 양)를 출력합니다.

./dirty_watch

시작                         Dirty       28 kB   Writeback        0 kB
write() 200MB 완료 직후      Dirty   204804 kB   Writeback        0 kB
   write() 에 걸린 시간 :     32.1 ms  (6235 MB/s)
fsync() 완료 직후            Dirty       24 kB   Writeback        0 kB
   fsync() 에 걸린 시간 :   1840.5 ms

(fsync 시간은 Disk에 따라 크게 다릅니다.)

  • write() 200MB가 32ms에 끝났습니다. 초당 6GB. 어떤 Disk도 이렇게 빠르지 않습니다. Memory 복사였기 때문입니다.
  • 그 직후 Dirty가 정확히 200MB 늘어 있습니다. Data는 전부 Page Cache에 있고 Disk에는 한 Byte도 가지 않았습니다.
  • fsync()가 1.8초 걸렸고, 끝나자 Dirty가 0으로 돌아왔습니다. 실제 Disk 쓰기는 여기서 일어났습니다.

"write()가 성공하면 Disk에 저장된 것인가?"의 답은 아니오입니다.

15-2. Writeback: Kernel이 알아서 쓰는 시점

fsync를 부르지 않아도 Dirty Page는 결국 Disk로 갑니다. Kernel의 Flusher Thread(kworker/u*:*-flush-8:0 같은 이름)가 Background에서 기록합니다. 이것을 Writeback이라고 합니다.

sysctl vm.dirty_expire_centisecs vm.dirty_writeback_centisecs vm.dirty_background_ratio vm.dirty_ratio

vm.dirty_expire_centisecs = 3000
vm.dirty_writeback_centisecs = 500
vm.dirty_background_ratio = 10
vm.dirty_ratio = 20
계기 설정 동작
시간 dirty_writeback_centisecs = 5초마다 Flusher가 깨어나 dirty_expire_centisecs = 30초 넘게 Dirty였던 Page를 기록 Background
양 (1단계) Dirty가 사용 가능 Memory의 dirty_background_ratio = 10% 를 넘으면 기록 시작 Background. Application은 계속 진행
양 (2단계) Dirty가 dirty_ratio = 20% 를 넘으면 write()를 호출한 Process가 직접 기록하며 Block된다
명시적 요청 fsync, fdatasync, msync, sync, O_SYNC 호출한 쪽이 완료까지 대기
Memory 부족 Reclaim이 Dirty Page를 만남 (L13)

정리하면 전원이 갑자기 꺼졌을 때 최대 약 30초 분량의 write()가 유실될 수 있습니다. 프로그램 Crash나 kill -9에서는 유실되지 않습니다(Data는 Kernel에 있으므로).

📌 NOTE
2단계가 "평소에는 빠르던 write()가 갑자기 몇 초씩 멈추는" 현상의 원인입니다. 대량의 쓰기가 Disk 속도를 넘어서 계속되면 Dirty가 20%에 도달하고, 그때부터 write()는 Disk 속도로 떨어집니다. Memory가 큰 Server에서는 20%가 수십 GB이므로 vm.dirty_bytes, vm.dirty_background_bytes로 절대값을 지정하기도 합니다.

Writeback이 비동기인 이유는 성능입니다. 여러 번의 작은 쓰기를 모아 한 번에 기록할 수 있고, 같은 Page를 100번 고쳐도 Disk에는 한 번만 쓰며, 곧 지워질 임시 File은 아예 Disk에 가지 않습니다.

15-4. fsync와 그 친척들

호출 보장하는 것 return 시점
write() Page Cache에 복사됨 즉시
fsync(fd) 이 File의 Data + 모든 Metadata(크기, 수정 시각, Block 위치)가 저장 장치에 기록됨 장치가 완료를 보고한 뒤
fdatasync(fd) Data + Data를 읽는 데 필요한 Metadata만(크기, Block 위치). 수정 시각(mtime) 등은 생략 같음. Metadata 기록이 줄어 더 빠를 수 있음
open(..., O_SYNC) 모든 write()가 fsync를 포함 write()가 느려짐
open(..., O_DSYNC) 모든 write()가 fdatasync를 포함 〃
sync(), syncfs(fd) System 전체 / File System 하나의 모든 Dirty Page 완료 후
msync(addr, len, MS_SYNC) mmap 영역 (L10) 완료 후
sync_file_range() 지정 범위의 Writeback을 시작시킴 Metadata와 장치 Cache를 보장하지 않음. 영속성 용도로 쓰면 안 됨

fsync가 하는 일은 Dirty Page를 쓰는 것만이 아닙니다. 마지막에 Disk에게 "네 내부 Cache도 비워라"(FLUSH 명령)를 보냅니다. Disk에도 자체 Write Cache(DRAM)가 있어서, 이 명령 없이는 "Disk가 받았다"가 "매체에 기록되었다"를 의미하지 않습니다.

fdatasync가 빠른 경우는 이미 할당된 영역을 덮어쓸 때입니다(Database의 Data File). File 크기가 바뀌는 Append에서는 크기 Metadata를 써야 하므로 fsync와 비슷합니다.

위 결과의 마지막 줄이 해법입니다. 여러 Record를 모아서 fsync 한 번.

매번 fsync       : [W][fsync........][W][fsync........][W][fsync........]
100 개마다 fsync : [W][W][W]...[W][fsync........]                          ← 100 개가 fsync 비용 한 번을 나눠 가진다

fsync 한 번의 비용은 Data가 4KB든 400KB든 크게 다르지 않습니다(장치의 응답 지연이 지배). 그래서 묶을수록 Record당 비용이 줄어듭니다.

어디에서 쓰는가 방식
PostgreSQL, MySQL의 WAL/Redo Log 동시에 Commit하려는 Transaction들을 모아 fsync 한 번. 각 Transaction은 그 fsync가 끝난 뒤에 "Commit 완료"를 응답
Redis AOF appendfsync everysec 1초마다 fsync. 최대 1초 유실을 감수하고 처리량 확보
Kafka 기본은 fsync하지 않고 Replica 복제로 내구성 확보

영속성은 0과 1이 아니라 "얼마나 유실을 감수할 것인가"와 처리량의 거래입니다.

15-7. File을 안전하게 교체하기

설정 File을 새 내용으로 저장하는 흔한 코드입니다.

fd = open("config.txt", O_WRONLY | O_TRUNC);    /* ← 이 순간 기존 내용이 사라진다 */
write(fd, new_content, len);                    /* ← 여기서 Crash 하거나 전원이 꺼지면? */
close(fd);

O_TRUNC와 write 사이, 또는 write 도중에 문제가 생기면 옛 내용도 새 내용도 아닌 빈 File이나 반쪽 File이 남습니다. safe_save.c는 표준적인 해법입니다.

fd = open("config.txt.tmp", O_WRONLY | O_CREAT | O_TRUNC, 0644);   /* 1. 원본은 건드리지 않는다 */
write_all(fd, text, len);
fsync(fd);                                                         /* 2. 새 내용이 Disk 에 있음을 보장 */
close(fd);
rename("config.txt.tmp", "config.txt");                            /* 3. 이름 교체는 Atomic (L12) */
dfd = open(".", O_RDONLY | O_DIRECTORY);
fsync(dfd);                                                        /* 4. "이름이 바뀌었다" 도 Disk 에 */

2번의 fsync를 빼면 안 됩니다. rename(Metadata)이 Data보다 먼저 Disk에 도달하면, 재부팅 후 config.txt라는 이름이 내용이 비어 있는 새 File을 가리키게 됩니다. 4번은 Directory도 File이고, 이름의 변경은 그 Directory의 내용 변경이기 때문에 필요합니다.

15-8. fsync가 실패하면

if (fsync(fd) < 0) { ... }      /* return 값을 반드시 확인한다 */

fsync의 실패(EIO, ENOSPC)는 "Page Cache에 있던 Data를 Disk에 쓰지 못했다" 는 뜻입니다.

⚠ WARNING
fsync가 실패한 뒤 다시 fsync를 호출해서 성공이 return되어도 Data가 기록되었다는 뜻이 아닙니다. Kernel은 기록에 실패한 Page의 Dirty 표시를 지우고 오류를 한 번만 보고합니다. 두 번째 fsync는 "쓸 것이 없으니 성공"입니다. 2018년 PostgreSQL에서 발견되어 "fsyncgate"로 알려진 문제입니다. 올바른 처리는 재시도가 아니라 그 Data를 신뢰하지 않고(Log에서 복구하거나) 중단하는 것입니다.

close()도 같습니다. close는 fsync를 하지 않습니다. close가 성공했다고 Data가 Disk에 있는 것이 아니며, NFS 등에서는 close가 지연된 쓰기 오류를 return하기도 하므로 return 값을 확인합니다.

15-9. Chapter 3 정리

read(fd) / write(fd)
   fd → struct file (Offset, Flag, f_op) → inode                                        L11
        └ f_op->read_iter: ext4 / pipe / procfs / Driver 로 분기 (VFS)                   L12
   Page Cache (inode 마다, 모든 Process 와 mmap 이 공유)                                 L13
        read : Hit → 복사하고 끝          Miss → Disk → Cache → 복사   (+ Readahead)
        write: Cache 에 복사, Dirty 표시, return                        ← Disk 에 가지 않았다
   경로의 선택: Buffered(복사 1) / O_DIRECT(Cache 없음) / mmap(복사 0, System Call 0)      L14
   Dirty → Disk: Writeback(30 초, 10%, 20%) 또는 fsync / fdatasync                       L15
        안전한 교체: tmp → fsync → rename → fsync(dir)

make clean

정리

  • write()는 Page Cache에 복사하고 Dirty 표시를 한 뒤 return합니다. Disk 기록은 나중입니다.
  • Writeback: Flusher Thread가 30초 지난 Dirty Page를, 또는 Dirty가 10% 를 넘으면 Background로 기록합니다. 20% 를 넘으면 write() 자체가 Block됩니다.
  • fsync는 Data + Metadata + Disk Write Cache Flush까지 끝난 뒤 return합니다. fdatasync는 Data를 읽는 데 필요 없는 Metadata를 생략합니다.
  • 매번 fsync하면 1,000배 느려집니다. 여러 Record를 모아 한 번에 fsync하는 Group Commit이 해법입니다.
  • 안전한 File 교체: 임시 File에 쓰기 → fsync → rename → Directory fsync.
  • fsync와 close의 return 값을 확인합니다. fsync 실패 후의 재시도 성공은 의미가 없습니다.
